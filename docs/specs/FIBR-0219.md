# FIBR-0219 — Accept a locale-formatted amount without ever guessing an ambiguous one

**Status:** 📋 **DRAFT** — awaiting the `/cold-eyes` gate (§13).
**Kind:** fix.
**Source:** ROADMAP FIBR-0219 (code-quality-review-2026-08-03), split out of
FIBR-0216 on 2026-08-03 because the obvious fix measured as a silent 100x error.
**Pairs with:** FIBR-0216 (made the manual-entry placeholder non-translatable so
the hint could not disagree with the parser; §9 decision 4 explains why this item
leaves that placeholder alone), FIBR-0153 (`_format_amount`, the display side
this input side must round-trip), FIBR-0105 (the negative-style wrapper, which is
display-only and out of scope).

**Layman:** If your computer writes numbers the European way — `1.234,56` — you
currently cannot type the number part of an amount back the way finbreak just
showed it to you. This makes the app accept your way of writing numbers *and* the
plain `12.34` way. And when a typed number could mean two different things, it
asks you instead of guessing, because guessing wrong on a money field is off by a
factor of 100 or 1000.

## 1. Goal

The manual-entry Amount field accepts the **numeric part** of the amount the app
itself just displayed, under the user's own locale, **without** ever silently
resolving an input that two conventions read as two different numbers.

*Numeric part*, precisely: `_format_amount` renders `«symbol»␣«magnitude»` and
wraps a negative in `-` or `( )`; `forecast.py` prepends a further `+` for a
positive projection. Only the **magnitude** is in scope — the currency symbol and
the bracket form stay refused (§9 decisions 2 and 6), and so does `forecast.py`'s
composite `+R 1<NBSP>234,56`, because of the symbol rather than the `+`. A goal
stated as "accepts what was displayed" would authorise symbol-stripping that no
invariant here requires.

A **bare** leading `+` (`+12.34`) is accepted, before and after this item —
verified 2026-08-04, `parse_transaction("2026-07-01", "+12.34", "x", 2)` stores
1234 minor units today. R3 normalises `positiveSign()` and §4.5 step 3's pattern
is anchored `^[+-]?` precisely because of it. Stated here because an earlier
draft listed `+` as refused, which would have had an implementer add a rejection
that regresses working input.

Three properties, in priority order, and the second is the one this item exists
for:

1. Every input unambiguous **by shape** (§2.3) is accepted — in the locale's convention *and* in the
   C convention, under every locale.
2. Every **ambiguous** input is refused, visibly, naming both readings. A
   refusal costs a retype; a wrong guess costs a factor of 100 or 1000 on
   somebody's money.
3. Nothing about how a **bank file** imports changes. Import must not depend on
   the desktop locale.

## 2. Problem

Display goes through `_format_amount` (`ui/_amount.py`), whose magnitude is
`QLocale().toString(float(abs(display)), "f", decimals)` — grouped, with
locale-correct separators. Input goes through `ManualEntryDialog._on_add`
(`ui/manual_entry.py`), which passes `self._amount.text()` straight to
`TransactionService.add_transaction` → `parse_transaction`
(`services/transactions.py`), which does `Decimal(str(raw_amount).strip())` — the
C convention and nothing else.

So under a locale that writes `1.234,56`, the app displays a number the user
cannot type back. It is refused, which is safe but wrong.

### 2.1 The measured matrix, and why the obvious fix is a regression

Re-measured 2026-08-04 on the pinned PySide6 (the same result the 2026-08-03
ROADMAP bullet records). §2.1's and §2.2's `qt` / `C` columns are reproducible from the repo with the
snippet below; the `naive` column, §4.3's two-order table and §4.4's extra
locales are separate one-off measurements, and INV-7 is the durable form of all
of them:

```bash
. .venv/bin/activate && QT_QPA_PLATFORM=offscreen python -c '
from decimal import Decimal, InvalidOperation
from PySide6.QtCore import QLocale
for n in ["en_US","en_ZA","de_DE","fr_FR","sv_SE"]:
    loc = QLocale(n)
    print(n, repr(loc.decimalPoint()), repr(loc.groupSeparator()), repr(loc.negativeSign()))
    for s in ["-12.34","-12,34","-1.234,56","1.234","1,500","1234,500"]:
        v, ok = loc.toDouble(s)
        try: c = Decimal(s)
        except InvalidOperation: c = None
        print("  ", repr(s), "qt=", v if ok else "REJ", "C=", c)'
```

`qt` is `QLocale(name).toDouble(s)`; `C` is `Decimal(s)`; `naive`
is the obvious fix — *strip the group separator, swap the decimal point for a
dot*:

| Locale | decimal point | group separator | negative sign |
|--------|---------------|-----------------|---------------|
| `en_US` | `.` U+002E | `,` U+002C | `-` U+002D |
| `en_ZA` | `,` U+002C | NBSP U+00A0 | `-` U+002D |
| `de_DE` | `,` U+002C | `.` U+002E | `-` U+002D |
| `fr_FR` | `,` U+002C | NNBSP U+202F | `-` U+002D |
| `sv_SE` | `,` U+002C | NBSP U+00A0 | **`−` U+2212** |

Four grouping conventions across the five measured locales — and `en_ZA` is the
base-currency locale of this
app's primary audience, so the gap bites the default user, not only a German
one. The rows that matter:

| Locale | Input | `qt` | `C` | `naive` |
|--------|-------|------|-----|---------|
| `de_DE` | `-12.34` | **rejected** | `-12.34` | **`-1234`** ← 100x, silent |
| `de_DE` | `-1234.56` | rejected | `-1234.56` | **`-123456`** ← 100x, silent |
| `de_DE` | `-12,34` | `-12.34` | rejected | `-12.34` |
| `de_DE` | `-1.234,56` | `-1234.56` | rejected | `-1234.56` |
| `en_ZA` | `-12,34` | `-12.34` | rejected | `-12.34` |
| `fr_FR` | `-1<NNBSP>234,56` | `-1234.56` | rejected | `-1234.56` |
| `en_US` | `-1,234.56` | `-1234.56` | rejected | `-1234.56` |

The `naive` column is the regression the ROADMAP bullet names: under `de_DE` a
typed `-12.34` becomes `-1234`, accepted, stored, and never flagged. Today that
same input is merely refused.

**The mechanism behind the fix is in the first column.** `QLocale::toDouble`
does not merely re-read separators — it **validates group placement**, so
`-12.34` under `de_DE` is *rejected* rather than read as `-1234`. That is the
property the naive string-munge threw away: it transformed without validating.

### 2.2 Where the genuine ambiguity is, measured

Both conventions succeeding *and disagreeing* is a small, precisely bounded set.
Same script, second run:

| Locale | Input | `qt` | `C` | |
|--------|-------|------|-----|---|
| `de_DE` | `1.234` | `1234` | `1.234` | **disagree** |
| `de_DE` | `12.345` | `12345` | `12.345` | **disagree** |
| `de_DE` | `-1.234` | `-1234` | `-1.234` | **disagree** |
| `de_DE` | `1.23` | rejected | `1.23` | one only |
| `de_DE` | `1.2345` | rejected | `1.2345` | one only |
| `en_US` | `1.234` | `1.234` | `1.234` | agree |
| `en_ZA`, `fr_FR` | *(every row)* | — | — | **no disagreement** |

Parser disagreement arises only where the locale's group separator is `.` — the
`de_DE` family — and only for a group of **exactly three** digits, because Qt
rejects a wrong-sized group (`1.23`, `1.2345`).

### 2.3 Parser disagreement is NOT the same thing as reading ambiguity

The §2.2 result is about the two *parsers* disagreeing. It is not the hazard, and
building the rule out of it alone ships the bug this item exists to prevent.

The dangerous class is a string that **one** parser accepts and the other merely
**rejects**, where the rejected convention would have read it as a *different
number*. Measured 2026-08-04, and this is the app's own primary locale:

| Locale | Input | `qt` | `C` | Naive "one candidate → take it" |
|--------|-------|------|-----|--------------------------------|
| `en_ZA` | `1,500` | `1.500` | rejected | **`1.5`** → stored as 150 minor units |
| `en_ZA` | `12,500` | `12.500` | rejected | **`12.5`** |
| `de_DE` | `2,000` | `2.000` | rejected | **`2.0`** |
| `fr_FR` | `1,250` | `1.250` | rejected | **`1.25`** |

A user typing `1,500` for one thousand five hundred — the US/UK grouping, and
the commonest thing to paste — gets **R 1,50**. `parse_transaction` does not save
us: `Decimal("1.500").normalize()` has one significant fractional digit, inside
exponent 2, so it is accepted and stored. **1000x, silent, and a regression** —
today that string is refused.

So ambiguity is a property of the **string's shape**, not of whether both parsers
happened to succeed. §4.5 step 3 is built on the shape, and it is the tie-break
for the case where only one convention produced a candidate at all.

The ambiguous shape is `<digits><separator><exactly 3 digits>`: it reads as a
thousands group in one convention and a three-place fraction in the other, and
both readings are structurally valid. The **tail** is what is constrained — a run
of one, two, four or more digits after the separator cannot be a group. The
**head** is not: a partially-grouped string is a shape people actually type, and
measured 2026-08-04, `1234,500` under `en_ZA` / `de_DE` / `fr_FR` leaves exactly
one surviving candidate at `1234.500`, stored as 123 450 minor units where the
user meant 1 234 500. Bounding the head to three digits would refuse `1,500` and
wave `1234,500` through — the same 1000x error, one digit further along.

## 3. Scope decisions

1. **`parse_transaction` does not change.** It is reused per-row by
   `csv_importer`, `ofx_importer` and `standard_bank`
   (verified: `grep -rn "parse_transaction(" src/` — the trailing `(` excludes the
   prose mentions; five hits, one of them the `def` line, leaving four call sites,
   three of them importers). Teaching it the desktop locale would make a bank statement
   import to different numbers on two machines — strictly worse than the bug
   being fixed. Bank files are machine data and keep their own conventions.
2. **The locale layer goes at the human-input seam only**, beside the display
   function it mirrors: a new `parse_amount_input` in `ui/_amount.py`.
3. **One call site.** `ManualEntryDialog` is the only typed-amount field in the
   app (verified 2026-08-04 with a **recursive** enumeration of every
   `QLineEdit` / `.text()` under `src/finbreak/ui/`, not a `ui/*.py` glob: the
   only money-bearing one is inside `ManualEntryDialog._on_add`. The other
   free-text fields are `start_over` (a confirm word), `set_hint` (a password
   hint) and `import_wizard` (a custom date format); `transfers.py`, `home.py`
   et al. import `_format_amount` for display only).
4. **Refuse ambiguity; never resolve it.** §8 alternative 2 records the
   resolution rule that was rejected and why.
5. **Money stays exact `Decimal`.** Qt's `toDouble` returns a float and is used
   **only as a validator**; the value is rebuilt from the input string.

## 4. Design

### 4.1 `parse_amount_input(text: str) -> Decimal`

New function in `ui/_amount.py`, beside `_format_amount`. The placement is a
**layering** call, not a reuse one: the rule is locale presentation, its only
caller is a widget, and **`parse_transaction` and the importers** must stay
locale-free or INV-1 fails. Putting it beside `parse_transaction` would drop
`QLocale` into the function whose whole guarantee here is that it does not know
about locales.

*Not* "`services/` must stay locale-free" — that whole-layer claim is false and
an implementer must not rely on it: `services/pdf_export.py` already imports
`_format_amount` from `ui/_amount` and renders money with it. The locale-free
guarantee is scoped to the parse path, which is exactly what INV-1 pins.
`_amount.py` is already the module holding the money-presentation rule, and it
already imports `services.auth` for `CURRENCY_SYMBOLS`.

Naming: `parse_amount_input` is public where its module-mate `_format_amount` is
underscore-prefixed. Deliberate — `_format_amount` is `_`-prefixed and imported
across `ui/` anyway (a historical inconsistency this item does not widen), and
the new function is the seam a test drives directly. The rebuild helper
`_locale_decimal` stays private.

It raises `ValueError` on every rejection. That is not a new convention: it is
`parse_transaction`'s contract (its docstring states `ValueError` for *every*
rejection precisely because `ManualEntryDialog` and `csv_importer` each catch and
render it), so `_on_add`'s existing `except ValueError as exc:
self._error.setText(str(exc))` renders the new failures with no new branch.

### 4.2 Two candidates, then a decision

Both candidates are computed from **one** stripped string, so no difference
between them can come from whitespace:

```python
s = text.strip()
try:
    c_value = Decimal(s)
except InvalidOperation:
    c_value = None
locale_value = _locale_decimal(s)   # None when the locale convention cannot read s
```

`_locale_decimal` is the validate-then-rebuild step:

R1. `value, ok = QLocale().toDouble(s)` — **validation only.** If `ok` is false
   there is no locale candidate. `value` is discarded; it is a float.
R2. Remove every group-separator character from the string (§4.4).
R3. Replace the locale's decimal point with `.`, and its `negativeSign()` /
   `positiveSign()` with `-` / `+` (§4.4).
R4. `Decimal(...)` on the result — the exact value. **On `InvalidOperation`,
   there is no locale candidate** — the same outcome as an R1 rejection.

The rebuild's steps are labelled **R1–R4** and §4.5's resolution steps **1–3**;
they are different sequences and a bare "step 2" would mean two things.

**R4's failure path is not defensive padding; it is the difference between a
refusal and a crash.** `InvalidOperation` is an `ArithmeticError`, *not* a
`ValueError`, so an escape from here sails past `_on_add`'s `except ValueError`
and takes the Qt slot down. That is the same class FIBR-0216 closed when it gave
`parse_transaction` its 64-bit bound ("a class no caller catches, unlike the
`ValueError` every other rejection here raises").

The reachable route is a **typed or pasted** non-ASCII minus, not the app's own
output. Measured 2026-08-04: `QLocale("sv_SE").negativeSign()` is **U+2212**, and
`toDouble` accepts a typed `−1234,56` under `sv_SE`, `de_DE` and `en_US` alike —
so without step 3's sign normalisation the rebuild yields `−1234.56`, which
`Decimal` rejects, and without R4's guard that leaves the slot.

**`_format_amount` itself never emits U+2212** — it renders
`QLocale().toString(float(abs(display)), …)`, so the magnitude carries no sign at
all, and the wrapper adds an ASCII `-` or brackets. Stated explicitly because the
opposite is an easy and wrong inference from `QLocale`'s own formatting, and it
is why INV-2's round-trip cannot be the leg that covers sign normalisation
(INV-9's typed-U+2212 leg is).

`QLocale()` (default-constructed) is used, not `QLocale.system()`, because that
is exactly what `_format_amount` uses. Display and input therefore read the same
locale by construction, and a test that pins one pins both.

### 4.3 The order trap — measured, and the reason R2 precedes R3

R2 and R3 do **not** commute, and getting them backwards reintroduces the
exact 100x error this item exists to prevent. Measured 2026-08-04 under `de_DE`:

| Input | remove-group-then-swap | swap-then-remove-group |
|-------|------------------------|------------------------|
| `1.234,56` | `1234.56` | **`123456`** |
| `-12,34` | `-12.34` | **`-1234`** |
| `1.234.567,89` | `1234567.89` | **`123456789`** |

Swapping first turns the decimal point into a `.`, which the group-removal step
then eats. The wrong order is silent and passes any test that only exercises a
locale whose group separator is not `.`.

### 4.4 Which characters the rebuild normalises

**Removed:** `QLocale().groupSeparator()` **plus** the three space variants
U+0020, U+00A0 and U+202F. Qt is more lenient than its own `groupSeparator()`
suggests: measured 2026-08-04, `en_ZA` (group NBSP) accepts a plain ASCII space
in `1 234,56`, and `fr_FR` (group NNBSP) accepts one too. Removing only
`groupSeparator()` would let Qt validate a string the rebuild then fails on.

Stripping all three space variants unconditionally is safe: no locale uses a
space as a *decimal* separator, and a space is never part of a number's value.

**Replaced:** `decimalPoint()` → `.`, `negativeSign()` → `-`,
`positiveSign()` → `+`. The sign entries are not hypothetical — measured
2026-08-04, `sv_SE`, `nb_NO` and `lt_LT` all return **U+2212** from
`negativeSign()`. (`_format_amount` does *not* render with it — §4.2.
`negativeSign()` also returns a **string, not a character**: `ar_EG` returns the
two-character `"؜-"` and `fa_IR` `"‎−"`, so the replacement must be
string-wise. A char-wise map would leave the mark and produce `--1234.56`.)

**Arabic-Indic digits work, and that is a measurement, not a design intent.**
`ar_EG` returns `zeroDigit()` U+0660 and `negativeSign()` U+061C; `fa_IR` returns
U+06F0 and U+200E. Python's `Decimal` accepts **any** Unicode `Nd` digit, so once
steps 2–3 have removed U+066C and mapped the sign, the rebuild succeeds:
measured 2026-08-04, `ar_EG`'s own `١٬٢٣٤٫٥٦` rebuilds to `Decimal("1234.56")`,
and `fa_IR`'s to `Decimal("-1234.56")`. Those locales therefore round-trip
incidentally. §9 decision 5 records that this is untested and unsupported rather
than promised.

**R4's guard is reachable, and in four of the five measured locales — the
opposite of what a first reading suggests.** Measured 2026-08-04: a typed
**U+2212** minus is accepted by `toDouble` under `en_US`, `de_DE`, `en_ZA` and
`fr_FR`, and in exactly those locales U+2212 is *not* `negativeSign()` (it is
ASCII `-`), so R3's sign replacement is a **no-op** and the rebuild raises
`InvalidOperation`. Only `sv_SE`, where U+2212 *is* the locale's sign, is saved
by the normalisation. So the two halves of the fix cover different locales:
sign normalisation carries `sv_SE`, R4's guard carries the other four, and
neither is redundant. INV-9's `en_US` U+2212 leg is what pins the guard.

### 4.5 The resolution rule

**Step 1 — discard non-finite candidates.** A candidate that is not
`is_finite()` is dropped. Without this, `Decimal("nan")` and
`QLocale().toDouble("nan")` both succeed (measured 2026-08-04) and
`Decimal.__eq__` is **false for two NaNs**, so a typed `nan` would route to the
disagree branch and produce *"reads as NaN or as NaN"* — a nonsense refusal on a
defined input path. Dropping both leaves no candidate and the ordinary "not a
valid number" message.

**Step 2 — resolve.**

| `c_value` | `locale_value` | Result |
|-----------|----------------|--------|
| none | none | `ValueError("amount is not a valid number")` |
| both, `==` | | the C value (deterministic; they are numerically equal) |
| both, `!=` | | `ValueError` — **refuse**, naming both readings |
| exactly one survives | | **step 3**, then that value |

Equality is `Decimal.__eq__` — numeric, so `Decimal("1.10") == Decimal("1.1")`
agrees, which is what we want; `parse_transaction` counts *significant*
fractional digits (`normalize()`), so trailing zeros cannot change the outcome
downstream either.

**Step 3 — the shape guard, and it applies ONLY to the one-surviving-candidate
row.**

*The operand is defined here and computed independently of `_locale_decimal`* —
that helper's intermediate string does not exist on the branch where the **C**
candidate is the survivor, and reading the guard against the rebuilt string
instead changes real inputs by 1000x. The guard's operand is:

> the stripped input, with `negativeSign()` / `positiveSign()` mapped to ASCII
> and the three space variants (U+0020, U+00A0, U+202F) **and `_`** removed —
> and nothing else removed. In particular `.` and `,` are left in place: they are
> what the pattern inspects.

The `_` is not cosmetic. `Decimal` accepts PEP 515 underscores, so INV-9 requires
`1_000` to parse — and measured 2026-08-04, without stripping it `1_234.500`
under `en_ZA` / `fr_FR` / `sv_SE` slips the guard entirely and returns
`Decimal("1234.500")`, where the bare `1234.500` is refused. One underscore would
otherwise disable the whole guard, in the 1000x class the guard exists for.

If that string matches

```
^[+-]?\d+(?:[.,]\d+)*[.,]\d{3}$
```

it is **ambiguous by shape** and is refused. §2.3 is the argument: the losing
convention did not disagree, it *rejected*, so the table above is blind to a
reading it never produced.

**The head may itself be grouped, which is why the pattern is not
`\d+[.,]\d{3}`.** Measured 2026-08-04: `1<NBSP>234,500` under `en_ZA`,
`1<NNBSP>234,500` under `fr_FR` and `1,234.500` under `en_US` each leave one
surviving candidate at `1234.500` — stored as 123 450 minor units where the
grouped reading is 1 234 500. A pattern anchored on a bare-digit head refuses
`1234,500` and waves `1,234.500` through: the same 1000x error wearing a
thousands separator. The pattern above reads as *"digits, then any number of
separator-plus-digit groups, then a final separator followed by exactly three
digits"* — the shape whose last separator could be either a group or a decimal
point.

Three things about this placement, each load-bearing:

- **It runs after the agreement test, not before it, and that is what keeps the
  guard from refusing perfectly good input.** Under `en_US`, `1.500` and `1.250`
  are read identically by both conventions, so they resolve at the `==` row and
  never reach the guard. Measured 2026-08-04 against every input this app stores
  today: with the guard at step 3, **`en_US` loses nothing at all**. Run before
  the table, the same guard refused all of them (§6 records the residual cost
  under the comma-decimal locales, which is real and smaller).
- **The pattern is written against both `.` and `,`, not the locale's own
  separators**, because the hazard is the user importing a **foreign**
  convention — the `en_ZA` user typing `1,500` is using the one grouping their
  locale does not have.
- **The head is unbounded and may contain separators** — §2.3 and the paragraph
  above measure why.

**The guard cannot refuse a string the app itself displayed** (INV-2), and that
is verified rather than assumed: every money value reaching `_format_amount`
arrives either from `to_display_decimal` (`Decimal(amount_minor).scaleb(-exponent)`)
or from a `.quantize(unit)` on the currency's minor unit — `recurring.py`'s
`_monthly_equivalent` is the one division in the money path and it re-quantizes —
so the exponent is `-2` for all six supported currencies and a magnitude always
carries two decimals. Two decimals never match `\d{3}`. §8 alternative 6 records
what moves if a 3-decimal currency is ever added.

**The refusal message renders both readings in the user's own convention**, via
the same `QLocale().toString()` the display side uses, and labels which is which.
Rendering them in the C convention would show a `de_DE` user
*"reads as 1234 or as 1.234"*, in which the second is how **their** locale spells
the first — the message would repeat the ambiguity it exists to resolve. So:

```
amount is ambiguous: "1.234" reads as 1.234 (grouped) or as 1,234 (decimal) — retype it using the format the app displays
```

Deriving the message from the parser's own candidates is what makes it impossible
for the hint to disagree with the parser — the same failure FIBR-0216 fixed in
the placeholder, arriving through a different door.

**Step 3's refusal must compute its two readings explicitly**, because it has
only one candidate to name. For an input matching the pattern, the two readings
are: **grouped** = every separator removed, and **decimal** = the *final*
separator read as a decimal point and the earlier ones removed.

Both are rendered with **`QLocale().toString(float(value), "f", n)`**, `n` being
that reading's **significant** fractional-digit count
(`-value.normalize().as_tuple().exponent`, floored at 0) — the same
significant-digit convention `parse_transaction` uses. Measured 2026-08-04 under
`en_ZA`: the decimal reading of `1,500` is `Decimal("1.500")`, which renders
`1,500` on the raw exponent (indistinguishable from the input) and `1,5` on the
significant count. The `float()` cast mirrors `_format_amount`'s, `toString`
having no `Decimal` overload. It is *not* the bare `toString(double)`
overload, which is `'g'` with six significant digits and turns
`1234500` into `1,2345e+06` (measured 2026-08-04 under `en_ZA`). Scientific
notation in a money refusal is worse than no message. Pinning the overload also
matches `_format_amount`, which already passes `"f"`.

One of the two readings will render back to the string the user typed — that is
unavoidable, and it is why the labels `(grouped)` / `(decimal)` are part of the
message rather than decoration.

The message is plain English, untranslated, matching every existing
`parse_transaction` message (`"amount is not a valid number"`,
`"amount must be non-zero"`) which `_on_add` already renders verbatim. §9
decision 3 records that translating parser messages is a separate, app-wide item.

### 4.6 The call site

`ManualEntryDialog._on_add`'s existing `add_transaction` call wraps its amount
argument; no statement is added:

```python
self._transactions.add_transaction(
    account_id,
    occurred_on,
    parse_amount_input(self._amount.text()),
    self._description.text(),
)
```

`add_transaction` already takes `str | Decimal` (verified:
`services/transactions.py`, `raw_amount: str | Decimal`) and passes a `Decimal`
straight through untouched, so no service-layer change is needed. Every existing
rejection — zero, non-finite, over-precise, past the 64-bit bound — still happens
in `parse_transaction`, unchanged and single-homed.

The existing `except VaultLockedError` stays correct: `parse_amount_input`
touches no vault, and `add_transaction` still reads the currency exponent before
parsing.

## 5. Invariants

- **INV-1** — `parse_transaction` remains C-locale only, and no importer's result
  depends on the desktop locale.
  *Test:* `tests/features/amount_input/test_amount_input.py` — run a CSV, an OFX
  and a `standard_bank` PDF fixture through their importers twice, once under
  `QLocale.setDefault(QLocale.c())` and once under `de_DE`, and assert the
  resulting `amount_minor` lists are identical. Also assert
  `parse_transaction("2026-07-01", "-12,34", "x", 2)` raises `ValueError` under
  `de_DE` — the C parser must stay C. The importer leg needs a **discriminating
  fixture row**: an ordinary `-12.34` yields the same result under both locales
  whether or not the layer moved, so at least one row must carry a grouped
  amount (`1,234.56`) whose two readings differ. Assert that row's
  `amount_minor` explicitly, not just list equality.
  *Breaks when:* someone "completes" this fix by moving the locale layer down
  into `parse_transaction`, so a German user's bank statement imports to
  different numbers than the same file on an English machine.

- **INV-2** — Every string `_format_amount`'s magnitude can produce is accepted,
  under each of the measured locales, and returns the magnitude exactly.
  *Precondition, and it is load-bearing:* display amounts reach `_format_amount`
  either via `to_display_decimal` (`Decimal(amount_minor).scaleb(-exponent)`) or
  via a `.quantize()` on the currency's minor unit — exponent `-2` for all six
  supported currencies — so a magnitude always carries two decimals. That is what
  keeps §4.5 step 3 from refusing the app's own output.
  *Test:* for each locale in `{en_US, en_ZA, de_DE, fr_FR, sv_SE}` and each of
  `Decimal("12.34")`, `Decimal("1234.56")`, `Decimal("1234567.89")`,
  `Decimal("0.05")`, `Decimal("-1234.56")`: pin the locale, call
  **`_format_amount(v, "ZAR")`** (not a re-implementation of its `toString`
  line), take the **magnitude** — strip a leading `-` or the `( )` wrapper, then
  the `"R "` prefix — feed it to `parse_amount_input`, and assert the result
  equals `abs(v)`. Anchoring on the shipping function is the point: a leg that
  re-renders the magnitude itself stays green when `_format_amount` changes and
  the real round-trip breaks.
  Two things this leg does **not** cover, so that no reader infers them:
  `_format_amount` takes `abs(display)`, so **no sign character ever reaches the
  parser here** — sign normalisation is INV-9's leg, not this one; and
  `forecast.py` prepends a `"+"` to the formatted string for a positive
  projection, a third wrapper this leg does not exercise.
  *Breaks when:* the separator set misses a locale's group character —
  `fr_FR`'s U+202F is the one a two-locale test would not catch.

- **INV-3** — Every C form that the locale convention does **not** read as a
  different number, **and whose shape §4.5 step 3 does not flag**, is accepted
  under every locale, unchanged.
  *Test:* for each of the five locales, `parse_amount_input("-12.34") ==
  Decimal("-12.34")` and `parse_amount_input("1234.56") == Decimal("1234.56")`.
  *Breaks when:* the implementation *replaces* C parsing with locale parsing
  instead of adding to it — which would break every user who types `12.34`
  today, and falsify the `-12.34` placeholder FIBR-0216 pinned. This is the
  invariant that keeps that placeholder honest without touching it.
  *Note the qualifier, which is not hedging:* under `de_DE`, `1.234` is a C form
  the locale reads as `1234`, so INV-4 refuses it. Stated unqualified, this
  invariant would authorise "prefer C whenever it parses" — deleting INV-4's
  refusal rule, with two invariants contradicting each other and no tie-break for
  the implementer. **Both qualifiers are load-bearing, and the second is the one an
  earlier draft omitted.** The first covers `de_DE` `1.234`. The second covers
  the comma-decimal locales, where `1.500` is a C form the locale does not read
  differently — it *rejects* it — so the first qualifier alone would mandate
  accepting exactly what INV-8 leg (b) mandates refusing. An implementer
  resolving that collision in INV-3's favour exempts every C-parseable string
  from the guard and re-opens `en_ZA` `1,500` → 150 minor units. §6 records the
  refusal as a real, accepted regression; this invariant must not contradict it.

- **INV-4** — When both conventions parse the input and disagree, it is
  **refused**; no value reaches the vault, and the message names both readings.
  *Test:* under `de_DE`, `parse_amount_input("1.234")` raises `ValueError`; same
  for `"12.345"` and `"-1.234"`. All three reach this rule and not INV-8's
  guard — verified 2026-08-04: both conventions parse them and disagree
  (`1.234` → C `1.234` vs locale `1234`), so §4.5's `!=` row fires first. That
  ordering is what makes this leg non-vacuous, and it is why the guard is at
  step 3 rather than ahead of the table.
  Assert the **decimal** rendering specifically (`"1,234"` for `1.234`,
  `"12,345"` for `12.345`) plus the presence of both `(grouped)` and `(decimal)`
  labels — **not** the raw input echo, which the message quotes verbatim, so a
  naive `"1.234" in msg` is satisfied by the echo alone and half the assertion
  cannot fail. Do **not** ask for an input whose two renderings both differ from
  the echo: no such input exists on this branch. The disagree row fires only when
  the locale reads the string as a valid group, so re-rendering that reading under
  the same locale always reproduces the input (`de_DE` `12.345` → grouped
  `12.345`). The decimal rendering is the half that always differs.
  Plus **two** `qtbot` legs, and the positive one is the load-bearing half:
  (a) under `de_DE`, type `1.234`, click Add, assert the error label is non-empty
  and the transaction count did not grow; (b) under `de_DE`, type `-12,34`, click
  Add, and assert **one transaction was stored with `amount_minor == -1234`**.
  Leg (a) alone passes against an implementation that never wires
  `parse_amount_input` into `_on_add` at all — unwired, `1.234` reaches
  `parse_transaction`, parses in C, and is refused as over-precise, producing
  exactly the asserted outcome. Leg (b) is the only leg in this spec that fails
  when §4.6 is omitted.
  *Breaks when:* the implementation prefers one candidate — a silent 1000x error
  on a money field, which is the whole hazard this spec exists for.

- **INV-5** — Group separators are removed **before** the decimal point is
  swapped.
  *Test:* under `de_DE`, `parse_amount_input("1.234,56") == Decimal("1234.56")`,
  `parse_amount_input("-12,34") == Decimal("-12.34")`, and
  `parse_amount_input("1.234.567,89") == Decimal("1234567.89")`.
  *Breaks when:* the two steps are swapped — measured §4.3, each of those three
  becomes 100x too large, silently. A test written only against `en_ZA` or
  `fr_FR` passes either order, which is why all three legs pin `de_DE`.

- **INV-6** — The returned value is an exact `Decimal` rebuilt from the input
  string, never Qt's `toDouble` float.
  *Test:* under `en_US`, `parse_amount_input("92233720368547758.07") ==
  Decimal("92233720368547758.07")` — the value `test_INV4b_accepts_the_largest_storable_amount`
  already uses as the 64-bit bound. Round-tripped through a binary float it
  becomes `9.223372036854776E+16` (measured 2026-08-04:
  `Decimal(str(float("92233720368547758.07")))`), so the leg is red against any
  implementation that returns `Decimal(str(value))`.
  *Breaks when:* someone uses the float `toDouble` already computed, because it
  is right there and looks free.

- **INV-7** — The §2.1/§2.2 matrix is asserted by a test, not only recorded in
  this document.
  *Test:* a table-driven leg that pins each locale and asserts, per row, whether
  `QLocale().toDouble` accepts the string and what `parse_amount_input` returns
  or raises.
  Name the columns it asserts: for each row, whether `toDouble` accepts, and
  what `parse_amount_input` returns or raises. The `naive` and `C` columns of §2.1/§2.2 are
  evidence for the design, not behaviour to assert, and §2.2's summary row is
  prose — none of them is part of this leg.
  *Breaks when:* a PySide6 upgrade changes `QLocale`'s group-placement
  **strictness**. That strictness is load-bearing — §2.1 depends on `de_DE`
  *rejecting* `-12.34` rather than reading it as `-1234` — and without this leg
  the change would land as a silent behaviour change in money parsing rather
  than a red suite. (Distinct from §4.4's *leniency*, which is Qt accepting an
  ASCII space where the locale groups with NBSP; the two are opposite
  properties and this invariant pins the first.)

- **INV-8** — When exactly one convention yields a candidate, an input matching
  `^[+-]?\d+(?:[.,]\d+)*[.,]\d{3}$` — matched against the operand §4.5 step 3
  defines — is refused rather than resolved.
  *Test:* four groups of legs, and the first three each close a branch that the
  others leave green.
  (a) **Locale-candidate branch** — under `en_ZA`, `de_DE`, `fr_FR`, assert
  `ValueError` for `"1,500"`, `"12,500"`, `"2,000"`.
  (b) **C-candidate branch** — under `en_ZA`, `fr_FR`, `sv_SE`, assert
  `ValueError` for `"1.500"`, `"1.250"`, `"0.100"`, `"1234.500"`. Without this
  group every input in (a) is comma-separated, so under those locales the
  *locale* convention is always the survivor and an implementation that applies
  the guard only when `_locale_decimal` succeeded passes the whole invariant
  green while accepting `en_ZA` `1.500`. This is also the group that pins §6's
  measured regression set.
  (c) **Grouped-head** — assert `ValueError` for `"1234,500"`, `"1<NBSP>234,500"`
  under `en_ZA`, `"1<NNBSP>234,500"` under `fr_FR`, and `"1,234.500"` under
  `en_US`. Note that `"1234,500"` under **`en_US`** is refused as *"not a valid
  number"* (neither convention parses it), so that cell passes with the guard
  removed entirely — assert the refusal **message** is the ambiguity one, not
  merely that `ValueError` was raised.
  (d) **Bounds from the other side** — assert that **no** `_format_amount`
  magnitude from INV-2's value list matches the pattern (the guard cannot refuse
  the app's own output); that under `en_US` `parse_amount_input("1.500") ==
  Decimal("1.500")` (the guard must not fire where both conventions agree); and
  that the refusal message for `"1,500"` under `en_ZA` names both readings
  (`1<NBSP>500` grouped — `en_ZA` groups with NBSP, so assert the U+00A0 form —
  and `1,5` decimal, which requires §4.5's significant-digit `n`) — the only leg covering §4.5's
  compute-the-readings requirement for this branch.
  *Breaks when:* (a) the guard is dropped as redundant because §4.5's table
  "already handles ambiguity" — measured 2026-08-04 without it, `en_ZA` `1,500`
  → `Decimal("1.500")` → stored as **150 minor units** where the user meant
  150 000; (b) the head is bounded to three digits — then `1234,500` under
  `en_ZA` yields `1234.500`, stored as 123 450 where the user meant 1 234 500,
  the same 1000x error one digit along; (b2) the head is written `\d+` without
  allowing separators inside it — then `1,234.500` under `en_US` and
  `1<NBSP>234,500` under `en_ZA` yield `1234.500`, stored as 123 450 where the
  grouped reading is 1 234 500; (d) the guard is run against `_locale_decimal`'s
  rebuilt string instead of the operand §4.5 step 3 defines — then `en_US`
  `1,500` rebuilds to `1500`, misses the pattern, and is accepted as one thousand
  five hundred where the typist may have meant one and a half; (c) the guard is
  moved ahead of the candidate table — then it refuses `1.500` and `1.250` under `en_US`, which the
  shipping app accepts today.

- **INV-9** — `parse_amount_input` raises **only** `ValueError`, for every input.
  *Test:* two tables, and conflating them is why the first draft of this clause
  would have gone red against a correct build.
  **Must raise `ValueError`:** `""`, `"-"`, `"nan"`, `"inf"`, `"."`, `","`.
  **Must return a value:** `"1_000"` → `Decimal("1000")` (PEP 515 underscores are
  valid `Decimal` input) and a 400-char digit string → its exact `Decimal`. Both
  are hostile-looking and both legitimately parse; asserting `pytest.raises`
  across one undifferentiated table fails a correct implementation.
  **The two sign legs, which cover different locales and different mechanisms:**
  (a) under `sv_SE`, `parse_amount_input("−1234,56") == Decimal("-1234.56")` —
  U+2212 *is* that locale's `negativeSign()`, so this is what §4.4's sign
  normalisation buys, and it is a **positive** assertion, not a raise;
  (b) under `en_US`, `parse_amount_input("−1234.56")` raises `ValueError` — U+2212
  is *not* that locale's sign, so the replacement is a no-op, `toDouble` still
  accepts the string (measured), and the rebuild raises `InvalidOperation`. Leg
  (b) is the only leg in this spec that fails against an unguarded R4.
  Do **not** source either leg from `_format_amount`, whose `abs()` means its
  output never carries a sign at all (§4.2).
  *Breaks when:* R4's rebuild is left unguarded (leg b), or the sign is not
  normalised (leg a). `Decimal` raises `InvalidOperation`, an `ArithmeticError`
  and **not** a `ValueError`, so an unguarded rebuild escapes `_on_add`'s handler
  and crashes the slot rather than showing an error.
  *Scope, stated so the leg is not read as covering more than it does:* this
  invariant is about `parse_amount_input`. `1e999999` is deliberately **not** in
  the table — measured 2026-08-04, it parses cleanly here and then raises
  `decimal.Overflow` inside `parse_transaction`'s `to_minor`, which is a
  **pre-existing** uncaught path from this dialog, independent of this item and
  filed separately (§12).

## 6. Failure modes

- **A `de_DE` user who means one thousand two hundred thirty-four types `1.234`
  and is refused.** Deliberate (§8 alternative 2). They retype `1.234,00` or
  `1234`. The cost is one retype, in the one input shape where the alternative
  is a 1000x error. Note the C reading of that same string (`1.234`, three
  decimals) is over-precise for every currency this app supports — all six in
  `CURRENCY_EXPONENTS` are exponent 2 (verified: `services/auth.py`) — so it
  would be refused by `parse_transaction` anyway; refusing here loses the user
  nothing they could have stored.
- **A grouped whole amount is refused — and under a comma-decimal locale this is
  a REAL REGRESSION, stated here because the first draft of this section claimed
  otherwise.** Measured 2026-08-04, the exact set: under `en_ZA`, `de_DE`,
  `fr_FR` and `sv_SE`, the inputs `1.500`, `1.250`, `2.000`, `0.100`, `12.500`
  and `1234.500` are **accepted and stored today** (`Decimal("1.500").normalize()`
  has one significant fractional digit, inside exponent 2) and are **refused
  after** this item. Under `en_US` nothing is lost — those inputs resolve at the
  `==` row before the guard is reached.
  The trade is deliberate: under a comma-decimal locale a `.`-separated
  three-digit tail is already foreign-convention input, and the same shape is
  how `1,500` → `1.5` (a 1000x error) arrives. The user pays one retype, and the
  refusal message names both readings. `1,50`, `1.50` and `1500` all work.
- **Under `en_US`, an ordinary grouped whole amount is refused too:** `1,500`,
  `1,234,500`, `1,500,000`. Nothing is *lost* — none of them parses today — but
  this is the refusal a US or ZA user meets most often, so it belongs in the
  failure modes rather than only in INV-8's leg list. `1500` and `1500.00` work.
- **A hazard this design deliberately RETAINS, and it is the mirror of §2.3's.**
  Under a `.`-decimal locale (`en_US`) both conventions read `1.500` alike, so it
  resolves at §4.5's `==` row and the guard never runs: a European pasting
  `1.500` for one thousand five hundred gets `1.5`. It is not a regression — the
  shipping app does the same today — and refusing it would cost every `en_US`
  user the `.`-tail forms they currently rely on (§8 alternative 7). Recorded
  rather than fixed, so that no reader believes the guard is symmetric.
- **A pasted `R 1 234,56` (with the currency symbol), or a bracketed negative
  `(R 12,34)`, is refused.** Unchanged from today. §9 decisions 2 and 6.
- **A locale with non-ASCII digits (`ar_EG`, `fa_IR`) round-trips incidentally.**
  Measured §4.4 — `Decimal` accepts any Unicode `Nd` digit, so the rebuild
  succeeds. Not a failure mode; recorded here because §9 decision 5 declines to
  *promise* it, and a reader who assumes it is refused would design a
  transliteration step nothing needs.
- **`nan` / `inf` typed literally.** Both parse on both sides; §4.5 step 1 drops
  non-finite candidates, so the message is the ordinary "not a valid number"
  rather than an ambiguity report naming NaN twice.
- **A locale outside the measured five with a further convention.** The design
  reads `groupSeparator()`, `decimalPoint()` and the signs from the locale rather
  than hardcoding them, but only five are asserted and Qt ships hundreds. §11
  carries this as an uncovered row.
- **An auto-lock while the dialog is open.** Unchanged: `parse_amount_input`
  touches no vault, and `_on_add`'s existing `except VaultLockedError` still
  guards the `add_transaction` call.

## 8. Alternatives considered (and rejected)

1. **Strip separators and swap the point (the naive fix).** Rejected on
   measurement, §2.1: under `de_DE` a typed `-12.34` becomes `-1234`, accepted
   silently. Trading a refusal for a 100x error is a regression however good the
   intent. This is the alternative the ROADMAP bullet was split out to prevent.
2. **Resolve ambiguity by dropping the candidate `parse_transaction` would
   reject anyway.** Tempting and *nearly* free: §2.2's disagreeing inputs all
   have a C reading with three decimals, over-precise for every supported
   currency, so dropping it would leave exactly one survivor and accept `1.234`
   as `1234` — what a German user means. Rejected because it makes the same
   typed string mean two different numbers depending on the vault's currency, a
   rule no user can predict; and because a user typing a C-style `1.234` would
   get `1234` — a silent 1000x error where today they get a refusal. That is
   alternative 1's failure mode wearing better clothes. The premise would move
   if a 3-decimal currency were ever added to `CURRENCY_EXPONENTS`; it would
   move in the direction of *more* ambiguity, not less.
3. **A `QDoubleValidator` on the field.** It would block the keystroke rather
   than explain the refusal, gives no route to report *why* an ambiguous input
   was rejected, and validates against the locale only — so it would reject the
   C form that INV-3 requires, and reject the `-12.34` placeholder under `de_DE`.
4. **Parse with `babel`.** A new runtime dependency, on a bundle that ships
   PySide6 already, for a rule that is four lines against an API already
   imported. `dependencies.md` § 1 (justify every dependency).
5. **Make the placeholder locale-aware instead.** Does not fix the bug — the
   user still cannot type back what the app displayed — and re-opens a decision
   FIBR-0216 closed. §9 decision 4.
6. **Let the two-candidate table carry ambiguity alone, with no shape guard.**
   Wrong by measurement: the table only fires when *both* conventions produce a
   value, so `en_ZA` `1,500` — where the C convention simply rejects — takes the
   single surviving candidate and stores `1.5`. Rejected because it reintroduces
   exactly the silent-1000x class this item was split out of FIBR-0216 to
   prevent, on the app's default locale.
7. **Run the shape guard before the candidate table rather than after.** Simpler
   to state, and measurably worse: it refuses `1.500` and `1.250` under `en_US`,
   which the shipping app accepts and stores today, for inputs both conventions
   read identically — a regression bought for very little safety. The reasoning
   is **not** "an agreed reading is by definition unambiguous"; §2.3 rejects
   exactly that principle. It is that an agreed reading is the **locale-native**
   one, and refusing every `.`-tail form under `en_US` costs more than the
   residual foreign-paste risk, which §6 now records as deliberately retained.
   §4.5 step 3 is the placement that keeps `en_US` whole.
   *Premise that could move (both 6 and 7):* the guard's safety rests on display
   magnitudes always carrying two decimals. Add a 3-decimal currency to
   `CURRENCY_EXPONENTS` and a displayed `1,234` would match the pattern, so the
   app could refuse its own output — at which point the guard must become
   exponent-aware, and INV-2's leg is what would go red first.

## 9. Out of scope

1. **Locale-aware amount input anywhere else.** There is nowhere else: §3
   decision 3 verified `ManualEntryDialog` is the only typed-amount field.
2. **Accepting a pasted currency symbol** (`R 1 234,56`). Refused today, refused
   after. A separate, larger question (which symbols, which positions, what
   about a non-base currency), and refusing is safe.
3. **Translating parser messages — and this is a recorded deviation, not an
   oversight.** Every `parse_transaction` message is untranslated English today
   and `_on_add` renders it verbatim; this item adds one more in the same style
   rather than opening an app-wide i18n item for the parser layer.
   The deviation: that precedent is a **services**-layer one, while this message
   is authored in `ui/_amount.py`, where `docs/standards/coding.md` § 5.2
   requires every user-facing string to go through `tr()` or
   `QCoreApplication.translate("Context", …)` outside a `QObject`. Named
   explicitly so an implementer meets one rule knowingly rather than discovering
   the other mid-build. Scoped to this one message; the standard is not amended.
4. **The manual-entry placeholder stays exactly as FIBR-0216 left it** — the
   non-translatable literal `-12.34`. It needs no change: INV-3 makes that
   string valid under every locale, so the hint and the parser still cannot
   disagree. This is stated rather than silently skipped because a reader who
   knows FIBR-0216 will ask.
5. **Non-ASCII digit entry** (`ar_EG`, `fa_IR` and the other Arabic-Indic
   locales). Measured §4.4, those inputs happen to round-trip correctly — but
   *happens to work* is not a contract: no leg pins it, the guard's `\d` is
   Unicode-wide in Python `re` while the C convention's acceptance of such digits
   is incidental, and the interaction of the two is unmeasured. Declared
   unsupported rather than promised.
   *Premise that will move:* `docs/design.md` lists **Arabic** in the FIBR-0017
   translation catalog. When that ships, this decision is re-opened — an RTL
   locale with a translated UI and unsupported numeric entry is a worse state
   than either end.
6. **The bracketed negative form** `(R 12,34)`. `_format_amount` can render it
   (`NegativeStyle.BRACKETS`), and it is refused on input before and after this
   item. Named here because §1 would otherwise read as promising it.
7. **`_format_amount` itself.** Display is already correct.

## 10. Resource cost

One regex match and three parse attempts per Add click (`Decimal(s)`,
`toDouble(s)`, `Decimal(rebuilt)`), on a user-initiated
action — unmeasurable. No new dependency. No new file in `src/`: the two
functions and their comments (§4.3's order trap, §4.5 step 3's reason for
existing) join `ui/_amount.py`, taking it from **56 lines** (`wc -l`,
2026-08-04) to roughly **120**. One new test directory.

Eighteen rows, **five** with a bolded `nothing` — this spec's error budget. Two

never exercised, and no leg discriminates a derived ambiguity message from a
hardcoded one. The other three are an out-of-scope behaviour, the open-ended
locale set (which no finite suite closes), and a deliberately unpinned

The budget fell from seven `nothing`s to five as the sign-normalisation and
rebuild-guard rows gained real catchers — the direction that matters, since both
