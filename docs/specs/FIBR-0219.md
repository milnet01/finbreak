# FIBR-0219 — Accept a locale-formatted amount without ever guessing an ambiguous one

**Status:** 📋 **DRAFT** — awaiting the `/cold-eyes` gate (§13).
**Kind:** fix.
**Source:** ROADMAP FIBR-0219 (code-quality-review-2026-08-03), split out of
FIBR-0216 on 2026-08-03 because the obvious fix measured as a silent 100x error.
**Pairs with:** FIBR-0216 (made the manual-entry placeholder non-translatable so
the hint could not disagree with the parser; §9 decision 4 explains why this item
leaves that placeholder alone), FIBR-0153 (`_format_amount`, the display side
this input side must round-trip), FIBR-0105 (the negative-style wrapper, which is
display-only and out of scope).

**Layman:** If your computer writes numbers the European way — `1.234,56` — you
currently cannot type the number part of an amount back the way finbreak just
showed it to you. This makes the app accept your way of writing numbers *and* the
plain `12.34` way. And when a typed number could mean two different things, it
asks you instead of guessing, because guessing wrong on a money field is off by a
factor of 100 or 1000.

## 1. Goal

The manual-entry Amount field accepts the **numeric part** of the amount the app
itself just displayed, under the user's own locale, **without** ever silently
resolving an input that two conventions read as two different numbers.

*Numeric part*, precisely: `_format_amount` renders `«symbol»␣«magnitude»` and
wraps a negative in `-` or `( )`. Only the **magnitude** is in scope — the
currency symbol and the bracket form stay refused (§9 decisions 2 and 6). A goal
stated as "accepts what was displayed" would authorise symbol-stripping that no
invariant here requires.

Three properties, in priority order, and the second is the one this item exists
for:

1. Every unambiguous input is accepted — in the locale's convention *and* in the
   C convention, under every locale.
2. Every **ambiguous** input is refused, visibly, naming both readings. A
   refusal costs a retype; a wrong guess costs a factor of 100 or 1000 on
   somebody's money.
3. Nothing about how a **bank file** imports changes. Import must not depend on
   the desktop locale.

## 2. Problem

Display goes through `_format_amount` (`ui/_amount.py`), whose magnitude is
`QLocale().toString(float(abs(display)), "f", decimals)` — grouped, with
locale-correct separators. Input goes through `ManualEntryDialog._on_add`
(`ui/manual_entry.py`), which passes `self._amount.text()` straight to
`TransactionService.add_transaction` → `parse_transaction`
(`services/transactions.py`), which does `Decimal(str(raw_amount).strip())` — the
C convention and nothing else.

So under a locale that writes `1.234,56`, the app displays a number the user
cannot type back. It is refused, which is safe but wrong.

### 2.1 The measured matrix, and why the obvious fix is a regression

Re-measured 2026-08-04 on the pinned PySide6, `QT_QPA_PLATFORM=offscreen`
(script: `scratchpad/measure_locale.py`; the same result the 2026-08-03 bullet
records). `qt` is `QLocale(name).toDouble(s)`; `C` is `Decimal(s)`; `naive` is
the obvious fix — *strip the group separator, swap the decimal point for a dot*:

| Locale | decimal point | group separator |
|--------|---------------|-----------------|
| `en_US` | `.` U+002E | `,` U+002C |
| `en_ZA` | `,` U+002C | NBSP U+00A0 |
| `de_DE` | `,` U+002C | `.` U+002E |
| `fr_FR` | `,` U+002C | NNBSP U+202F |

Four conventions, not two — and `en_ZA` is the base-currency locale of this
app's primary audience, so the gap bites the default user, not only a German
one. The rows that matter:

| Locale | Input | `qt` | `C` | `naive` |
|--------|-------|------|-----|---------|
| `de_DE` | `-12.34` | **rejected** | `-12.34` | **`-1234`** ← 100x, silent |
| `de_DE` | `-1234.56` | rejected | `-1234.56` | **`-123456`** ← 100x, silent |
| `de_DE` | `-12,34` | `-12.34` | rejected | `-12.34` |
| `de_DE` | `-1.234,56` | `-1234.56` | rejected | `-1234.56` |
| `en_ZA` | `-12,34` | `-12.34` | rejected | `-12.34` |
| `fr_FR` | `-1<NNBSP>234,56` | `-1234.56` | rejected | `-1234.56` |
| `en_US` | `-1,234.56` | `-1234.56` | rejected | `-1234.56` |

The `naive` column is the regression the ROADMAP bullet names: under `de_DE` a
typed `-12.34` becomes `-1234`, accepted, stored, and never flagged. Today that
same input is merely refused.

**The mechanism behind the fix is in the first column.** `QLocale::toDouble`
does not merely re-read separators — it **validates group placement**, so
`-12.34` under `de_DE` is *rejected* rather than read as `-1234`. That is the
property the naive string-munge threw away: it transformed without validating.

### 2.2 Where the genuine ambiguity is, measured

Both conventions succeeding *and disagreeing* is a small, precisely bounded set.
Same script, second run:

| Locale | Input | `qt` | `C` | |
|--------|-------|------|-----|---|
| `de_DE` | `1.234` | `1234` | `1.234` | **disagree** |
| `de_DE` | `12.345` | `12345` | `12.345` | **disagree** |
| `de_DE` | `-1.234` | `-1234` | `-1.234` | **disagree** |
| `de_DE` | `1.23` | rejected | `1.23` | one only |
| `de_DE` | `1.2345` | rejected | `1.2345` | one only |
| `en_US` | `1.234` | `1.234` | `1.234` | agree |
| `en_ZA`, `fr_FR` | *(every row)* | — | — | **no disagreement** |

Parser disagreement arises only where the locale's group separator is `.` — the
`de_DE` family — and only for a group of **exactly three** digits, because Qt
rejects a wrong-sized group (`1.23`, `1.2345`).

### 2.3 Parser disagreement is NOT the same thing as reading ambiguity

The §2.2 result is about the two *parsers* disagreeing. It is not the hazard, and
building the rule out of it alone ships the bug this item exists to prevent.

The dangerous class is a string that **one** parser accepts and the other merely
**rejects**, where the rejected convention would have read it as a *different
number*. Measured 2026-08-04, and this is the app's own primary locale:

| Locale | Input | `qt` | `C` | Naive "one candidate → take it" |
|--------|-------|------|-----|--------------------------------|
| `en_ZA` | `1,500` | `1.500` | rejected | **`1.5`** → stored as 150 minor units |
| `en_ZA` | `12,500` | `12.500` | rejected | **`12.5`** |
| `de_DE` | `2,000` | `2.000` | rejected | **`2.0`** |
| `fr_FR` | `1,250` | `1.250` | rejected | **`1.25`** |

A user typing `1,500` for one thousand five hundred — the US/UK grouping, and
the commonest thing to paste — gets **R 1,50**. `parse_transaction` does not save
us: `Decimal("1.500").normalize()` has one significant fractional digit, inside
exponent 2, so it is accepted and stored. **1000x, silent, and a regression** —
today that string is refused.

So ambiguity is a property of the **string's shape**, not of whether both parsers
happened to succeed. §4.5 step 0 is built on the shape; the two-candidate table
is what runs after it.

The ambiguous shape is exactly `<1–3 digits><separator><exactly 3 digits>`: it
reads as a thousands group in one convention and a three-place fraction in the
other, and both readings are structurally valid. A leading run of four or more
digits cannot be a first group, and a run of one, two, four or more digits after
the separator cannot be a group — which is why the shape is this narrow.

## 3. Scope decisions

1. **`parse_transaction` does not change.** It is reused per-row by
   `csv_importer`, `ofx_importer` and `standard_bank`
   (verified: `grep -rn "parse_transaction" src/` — four call sites, three of
   them importers). Teaching it the desktop locale would make a bank statement
   import to different numbers on two machines — strictly worse than the bug
   being fixed. Bank files are machine data and keep their own conventions.
2. **The locale layer goes at the human-input seam only**, beside the display
   function it mirrors: a new `parse_amount_input` in `ui/_amount.py`.
3. **One call site.** `ManualEntryDialog` is the only typed-amount field in the
   app (verified 2026-08-04 with a **recursive** enumeration of every
   `QLineEdit` / `.text()` under `src/finbreak/ui/`, not a `ui/*.py` glob: the
   only money-bearing one is inside `ManualEntryDialog._on_add`. The other
   free-text fields are `start_over` (a confirm word), `set_hint` (a password
   hint) and `import_wizard` (a custom date format); `transfers.py`, `home.py`
   et al. import `_format_amount` for display only).
4. **Refuse ambiguity; never resolve it.** §8 alternative 2 records the
   resolution rule that was rejected and why.
5. **Money stays exact `Decimal`.** Qt's `toDouble` returns a float and is used
   **only as a validator**; the value is rebuilt from the input string.

## 4. Design

### 4.1 `parse_amount_input(text: str) -> Decimal`

New function in `ui/_amount.py`, beside `_format_amount`. The placement is a
**layering** call, not a reuse one: the rule is locale presentation, its only
caller is a widget, and `services/` must stay locale-free or INV-1 fails. Putting
it beside `parse_transaction` in `services/` would drop `QLocale` into the layer
whose whole guarantee here is that it does not know about locales. `_amount.py`
is already the module holding the ui-side locale rule, and it already imports
`services.auth` — the one-way `ui → services` edge that module's own comment
names.

Naming: `parse_amount_input` is public where its module-mate `_format_amount` is
underscore-prefixed. Deliberate — `_format_amount` is `_`-prefixed and imported
across `ui/` anyway (a historical inconsistency this item does not widen), and
the new function is the seam a test drives directly. The rebuild helper
`_locale_decimal` stays private.

It raises `ValueError` on every rejection. That is not a new convention: it is
`parse_transaction`'s contract (its docstring states `ValueError` for *every*
rejection precisely because `ManualEntryDialog` and `csv_importer` each catch and
render it), so `_on_add`'s existing `except ValueError as exc:
self._error.setText(str(exc))` renders the new failures with no new branch.

### 4.2 Two candidates, then a decision

Both candidates are computed from **one** stripped string, so no difference
between them can come from whitespace:

```python
s = text.strip()
try:
    c_value = Decimal(s)
except InvalidOperation:
    c_value = None
locale_value = _locale_decimal(s)   # None when the locale convention cannot read s
```

`_locale_decimal` is the validate-then-rebuild step:

1. `value, ok = QLocale().toDouble(s)` — **validation only.** If `ok` is false
   there is no locale candidate. `value` is discarded; it is a float.
2. Remove every group-separator character from the string (§4.4).
3. Replace the locale's decimal point with `.`, and its `negativeSign()` /
   `positiveSign()` with `-` / `+` (§4.4).
4. `Decimal(...)` on the result — the exact value. **On `InvalidOperation`,
   there is no locale candidate** — the same outcome as a step-1 rejection.

**Step 4's failure path is not defensive padding; it is the difference between a
refusal and a crash.** `InvalidOperation` is an `ArithmeticError`, *not* a
`ValueError`, so an escape from here sails past `_on_add`'s `except ValueError`
and takes the Qt slot down. That is the same class FIBR-0216 closed when it gave
`parse_transaction` its 64-bit bound ("a class no caller catches, unlike the
`ValueError` every other rejection here raises").

It is reachable, measured 2026-08-04: under `sv_SE`, `_format_amount`'s own
magnitude for `-1234.56` is `−1<NBSP>234,56` with a **U+2212** minus.
`toDouble` accepts it; the rebuild without step 3's sign normalisation yields
`−1234.56`, which `Decimal` rejects. Without both halves of this fix, a Swedish
user crashes the dialog by typing back the string the app just displayed.

`QLocale()` (default-constructed) is used, not `QLocale.system()`, because that
is exactly what `_format_amount` uses. Display and input therefore read the same
locale by construction, and a test that pins one pins both.

### 4.3 The order trap — measured, and the reason step 2 precedes step 3

Steps 2 and 3 do **not** commute, and getting them backwards reintroduces the
exact 100x error this item exists to prevent. Measured 2026-08-04 under `de_DE`:

| Input | remove-group-then-swap | swap-then-remove-group |
|-------|------------------------|------------------------|
| `1.234,56` | `1234.56` | **`123456`** |
| `-12,34` | `-12.34` | **`-1234`** |
| `1.234.567,89` | `1234567.89` | **`123456789`** |

Swapping first turns the decimal point into a `.`, which the group-removal step
then eats. The wrong order is silent and passes any test that only exercises a
locale whose group separator is not `.`.

### 4.4 Which characters the rebuild normalises

**Removed:** `QLocale().groupSeparator()` **plus** the three space variants
U+0020, U+00A0 and U+202F. Qt is more lenient than its own `groupSeparator()`
suggests: measured 2026-08-04, `en_ZA` (group NBSP) accepts a plain ASCII space
in `1 234,56`, and `fr_FR` (group NNBSP) accepts one too. Removing only
`groupSeparator()` would let Qt validate a string the rebuild then fails on.

Stripping all three space variants unconditionally is safe: no locale uses a
space as a *decimal* separator, and a space is never part of a number's value.

**Replaced:** `decimalPoint()` → `.`, `negativeSign()` → `-`,
`positiveSign()` → `+`. The sign entries are not hypothetical — measured
2026-08-04, `sv_SE`, `nb_NO` and `lt_LT` all return **U+2212** from
`negativeSign()`, and `_format_amount` renders with it.

**Not handled — and deliberately, with the measurement to say why:** locales
whose digits are not ASCII. `ar_EG` returns `zeroDigit()` U+0660 and
`negativeSign()` U+061C; `fa_IR` returns U+06F0 and U+200E. Their rebuilt
strings still fail `Decimal`, which step 4 now turns into *no locale candidate*
— so the input is **refused**, not mis-parsed and not a crash. Supporting
Arabic-Indic digit entry is §9 decision 5. The value of step 4's guard is
exactly that this degrades to today's behaviour instead of to an exception.

### 4.5 The resolution rule

**Step 0 — the shape guard, before any candidate is consulted.** If the stripped
string matches

```
^[+-]?\d{1,3}[.,]\d{3}$
```

it is **ambiguous by shape** and is refused, whatever the two parsers say. §2.3
is the whole argument: this shape reads as a thousands group in one convention
and a three-place fraction in the other, and the two-candidate table below cannot
see it, because the losing convention *rejects* rather than disagreeing.

The guard is written against both `.` and `,` rather than against the locale's
own separators, because the hazard is the user importing a **foreign**
convention — the `en_ZA` user typing `1,500` is using the one grouping their
locale does not have.

**Step 0 cannot refuse a string the app itself displayed** (INV-2), and that is
not luck: every display magnitude carries the currency's minor-unit exponent
(`to_display_decimal` → `Decimal(amount_minor).scaleb(-exponent)`, so exponent
`-2` for all six supported currencies), and `_format_amount` renders that many
decimals. Two decimals after the separator never matches `\d{3}`. §8
alternative 6 records what moves if a 3-decimal currency is ever added.

**Steps 1–2 — non-finite candidates are discarded, then the table.** A candidate
that is not `is_finite()` is dropped before the comparison. Without this,
`Decimal("nan")` and `QLocale().toDouble("nan")` both succeed (measured
2026-08-04) and `Decimal.__eq__` is **false for two NaNs**, so a typed `nan`
routes to the disagree branch and produces *"reads as NaN or as NaN"* — a
nonsense refusal on a defined input path. Dropping both leaves no candidate and
the ordinary "not a valid number" message.

| `c_value` | `locale_value` | Result |
|-----------|----------------|--------|
| none | none | `ValueError("amount is not a valid number")` |
| a value | none | that value |
| none | a value | that value |
| both, `==` | | the C value (deterministic; they are numerically equal) |
| both, `!=` | | `ValueError` — **refuse**, naming both readings |

Equality is `Decimal.__eq__` — numeric, so `Decimal("1.10") == Decimal("1.1")`
agrees, which is what we want; `parse_transaction` counts *significant*
fractional digits (`normalize()`), so trailing zeros cannot change the outcome
downstream either.

**The refusal message renders both readings in the user's own convention**, via
the same `QLocale().toString()` the display side uses, and labels which is which.
Rendering them in the C convention would show a `de_DE` user
*"reads as 1234 or as 1.234"*, in which the second is how **their** locale spells
the first — the message would repeat the ambiguity it exists to resolve. So:

```
amount is ambiguous: "1.234" reads as 1.234 (grouped) or as 1,234 (decimal)
                     — retype it using the format the app displays
```

Deriving the message from the parser's own candidates is what makes it impossible
for the hint to disagree with the parser — the same failure FIBR-0216 fixed in
the placeholder, arriving through a different door. Step 0's refusal uses the
same message, with the two readings computed from the shape.

The message is plain English, untranslated, matching every existing
`parse_transaction` message (`"amount is not a valid number"`,
`"amount must be non-zero"`) which `_on_add` already renders verbatim. §9
decision 3 records that translating parser messages is a separate, app-wide item.

### 4.6 The call site

`ManualEntryDialog._on_add`'s existing `add_transaction` call wraps its amount
argument; no statement is added:

```python
self._transactions.add_transaction(
    account_id, occurred_on, parse_amount_input(self._amount.text()), self._description.text()
)
```

`add_transaction` already takes `str | Decimal` (verified:
`services/transactions.py`, `raw_amount: str | Decimal`) and passes a `Decimal`
straight through untouched, so no service-layer change is needed. Every existing
rejection — zero, non-finite, over-precise, past the 64-bit bound — still happens
in `parse_transaction`, unchanged and single-homed.

The existing `except VaultLockedError` stays correct: `parse_amount_input`
touches no vault, and `add_transaction` still reads the currency exponent before
parsing.

## 5. Invariants

- **INV-1** — `parse_transaction` remains C-locale only, and no importer's result
  depends on the desktop locale.
  *Test:* `tests/features/amount_input/test_amount_input.py` — run a CSV, an OFX
  and a `standard_bank` PDF fixture through their importers twice, once under
  `QLocale.setDefault(QLocale.c())` and once under `de_DE`, and assert the
  resulting `amount_minor` lists are identical. Also assert
  `parse_transaction("2026-07-01", "-12,34", "x", 2)` raises `ValueError` under
  `de_DE` — the C parser must stay C. The importer leg needs a **discriminating
  fixture row**: an ordinary `-12.34` yields the same result under both locales
  whether or not the layer moved, so at least one row must carry a grouped
  amount (`1,234.56`) whose two readings differ. Assert that row's
  `amount_minor` explicitly, not just list equality.
  *Breaks when:* someone "completes" this fix by moving the locale layer down
  into `parse_transaction`, so a German user's bank statement imports to
  different numbers than the same file on an English machine.

- **INV-2** — Every string `_format_amount`'s magnitude can produce is accepted,
  under each of the measured locales, and returns the magnitude exactly.
  *Precondition, and it is load-bearing:* display amounts reach `_format_amount`
  via `to_display_decimal`, which returns `Decimal(amount_minor).scaleb(-exponent)`
  — exponent `-2` for all six supported currencies — so a magnitude always
  carries two decimals. That is what keeps §4.5 step 0 from refusing the app's
  own output.
  *Test:* for each locale in `{en_US, en_ZA, de_DE, fr_FR, sv_SE}` and each of
  `Decimal("12.34")`, `Decimal("1234.56")`, `Decimal("1234567.89")`,
  `Decimal("0.05")`: pin the locale, call **`_format_amount(v, "ZAR")`** (not a
  re-implementation of its `toString` line), strip the known `"R "` prefix, feed
  the remainder to `parse_amount_input`, and assert the result equals `v`.
  Anchoring on the shipping function is the point: a leg that re-renders the
  magnitude itself stays green when `_format_amount` changes and the real
  round-trip breaks. `sv_SE` is in the list because its U+2212 minus is the one
  locale in the set whose own display string crashes an implementation missing
  §4.4's sign normalisation.
  *Breaks when:* the separator or sign set misses a locale's character —
  `fr_FR`'s U+202F group and `sv_SE`'s U+2212 minus are the two a
  two-locale test would not catch.

- **INV-3** — Every C form that the locale convention does **not** read as a
  different number is accepted under every locale, unchanged.
  *Test:* for each of the five locales, `parse_amount_input("-12.34") ==
  Decimal("-12.34")` and `parse_amount_input("1234.56") == Decimal("1234.56")`.
  *Breaks when:* the implementation *replaces* C parsing with locale parsing
  instead of adding to it — which would break every user who types `12.34`
  today, and falsify the `-12.34` placeholder FIBR-0216 pinned. This is the
  invariant that keeps that placeholder honest without touching it.
  *Note the qualifier, which is not hedging:* `1.234` is a C form that INV-4 and
  INV-8 refuse. Stated unqualified, this invariant would authorise "prefer C
  whenever it parses" — deleting INV-4's refusal rule, with two invariants
  contradicting each other and no tie-break for the implementer.

- **INV-4** — When both conventions parse the input and disagree, it is
  **refused**; no value reaches the vault, and the message names both readings.
  *Test:* under `de_DE`, `parse_amount_input("1.234")` raises `ValueError`; same
  for `"12.345"` and `"-1.234"`. Assert the two rendered readings, **not** the
  raw input echo — the message quotes the input verbatim, so a naive
  `"1.234" in msg` is satisfied by the echo alone and half the assertion cannot
  fail. Assert the substring after `reads as`.
  Plus **two** `qtbot` legs, and the positive one is the load-bearing half:
  (a) under `de_DE`, type `1.234`, click Add, assert the error label is non-empty
  and the transaction count did not grow; (b) under `de_DE`, type `-12,34`, click
  Add, and assert **one transaction was stored with `amount_minor == -1234`**.
  Leg (a) alone passes against an implementation that never wires
  `parse_amount_input` into `_on_add` at all — unwired, `1.234` reaches
  `parse_transaction`, parses in C, and is refused as over-precise, producing
  exactly the asserted outcome. Leg (b) is the only leg in this spec that fails
  when §4.6 is omitted.
  *Breaks when:* the implementation prefers one candidate — a silent 1000x error
  on a money field, which is the whole hazard this spec exists for.

- **INV-5** — Group separators are removed **before** the decimal point is
  swapped.
  *Test:* under `de_DE`, `parse_amount_input("1.234,56") == Decimal("1234.56")`,
  `parse_amount_input("-12,34") == Decimal("-12.34")`, and
  `parse_amount_input("1.234.567,89") == Decimal("1234567.89")`.
  *Breaks when:* the two steps are swapped — measured §4.3, each of those three
  becomes 100x too large, silently. A test written only against `en_ZA` or
  `fr_FR` passes either order, which is why all three legs pin `de_DE`.

- **INV-6** — The returned value is an exact `Decimal` rebuilt from the input
  string, never Qt's `toDouble` float.
  *Test:* under `en_US`, `parse_amount_input("92233720368547758.07") ==
  Decimal("92233720368547758.07")` — the value `test_INV4b_accepts_the_largest_storable_amount`
  already uses as the 64-bit bound. Round-tripped through a binary float it
  becomes `9.223372036854776E+16` (measured 2026-08-04:
  `Decimal(str(float("92233720368547758.07")))`), so the leg is red against any
  implementation that returns `Decimal(str(value))`.
  *Breaks when:* someone uses the float `toDouble` already computed, because it
  is right there and looks free.

- **INV-7** — The §2.1/§2.2 matrix is asserted by a test, not only recorded in
  this document.
  *Test:* a table-driven leg that pins each locale and asserts, per row, whether
  `QLocale().toDouble` accepts the string and what `parse_amount_input` returns
  or raises.
  Name the columns it asserts: for each row, whether `toDouble` accepts, and
  what `parse_amount_input` returns or raises. The `naive` column of §2.1 is
  evidence for the design, not behaviour to assert, and §2.2's summary row is
  prose — neither is part of this leg.
  *Breaks when:* a PySide6 upgrade changes `QLocale`'s group-placement
  **strictness**. That strictness is load-bearing — §2.1 depends on `de_DE`
  *rejecting* `-12.34` rather than reading it as `-1234` — and without this leg
  the change would land as a silent behaviour change in money parsing rather
  than a red suite. (Distinct from §4.4's *leniency*, which is Qt accepting an
  ASCII space where the locale groups with NBSP; the two are opposite
  properties and this invariant pins the first.)

- **INV-8** — An input matching `^[+-]?\d{1,3}[.,]\d{3}$` is refused under every
  locale, whatever the two candidates say.
  *Test:* under each of `en_ZA`, `de_DE`, `fr_FR`, `en_US`, assert
  `parse_amount_input` raises `ValueError` for `"1,500"`, `"12,500"`, `"1.500"`
  and `"2,000"`. Then the leg that proves it matters: assert that **no**
  `_format_amount` magnitude from INV-2's value list matches the pattern, so the
  guard cannot refuse the app's own output.
  *Breaks when:* the guard is dropped as redundant on the grounds that §4.5's
  table "already handles ambiguity". Measured 2026-08-04 without it: `en_ZA`
  `1,500` → `Decimal("1.500")` → stored as **150 minor units** where the user
  meant 150 000 — accepted silently, and a regression against today's refusal.

- **INV-9** — `parse_amount_input` raises **only** `ValueError`, for every input.
  *Test:* drive a table of hostile inputs — `""`, `"-"`, `"nan"`, `"inf"`,
  `"1_000"`, `"."`, `","`, `"1e999999"`, a 500-char digit string, and (pinned
  under `sv_SE`) `_format_amount(Decimal("-1234.56"), "ZAR")`'s magnitude —
  through `parse_amount_input` under every measured locale, and assert that
  anything raised is a `ValueError`.
  *Breaks when:* step 4's rebuild is left unguarded. `Decimal` raises
  `InvalidOperation`, an `ArithmeticError` and **not** a `ValueError`, so it
  escapes `_on_add`'s handler and crashes the slot rather than showing an error.
  Measured reachable 2026-08-04 under `sv_SE` on the app's own display string.

## 6. Failure modes

- **A `de_DE` user who means one thousand two hundred thirty-four types `1.234`
  and is refused.** Deliberate (§8 alternative 2). They retype `1.234,00` or
  `1234`. The cost is one retype, in the one input shape where the alternative
  is a 1000x error. Note the C reading of that same string (`1.234`, three
  decimals) is over-precise for every currency this app supports — all six in
  `CURRENCY_EXPONENTS` are exponent 2 (verified: `services/auth.py`) — so it
  would be refused by `parse_transaction` anyway; refusing here loses the user
  nothing they could have stored.
- **A grouped whole amount is refused: `1,500` everywhere, `1.500` too.**
  Deliberate, INV-8 — this is the §2.3 hazard, and the shape genuinely has two
  valid readings. Under `en_US` the input would have resolved to `1500`
  correctly, so the guard costs that locale a small convenience; it is refused
  today as well, so nothing regresses. `1,500.00` and `1500` both work.
- **A pasted `R 1 234,56` (with the currency symbol), or a bracketed negative
  `(R 12,34)`, is refused.** Unchanged from today. §9 decisions 2 and 6.
- **A locale with non-ASCII digits (`ar_EG`, `fa_IR`) refuses everything the
  locale convention would have accepted.** Measured §4.4: the rebuild fails and
  step 4 yields no locale candidate, so such a user falls back to the C form,
  which INV-3 keeps working. Refusal, never a wrong number and never a crash.
  §9 decision 5.
- **`nan` / `inf` typed literally.** Both parse on both sides; §4.5 step 1 drops
  non-finite candidates, so the message is the ordinary "not a valid number"
  rather than an ambiguity report naming NaN twice.
- **A locale outside the measured four with a fifth grouping convention.** The
  design is convention-agnostic — it reads `groupSeparator()` and
  `decimalPoint()` from the locale rather than hardcoding — but only four are
  asserted. §11 carries this as an uncovered row.
- **An auto-lock while the dialog is open.** Unchanged: `parse_amount_input`
  touches no vault, and `_on_add`'s existing `except VaultLockedError` still
  guards the `add_transaction` call.

## 8. Alternatives considered (and rejected)

1. **Strip separators and swap the point (the naive fix).** Rejected on
   measurement, §2.1: under `de_DE` a typed `-12.34` becomes `-1234`, accepted
   silently. Trading a refusal for a 100x error is a regression however good the
   intent. This is the alternative the ROADMAP bullet was split out to prevent.
2. **Resolve ambiguity by dropping the candidate `parse_transaction` would
   reject anyway.** Tempting and *nearly* free: §2.2's disagreeing inputs all
   have a C reading with three decimals, over-precise for every supported
   currency, so dropping it would leave exactly one survivor and accept `1.234`
   as `1234` — what a German user means. Rejected because it makes the same
   typed string mean two different numbers depending on the vault's currency, a
   rule no user can predict; and because a user typing a C-style `1.234` would
   get `1234` — a silent 1000x error where today they get a refusal. That is
   alternative 1's failure mode wearing better clothes. The premise would move
   if a 3-decimal currency were ever added to `CURRENCY_EXPONENTS`; it would
   move in the direction of *more* ambiguity, not less.
3. **A `QDoubleValidator` on the field.** It would block the keystroke rather
   than explain the refusal, gives no route to report *why* an ambiguous input
   was rejected, and validates against the locale only — so it would reject the
   C form that INV-3 requires, and reject the `-12.34` placeholder under `de_DE`.
4. **Parse with `babel`.** A new runtime dependency, on a bundle that ships
   PySide6 already, for a rule that is four lines against an API already
   imported. `dependencies.md` § 1 (justify every dependency).
5. **Make the placeholder locale-aware instead.** Does not fix the bug — the
   user still cannot type back what the app displayed — and re-opens a decision
   FIBR-0216 closed. §9 decision 4.
6. **Skip §4.5 step 0 and let the two-candidate table carry ambiguity alone.**
   This is what the spec said before its first review, and it is wrong by
   measurement: the table only fires when *both* parsers succeed, so `en_ZA`
   `1,500` — where C simply rejects — takes the single surviving candidate and
   stores `1.5`. Rejected because it reintroduces exactly the silent-1000x class
   this item was split out of FIBR-0216 to prevent, on the app's default locale.
   *Premise that could move:* step 0's safety rests on display magnitudes always
   carrying two decimals. Add a 3-decimal currency to `CURRENCY_EXPONENTS` and a
   displayed `1,234` would match the guard's pattern, so the app would refuse its
   own output — at which point the guard must become exponent-aware, and INV-2's
   leg is what would go red first.

## 9. Out of scope

1. **Locale-aware amount input anywhere else.** There is nowhere else: §3
   decision 3 verified `ManualEntryDialog` is the only typed-amount field.
2. **Accepting a pasted currency symbol** (`R 1 234,56`). Refused today, refused
   after. A separate, larger question (which symbols, which positions, what
   about a non-base currency), and refusing is safe.
3. **Translating parser messages.** Every `parse_transaction` message is
   untranslated English today; this item adds one more in the same style rather
   than opening an app-wide i18n item for the parser layer.
4. **The manual-entry placeholder stays exactly as FIBR-0216 left it** — the
   non-translatable literal `-12.34`. It needs no change: INV-3 makes that
   string valid under every locale, so the hint and the parser still cannot
   disagree. This is stated rather than silently skipped because a reader who
   knows FIBR-0216 will ask.
5. **Non-ASCII digit entry** (`ar_EG`, `fa_IR` and the other Arabic-Indic
   locales). Measured §4.4: those inputs are refused, not mis-read. Supporting
   them means a digit-transliteration step and a test matrix of its own, and the
   app ships no translations for those locales today.
6. **The bracketed negative form** `(R 12,34)`. `_format_amount` can render it
   (`NegativeStyle.BRACKETS`), and it is refused on input before and after this
   item. Named here because §1 would otherwise read as promising it.
7. **`_format_amount` itself.** Display is already correct.
