## 1. Summary

Turn finbreak from backward-looking ("what did I spend?") into forward-looking
("can I afford this?"). A new **Forecast** tab projects the account balance
forward from **confirmed** recurring income and expenses (FIBR-0142), drawing a
projected-balance line to a chosen horizon.

The forecast's **starting number is a real, current balance** — not a guess and
not a stale figure. Every bank statement prints a closing balance; the importers
already parse it (the Standard Bank importer computes it for its completeness
checksum, then discards it). This feature **persists** that closing balance
(D3), then **brings it current to today** by adding the actual transactions
finbreak has already imported since the statement's date (D1). The forecast
anchors to the sum of those per-account current balances, then projects the
confirmed recurring flows forward.

When no statement has recorded a balance yet (e.g. a CSV-only account), the
forecast falls back to an honest **net-flow** framing: a line from zero showing
the projected *change* ("+R2,400 net by month-end"), never a fabricated balance.

Correctness-critical: finbreak handles people's money, so the forecast must never
show a confidently-wrong number. Every rand shown is either a real balance
brought current from persisted data (with its provenance) or an explicit
projected *change*.

## 2. Design decisions

**D1 — Anchor = persisted statement balance brought current with real
transactions.** A statement's closing balance is the only real absolute balance
finbreak can know (summing all imported transactions gives net *change* since the
first import, not a true balance). So for each account we take its **latest**
statement that recorded a closing balance (INV-6), then **add the account's
actual transactions dated in the half-open window `(period_end, today]`** — i.e.
strictly after the statement's `period_end` (rows on `period_end` are already in
the closing balance) and no later than today (future-dated rows are excluded from
the *current* balance) — the running-balance roll-forward every bank does. The
vault-wide anchor is the sum of these per-account current balances. Because each
account is independently rolled to *today*, the summed anchor is coherently "as
of today" (no mixed-date figure), and any income/expense already imported since
the last statement is included, not omitted. The projection window is the
**disjoint** `(today, horizon]` (D6), so no flow is counted in both the anchor
and the forecast. This assumes the post-statement imports are gap-free; a gap is
the reconciliation concern tracked separately (FIBR-0177), and is the best any
local app can do.

> **Amended by FIBR-0179 (post-ship fix).** "For each account" above is narrowed
> to **cash accounts only** (`current`, `savings`) — the same gate FIBR-0177 D1
> applies, for the same reason: a debt product prints its closing balance in the
> *owed* convention (positive = debt), the opposite sign to `amount_minor`, so
> the roll-forward moved it the wrong way and an owed figure was summed into a
> cash total. Debt / investment / other accounts now contribute nothing to the
> anchor and are listed as excluded by D10's provenance line. Contract:
> `tests/features/forecast/spec.md` INV-14.

**D2 — Net-flow fallback when no balance is known.** If *no* account has any
recorded closing balance, the forecast runs in `NET_FLOW` mode: the projected
line starts at 0 and is framed as a projected *net change*, not a balance. Mode
is a vault-wide switch (INV-2). In `ANCHORED` mode, accounts that have no
recorded balance contribute nothing to the anchor and are named as excluded in
the provenance line (D10), and the headline states the account coverage so a
partial total is never mistaken for a whole-vault balance.

**D3 — Persist the closing balance: schema v11.** The migration chain is
currently at **v10** (`LATEST_SCHEMA_VERSION = 10`; `_migrate_to_v10` already
exists — the hot-path indexes). This feature adds **`_migrate_to_v11`**:
`statement_periods` gains a nullable `closing_balance_minor INTEGER` column,
inside an `owned_transaction` block that ends `UPDATE schema_version SET version
= 11`. `LATEST_SCHEMA_VERSION` bumps **10 → 11**, and `_MIGRATIONS` gains the
`11: _migrate_to_v11` entry. The balance's effective date is the row's existing
`period_end` (a closing balance is as-of the statement end date) — no separate
date column. **No backfill** is possible: historical statements' balances were
discarded at import and are gone; only statements imported *after* this ships (or
re-imported) populate the column. Old rows stay `NULL` and contribute nothing to
the anchor. Idempotency comes from **version-gating** — `run_migrations` only
calls `_migrate_to_v11` for a vault at exactly v10 (`range(current+1,
LATEST+1)`), so the bare `ALTER TABLE ADD COLUMN` runs once and is never replayed
(it is *not* replay-safe on its own). **The version bump is a repo-wide test
sweep, not a two-file edit.** Every assertion that pins the *fully-migrated /
first-run* schema version to `10` bumps to `11` — grep `tests/features` for
`== 10` in a migrate-to-latest / first-run context and for `LATEST_SCHEMA_VERSION
== 10`. The grep is **authoritative**; treat the following list as illustrative, not
exhaustive — it spans ~11 files (db_performance, ofx_import, import_, pdf_import,
categorisation, recurring, transfers, categories, vault, accounts, and the backup
first-run manifest `schema_version == 10`), plus the version stated in the
affected feature `spec.md` prose. **Leave untouched:**
intermediate-version assertions in the per-feature migration atomicity/rollback
tests (`== 2 … == 9`), and the `LATEST_SCHEMA_VERSION + 1` self-tracking sites
(e.g. `accounts` too-new-vault-rejection) which track the constant automatically.
Where an assertion means "the latest version", prefer asserting against
`LATEST_SCHEMA_VERSION` (the codebase's own self-tracking idiom) over a fresh
hard-coded `11`. Note `accounts/test_accounts.py` has **both** kinds — three
hard-coded `== 10` first-run/migrate assertions that DO bump, alongside its
`LATEST_SCHEMA_VERSION + 1` rejection test that does not.

**D4 — Thread the balance through the whole importer→persist pipeline.**
`ParseResult` gains `closing_balance_minor: int | None = None` (its **last**
field; the default `None` keeps every existing 4-arg positional construction and
every existing importer/test unchanged — INV-8). But `commit_import` consumes an
`ImportPreview`, not a `ParseResult`, so the balance must be carried across the
preview boundary too:
- `StandardBankImporter.parse` sets `closing_balance_minor = _minor(closing,
  exponent)` when a closing prints, else `None` (Family A / Savings prints none).
- `OfxImporter._parse_statement` sets it from the OFX ledger balance via
  `getattr(statement, "balance", None)` (ofxparse leaves `balance` **unset**, not
  `None`, when no `<LEDGERBAL>` is present — a bare attribute access raises
  `AttributeError`, and `_parse_statement` runs outside the wizard's boundary
  `try/except`), converting a present `Decimal` to minor with the shared
  `services.transactions.to_minor(value, exponent)` — the same helper
  `standard_bank.py` uses (FIBR-0181 consolidated the two).
- CSV and manual entry leave it `None` (no balance column in v1).
- `ImportPreview` gains `closing_balance_minor: int | None`, threaded through
  `_preview_from_result` / `_build_preview` (read off the `ParseResult`) and
  preserved by `retarget` (a re-target must not drop it).
- `ImportService.commit_import` passes `preview.closing_balance_minor` to
  `StatementPeriodRepository.add(...)`.
- **Span-reuse path** (an identical `(account, period_start, period_end)`
  re-import returns an existing id): call a new
  `StatementPeriodRepository.update_closing_balance(period_id, balance_minor)`
  **only when the stored value is currently `NULL`** and the incoming balance is
  non-`None` (fill a gap left by a prior CSV-only import). A non-`NULL` stored
  balance is **never** overwritten — for one span the closing balance is fixed,
  so an incoming *different* non-`NULL` value signals a parse/wrong-file error;
  keep the stored value but **log a warning** naming the span and both values so
  the disagreement is not swallowed unseen (INV-12).

**D5 — Project the confirmed recurring set only.** The projection consumes
`RecurringService.confirmed(today)` — the user-vetted arrangements. Suggested
(un-decided) and dismissed items never appear. The recurring engine is
vault-wide, so the forecast is vault-wide.

**D6 — Pure projection core, integer-minor only, reusing the recurring stepper.**
The service prepares each confirmed item into a Decimal-free input and calls a
clock-free pure function:
```
project_forecast(
    anchor_minor: int | None,          # None => NET_FLOW mode
    items: list[ForecastInput],        # signed integer-minor amounts, prepared
    today: date,
    horizon: date,                     # inclusive end
    anchor_sources: list[AnchorSource] | None = None,  # service-built; carried onto the result (normalised to [])
) -> Forecast
```
`ForecastInput` carries `amount_minor: int` (**signed**: `+` for `IN`, `-` for
`OUT`), `next_expected: date`, `cadence: Cadence`, `merchant: str`, `direction:
Direction`. There is **no `exponent` and no `Decimal` in the core** — the service
does the exact minor conversion once (D7) and passes in the `anchor_sources` it
assembled (the core has no account context of its own, so it just carries them
onto the returned `Forecast` — this is the pure-vs-service seam §7 tests split
on). For each item the core generates future occurrences by **reusing
`finbreak.services.recurring._add_cadence`** (the same calendar-aware stepper
FIBR-0142 uses — month/year day-clamped, Jan 31 → Feb 28/29; weekly/fortnightly
fixed-day): start at `next_expected`, roll forward with `_add_cadence` while
`<= today`, then emit each occurrence while `<= horizon`. So every projected
event falls strictly after today, in the **disjoint** `(today, horizon]` window
(the anchor already owns `(period_end, today]`, D1) — no double-count. This also
guarantees the Forecast tab and Recurring tab never disagree about an item's
dates (rule 3, reuse). Each occurrence is a signed event.

The per-item events are then **merged across all items and stable-sorted by
`(on, merchant, direction)`** (a stable sort over that key, fed by the
deterministic `confirmed()` order, so two occurrences that tie on all three keep
a stable, reproducible position) before the running balance is accumulated:
`start_minor = anchor_minor or 0`; walking the sorted events, each
`event.running_after_minor` is the running total after applying it; `end_minor =
start_minor + Σ event.amount_minor` (order-independent, INV-1). The step-line
`points` is `(today, start_minor)`, then one `(event.on, event.running_after_minor)`
per event, then a terminal `(horizon, end_minor)` — so a zero-event forecast
still has two points and draws a flat line to the horizon (INV-13). Two benign
degenerate cases: an event landing exactly on `horizon` yields a point equal to
the terminal vertex (a duplicate `(horizon, end_minor)` — harmless, the line has
a zero-length final segment); and `horizon == today` (the "End of this month"
preset on the last day of a month) yields an empty `(today, horizon]` window and
two coincident points `(today, start_minor)` — an honest zero-width forecast, not
an error. Termination is guaranteed: every `_add_cadence` step advances the date
by ≥ 7 days.

**D7 — Amount → minor conversion is exact, and lives in the service.**
`RecurringItem.amount` is `to_display_decimal(median_low_minor, exponent)` =
`Decimal(minor).scaleb(-exponent)`; converting it back with the same exponent
(`to_minor(amount, exponent)`, its exact inverse) recovers the exact minor
integer (INV-7). `ForecastService` does this once per confirmed item (applying
the direction sign) and passes integer minor amounts into the core, so the core
is Decimal-free and money-safe. The `Account` model carries **no**
per-account currency field; the vault has a single base-currency exponent (the
`minor_unit_exponent` setting), so summing `closing_balance_minor` across
accounts can never mix exponents (INV-13). Multi-currency is out of scope (D12).

**D8 — Horizon: presets in the UI, an explicit date in the core.** The tab offers
**End of this month** (default), **30 days**, **60 days**, **90 days**. The UI
computes the concrete horizon date from the preset and `today` (`today` ≤
horizon always); the pure core takes the date. End date is inclusive (INV-11).

**D9 — Surface: a new Forecast tab**, added to the workspace immediately after
Recurring (`main_window._build_workspace`). `ForecastWidget(service: AuthService)`
mirrors `RecurringWidget` — it takes the `AuthService` and builds
`ForecastService(service.vault)` internally. It contains:
- a **headline figure** — `ANCHORED`: "Projected balance <coverage>: ~R X by
  <horizon>", where `<coverage>` names the account scope when not all accounts
  contributed (e.g. "(Cheque only)"); `NET_FLOW`: "Projected net change: +R X by
  <horizon>". The double-empty case (NET_FLOW *and* zero confirmed items) reads
  "Projected net change: R0 by <horizon>" (start 0, end 0);
- an **anchor-provenance** line (D10);
- a **horizon picker** (`QComboBox`);
- a themed projected-balance **line chart** — a new `build_forecast_chart(points,
  theme) -> QChart` returning a `QChart` (matching every existing `ui/charts.py`
  builder, which return `QChart`; the widget wraps it in a `QChartView`). It
  draws a `QLineSeries`, which the existing `_themed_chart` helper does **not**
  accept (its union is `QPieSeries | QBarSeries`), so it uses its own small
  themed-line path — it is **not** modelled on `build_trend_chart` (a bar chart);
- an **upcoming-events table** (date · merchant · signed amount · running balance
  after), reusing the `RecurringWidget` table idiom.
Empty states: zero confirmed recurring → `points` is just `[(today,
start_minor), (horizon, start_minor)]`, so the chart draws a flat line from today
to the horizon, and the table shows "No confirmed recurring items yet — confirm
some on the Recurring tab"; the headline still renders per the rules above.
(While editing `_build_workspace`, correct its stale "seven-tab" docstring — it
already adds eight tabs; Forecast makes nine.)

**D10 — Anchor provenance is explicit and honest.** The provenance line states
that the starting figure is brought current to today and names each contributing
account with its source statement date and how many transactions were rolled in,
e.g. "Starting balance R8,600 as of today — from Cheque's statement of 2026-06-30
+ 4 later transactions, Savings' statement of 2026-07-15 + 1 later transaction".
The "+ N later transaction(s)" clause is correctly pluralised and **omitted
entirely when N is 0** (a freshly-imported statement adds no "+ 0"). A negative
brought-current balance (overdrawn account) is legitimate and renders as a
negative figure. Accounts with no recorded balance are named as excluded from the
starting figure.
In `NET_FLOW` mode the line instead explains there is no known balance yet and the
chart shows projected change only.

**D11 — Themed + translatable.** Chart colours come from `ChartTheme`; all
user-facing strings go through `tr()` / the established translate context, like
`build_trend_chart` and `RecurringWidget`.

**D12 — Explicitly out of scope for v1** (roadmap follow-ups, logged not dropped):
a user-typed manual balance override for balance-less accounts; per-account
(rather than vault-wide) forecasts; multi-currency accounts; scenario/what-if
one-off inputs; a CSV balance-column mapping.

## 3. New / changed models

In `models.py`:
- `StatementPeriod` **gains** `closing_balance_minor: int | None` as its **last**
  field (the three repo SELECT column lists append it to keep `StatementPeriod(*row)`
  aligned — the codebase's field-order convention).
- `ForecastMode(StrEnum)`: `ANCHORED`, `NET_FLOW`.
- `ForecastEvent` (`@dataclass`, field order pinned): `on: date`, `merchant: str`,
  `direction: Direction`, `amount_minor: int` (**signed**; its sign is
  authoritative for INV-1 sums — `direction` is carried only for display/colour
  and must agree), `running_after_minor: int`.
- `ForecastPoint` (`@dataclass`): `on: date`, `balance_minor: int` — the step-line
  vertices (the start point plus one after each event).
- `Forecast` (`@dataclass`): `mode: ForecastMode`, `start_minor: int`,
  `end_minor: int`, `horizon: date`, `points: list[ForecastPoint]`,
  `events: list[ForecastEvent]`, `anchor_sources: list[AnchorSource]`.
- `AnchorSource` (`@dataclass`): `account_id: int`, `account_name: str`,
  `statement_balance_minor: int`, `as_of: date` (the source statement's
  `period_end`), `since_txn_count: int`, `current_balance_minor: int` — one per
  contributing account (empty in `NET_FLOW` mode).

`ForecastInput` (D6) lives in `services/forecast.py` (a service-internal prep
type, not persisted). `StatementRow` (the Statements-tab view model) is
**unchanged** — showing the balance on the Statements tab is out of scope.

## 5. Invariants (test targets)

- **INV-1** — `end_minor == start_minor + Σ event.amount_minor` (signed), exact
  integer, both modes.
- **INV-2** — `mode == NET_FLOW` ⟺ `anchor_minor is None` ⟺ no account has a
  recorded closing balance; in `NET_FLOW` `start_minor == 0` and `anchor_sources`
  is empty. Mode is a single vault-wide switch.
- **INV-3** — only `confirmed` recurring items are projected; a suggested or
  dismissed item never produces an event.
- **INV-4** — every projected event date is in the half-open `(today, horizon]`;
  an item's first occurrence is its `next_expected` rolled forward with
  `_add_cadence` while `<= today` (so the first emitted date is strictly `>
  today`); each subsequent occurrence equals `_add_cadence` applied to the
  previous (byte-for-byte the recurring engine's stepping, incl. the month-end
  clamp — testable via a monthly item crossing Jan 31 → Feb 28).
- **INV-5** — an `IN` item raises the running balance, an `OUT` item lowers it;
  each `ForecastEvent.amount_minor` sign matches its `direction`.
- **INV-6** — a contributing account's statement balance is its latest
  (`max period_end`, tie `max id`) `statement_periods` row with a non-`NULL`
  `closing_balance_minor`; accounts without one contribute nothing.
- **INV-7** — a persisted closing balance round-trips exactly (Decimal ↔ minor);
  a statement with no closing (Savings) stores `NULL` and imports fine; the
  service's amount→minor prep recovers the exact `median_low` minor value.
- **INV-8** — existing importers/tests unaffected: `ParseResult`'s new field
  defaults `None`; the CSV/manual path stores `NULL`; a pre-v11 `StatementPeriod`
  round-trips with `closing_balance_minor is None`.
- **INV-9** — `_migrate_to_v11` turns a v10 vault into a v11 vault: the column
  exists, old rows are `NULL`, the vault version reads 11; the step is
  version-gated (never replayed).
- **INV-10** — the Forecast tab is present after Recurring and renders without
  crashing when there are zero confirmed recurring items and/or zero statements.
- **INV-11** — horizon presets compute the correct dates (end-of-month; `today +
  N days`) with `today <= horizon`; the projection window is `(today, horizon]`;
  the pure core is clock-free.
- **INV-12** — span-reuse balance write is **fill-only**: it writes iff the stored
  value is `NULL` and the incoming is non-`None`; a stored non-`NULL` balance is
  never overwritten, even by a different incoming value.
- **INV-13** — the anchor is the sum over contributing accounts of
  (`statement_balance_minor` + `sum_after(account_id, period_end, today)[0]`),
  i.e. the statement balance brought current with transactions in `(period_end,
  today]`; because `Account` has no per-account currency and the vault has one
  `minor_unit_exponent`, this cross-account sum never mixes exponents. The
  step-line is consistent — `len(points) == 2 + len(events)`, `points[0] ==
  (today, start_minor)`, `points[-1] == (horizon, end_minor)`, point dates
  non-decreasing, and each interior `point.balance_minor` equals
  `event.running_after_minor` for the event that produced it.

## 6. Known limitations (documented, honest)

- Bringing the balance current assumes the imports **since** the last statement
  are gap-free. A missed import between the statement and today would make the
  starting figure off by the gap — this is the account-reconciliation concern,
  tracked separately (FIBR-0177), and is the best a local, import-driven app can
  do. The provenance line's "+ N later transactions" makes the roll-forward
  visible so a surprising figure is traceable.
- Accounts whose latest import carried no balance (CSV-only, older pre-v11
  imports) contribute nothing to the anchor until a balance-bearing statement is
  imported; they are named as excluded.
- The forecast projects only *recurring* items; one-off future costs a user knows
  about are not modelled (a possible what-if follow-up, D12).
- The anchor owns dates through today and the projection owns dates strictly
  after today (D1/D6), so a recurring item *expected today but not yet imported*
  is neither in the anchor nor projected until its next cadence — a ≤1-cadence
  edge, accepted for a clean disjoint boundary rather than risking a double-count
  at today.
