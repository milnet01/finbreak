# FIBR-0171 — Cash-flow forecast

**Status:** DRAFT (pre-cold-eyes)
**Kind:** feature
**Section:** features-accessibility
**Depends on:** FIBR-0142 (recurring-money detection — the confirmed set this
projects), FIBR-0007/FIBR-0052 (statement-period records — where the anchor
balance is persisted), FIBR-0008 (importer `ParseResult` contract).

---

## 1. Summary

Turn finbreak from backward-looking ("what did I spend?") into forward-looking
("can I afford this?"). A new **Forecast** tab projects the account balance
forward from **confirmed** recurring income and expenses (FIBR-0142), drawing a
projected-balance line to a chosen horizon.

The forecast's **starting number is a real balance**, not a guess. Every bank
statement prints a closing balance; the importers already parse it (the Standard
Bank importer computes it for its completeness checksum, then discards it). This
feature **persists** that closing balance and anchors the forecast to the sum of
each account's latest recorded closing balance — labelled with its "as of"
statement date so a stale anchor is never mistaken for a live balance.

When no statement has recorded a balance yet (e.g. a CSV-only account), the
forecast falls back to an honest **net-flow** framing: a line from zero showing
the projected *change* ("+R2,400 net by month-end"), never a fabricated balance.

Correctness-critical: finbreak handles people's money, so the forecast must never
show a confidently-wrong number. Every rand shown is either a real persisted
balance (with its date) or an explicit projected *change*.

## 2. Design decisions

**D1 — Anchor from persisted statement closing balances, not a typed field.**
A statement's closing balance is the only real absolute balance finbreak can
know (summing imported transactions gives net *change* since the first import,
not a true balance — it would be confidently wrong). So we persist the closing
balance at import time and anchor the forecast to it. No user-typed "current
balance" field in v1 (that is a possible follow-up, D12).

**D2 — Net-flow fallback when no balance is known.** If *no* account has any
recorded closing balance, the forecast runs in `NET_FLOW` mode: the projected
line starts at 0 and is framed as a projected *net change*, not a balance. This
folds the earlier "anchor if available, else net-flow" decision into a
statement-sourced anchor.

**D3 — Persist the closing balance: schema v10.** `statement_periods` gains a
nullable `closing_balance_minor INTEGER` column (migration `_migrate_to_v10`).
The balance's effective date is the row's existing `period_end` (a closing
balance is as-of the statement's end date) — no separate date column. **No
backfill** is possible: historical statements' balances were discarded at import
and are gone; only statements imported *after* this ships (or re-imported)
populate the column. Old rows stay `NULL` and simply don't contribute to the
anchor. The migration is additive and idempotent; every feature's drift-guard
schema-version constant bumps 9 → 10.

**D4 — Thread the balance out of the importer pipeline.** `ParseResult` gains
`closing_balance_minor: int | None = None`. The default `None` keeps every
existing importer and test unchanged unless it opts in.
- `StandardBankImporter.parse` sets it from the already-captured `closing`
  (`_minor(closing, exponent)`); `None` when the statement prints no closing
  (Family A / Savings legitimately prints none — INV-11 in that importer).
- `OfxImporter._parse_statement` sets it from the OFX ledger balance
  (`statement.balance`) when ofxparse exposes one, else `None`.
- CSV and manual entry leave it `None` (no balance column in v1).
`ImportService.commit_import` passes `result.closing_balance_minor` to
`StatementPeriodRepository.add`. On the **span-reuse path** (an identical
`(account, period_start, period_end)` re-import), if the incoming balance is
non-`None` it **updates** the stored value — so re-importing a PDF over a prior
CSV-only import fills in a balance that was missing.

**D5 — Project the confirmed recurring set only.** The projection consumes
`RecurringService.confirmed(today)` — the user-vetted arrangements. Suggested
(un-decided) and dismissed items never appear. The recurring engine is
vault-wide, so the forecast is vault-wide.

**D6 — Pure projection core.** A clock-free pure function:
```
project_forecast(
    anchor_minor: int | None,          # None => NET_FLOW mode
    confirmed: list[RecurringItem],
    today: date,
    horizon: date,                     # inclusive end
    exponent: int,
) -> Forecast
```
For each confirmed item it generates future occurrences: start at
`item.next_expected`, but if that is before `today` roll it forward by the item's
cadence until it is `>= today`; then step by cadence while `<= horizon`. Each
occurrence is a signed event (`+amount` for `IN`, `-amount` for `OUT`). It builds
a step-line of running balances and an events list, sorted by date then merchant.
`start_minor` = `anchor_minor or 0`; `end_minor` = `start_minor + Σ signed
events`. Termination is guaranteed: every cadence step advances the date by
`>= 7` days.

**D7 — Amount → minor is an exact round-trip.** `RecurringItem.amount` is
`to_display_decimal(median_low_minor, exponent)`; converting it back with the
**same** exponent (`quantize` + `* 10**exponent`, `ROUND_HALF_EVEN`) recovers the
exact minor integer. All projection arithmetic is integer minor units (money-safe,
matching the rest of the app). The conversion lives in one helper, reused.

**D8 — Horizon: presets in the UI, an explicit date in the core.** The tab offers
**End of this month** (default), **30 days**, **60 days**, **90 days**. The UI
computes the concrete horizon date from the preset and `today`; the pure core
takes the date. End date is inclusive.

**D9 — Surface: a new Forecast tab**, added to the workspace immediately after
Recurring (`main_window._build_workspace`). It contains:
- a headline figure — "Projected balance: ~R X by <horizon>" (ANCHORED) or
  "Projected net change: +R X by <horizon>" (NET_FLOW);
- an anchor-provenance line (D10);
- a horizon picker (`QComboBox`);
- a themed projected-balance **line chart** (`build_forecast_chart`, reusing
  `ChartTheme`, the QtCharts convention of `build_trend_chart`);
- an **upcoming-events table** (date · merchant · +/- amount · running balance
  after), reusing the `RecurringWidget` table idiom.
Empty states: zero confirmed recurring → the chart/table show a friendly "No
confirmed recurring items yet — confirm some on the Recurring tab" message and a
flat line; zero statements with a balance → NET_FLOW framing.

**D10 — Anchor provenance is explicit and honest.** The provenance line names
which accounts contributed and each contributing account's balance date, e.g.
"Starting balance R8,600 — from your latest statements (Cheque as of 2026-06-30,
Savings as of 2026-07-15)". Accounts with no recorded balance are noted as
excluded from the starting figure. Because different accounts' latest balances
carry different dates, the figure is labelled "from your latest statements" and
the projection runs forward from **today** — it does **not** attempt to fold in
actual transactions posted between each balance's date and today (documented
limitation §6; a possible follow-up, D12).

**D11 — Themed + translatable.** Chart colours come from `ChartTheme`; all
user-facing strings go through `tr()` / the established translate context, like
`build_trend_chart` and `RecurringWidget`.

**D12 — Explicitly out of scope for v1** (roadmap follow-ups, not built here):
a user-typed manual balance override for balance-less accounts; folding actual
transactions since the balance date into the anchor; per-account forecasts;
scenario/what-if inputs; CSV balance-column mapping. Each is logged as a planned
bullet rather than silently dropped.

## 3. New / changed models (`models.py`)

- `StatementPeriod` **gains** `closing_balance_minor: int | None` as its **last**
  field (the repo SELECT column lists append it to keep `StatementPeriod(*row)`
  aligned — the codebase's field-order convention).
- `ForecastMode(StrEnum)`: `ANCHORED`, `NET_FLOW`.
- `ForecastEvent` (`@dataclass`, field order pinned): `on: date`, `merchant: str`,
  `direction: Direction`, `amount_minor: int` (signed), `running_after_minor: int`.
- `ForecastPoint` (`@dataclass`): `on: date`, `balance_minor: int` — the step-line
  vertices (the start point plus one after each event).
- `Forecast` (`@dataclass`): `mode: ForecastMode`, `start_minor: int`,
  `end_minor: int`, `horizon: date`, `points: list[ForecastPoint]`,
  `events: list[ForecastEvent]`, `anchor_sources: list[AnchorSource]`.
- `AnchorSource` (`@dataclass`): `account_id: int`, `account_name: str`,
  `balance_minor: int`, `as_of: date` — one per contributing account (empty in
  NET_FLOW mode).

`StatementRow` (the Statements-tab view model) is **unchanged** — showing the
balance on the Statements tab is out of scope (YAGNI).

## 5. Invariants (test targets)

- **INV-1** — `end_minor == start_minor + Σ event.amount_minor` (signed), exact
  integer, for both modes.
- **INV-2** — `mode == NET_FLOW` ⟺ `anchor_minor is None` ⟺ no account has a
  recorded closing balance; in NET_FLOW `start_minor == 0` and `anchor_sources`
  is empty.
- **INV-3** — only `confirmed` recurring items are projected; a suggested or
  dismissed item never produces an event.
- **INV-4** — every projected event date is in `[today, horizon]`; the first
  occurrence of an item is `>= today` (a past `next_expected` is rolled forward);
  successive occurrences of one item are spaced by exactly its cadence.
- **INV-5** — an `IN` item raises the running balance, an `OUT` item lowers it;
  the running-balance column equals the cumulative signed sum.
- **INV-6** — `anchor_minor` = Σ over accounts of each account's latest
  (`max period_end`, tie `max id`) statement row with a non-`NULL`
  `closing_balance_minor`; accounts without one contribute nothing.
- **INV-7** — a persisted closing balance round-trips exactly (Decimal ↔ minor);
  a statement with no closing (Savings) stores `NULL` and imports fine.
- **INV-8** — existing importers/tests are unaffected: `ParseResult`'s new field
  defaults `None`; the CSV/manual path stores `NULL`; a v9-era `StatementPeriod`
  round-trips with `closing_balance_minor is None`.
- **INV-9** — `_migrate_to_v10` turns a v9 vault into a v10 vault: the column
  exists, old rows are `NULL`, re-running is a no-op; the vault version reads 10.
- **INV-10** — the Forecast tab is present after Recurring and renders without
  crashing when there are zero confirmed recurring items and/or zero statements.
- **INV-11** — horizon presets compute the correct dates (end-of-month; `today +
  N days`); the pure core is clock-free (`today` and `horizon` injected).

## 6. Known limitations (documented, honest)

- The anchor is the **latest statement** balance per account, not a live balance.
  If a statement is weeks old, spending since then is not reflected in the
  starting figure. Mitigated by labelling the figure "from your latest
  statements" with each account's as-of date. Folding in actual transactions
  posted since the balance date is a **follow-up** (D12), not v1.
- Accounts whose latest import carried no balance (CSV-only, older imports)
  contribute nothing to the anchor until a balance-bearing statement is imported.
- The forecast projects only *recurring* items; one-off future costs a user knows
  about are not modelled (a possible what-if follow-up, D12).

  statements-with-balances + confirmed recurring) returns the expected anchored

  and renders; empty state (no recurring / no statements) does not crash
