# FIBR-0198 — Reveal the masked account number, with an auto re-mask

**Status:** spec draft (2026-07-30).
**Kind:** feature.
**Source:** ROADMAP FIBR-0198 (in-session-2026-07-30). Split out of FIBR-0113 on
2026-07-30 (§13).
**Blocked by:** FIBR-0113 — this item reveals the account-number **column** and
the account-number **form field** that item creates, and re-uses its
`_mask_account_number` helper, its `_refresh()` fill and its
`_apply_forget_gating()` helper.
**Pairs with:** FIBR-0032 (§3 decision 3 — `_REVEAL_SECONDS` takes its value from
that item's `clipboard_clear_seconds` default), FIBR-0128 (§4.4 — the Forget
gating this must re-apply), FIBR-0193 (stores the value being revealed).

**Layman:** The Accounts tab gets a "Show account numbers" tick-box, so you can
read a full account number when you need to pay someone. It hides itself again
after half a minute, so a number can't be left sitting on screen.

## 1. Goal

The Accounts tab gains one control — a "Show account numbers" checkbox — that
switches the account number from its masked form to the raw stored value on
**both** surfaces that display it: the table cell and the edit form's field. The
reveal is session-scoped, is written to no store, and lapses back to masked after
`_REVEAL_SECONDS` without the user doing anything.

## 2. Problem

FIBR-0113 ships the Accounts table with the account number **always** masked:
`ui/accounts.py::_mask_account_number` renders `"•••• 7890"` in the cell, and the
form's `self._account_number` field is constructed in
`QLineEdit.EchoMode.Password` and never leaves it. That is the right default —
FIBR-0113 §3 decision 2 is defending against shoulder-surfing and screenshots —
but it is not a usable end state.

A user who needs the full number to pay someone has nowhere to get it. The value
is in the vault, encrypted at rest, and finbreak is the only thing that can
decrypt it — so "read it from the file instead" is not an escape hatch, it is a
dead end. FIBR-0113 §8 records "mask with no reveal" as a **rejected**
alternative for exactly this reason; this item is what makes that rejection true
rather than aspirational.

The last 4 characters the mask does show are enough to *disambiguate* two
accounts at the same bank, which is what FIBR-0113 §2 consequence 2 asked for.
They are not enough to *use* the number.

## 3. Scope decisions

Settled with the user on 2026-07-28 as decisions 4 and 5 of FIBR-0113's
pre-split draft, and travelled here with the reveal on 2026-07-30:

1. **The reveal is an explicit toggle over a default-masked value** — the
   masking itself, and the shoulder-surfing-and-screenshots reasoning behind it,
   are **FIBR-0113 §3 decision 2's**, which this spec cites rather than
   restates. What is decided here is only that the way back to the raw value is
   a control the user operates deliberately.
2. **Reveal is session-scoped**, never persisted — a reveal that survives a
   restart is a reveal the user did not ask for that day.
3. **A reveal auto-hides after `_REVEAL_SECONDS` (30).** Masking defends
   against someone seeing the screen; a reveal left on indefinitely gives that
   back the moment the user walks away. 30 seconds is taken from
   `services/auth.py::DEFAULT_CLIPBOARD_CLEAR_SECONDS` — the app's other
   "sensitive thing visible for a bounded time" control, recorded in
   `docs/security-model.md` T13 — so the two exposure windows match rather than
   each being invented. A fixed constant, not a setting: see §9.

## 4. Design

### 4.1 The toggle

A `QCheckBox` — `self._reveal`, labelled "Show account numbers" — sits on its own
row between the table and the form. It is constructed unchecked and its state is
never written to `QSettings`, to the vault settings, or anywhere else.

Reveal cannot outlive a lock without any extra code:
`main_window.py::MainWindow._lock()` locks the vault and then calls
`_clear_live()`, which drops every tab reference and `deleteLater()`s the
workspace (its INV-3), and `_build_workspace()` constructs a fresh
`AccountsWidget` on the next unlock — so the checkbox returns to unchecked. This
is a property to *test*, not to implement.

### 4.2 Reveal governs two surfaces

The **table cell** and the **form field** both display the account number, and an
implementation that reveals one and not the other satisfies decision 1 nowhere.
This section is this spec's single statement of that; INV-3 and INV-5 lock one
surface each, and §8 records why neither alone would do.

The two surfaces are masked by **different mechanisms**, because a
`QTableWidgetItem` has no echo mode:

- **The cell** is masked by text substitution — FIBR-0113's `_refresh()` writes
  `_mask_account_number(account.account_number)`. This item makes that write
  conditional: the raw `account.account_number` while the box is checked, the
  masked form while it is not (INV-5, amending FIBR-0113 INV-20).
- **The field** keeps the raw stored value in `text()` at all times and switches
  only its echo mode — `Password` when reveal is off, `Normal` when on (INV-3).
  It stays fully editable in both states, exactly like any password box (user,
  2026-07-28).

`_mask_account_number` is for the cell only and must **never** reach the form: an
Update would write `"•••• 7890"` back into the vault as the account number.

The field is constructed `Password` by FIBR-0113, and **`_on_reveal_toggled` is
the only thing that changes its echo mode** (§4.4 step 2). It is deliberately
*not* set from `_on_selection_changed`, which §4.4 step 5 suppresses across the
reveal re-selection and which therefore does not run on the one transition INV-3
governs.

### 4.3 The auto-hide timer

Checking the box starts a single-shot timer that re-masks on expiry:

```python
_REVEAL_SECONDS = 30

self._reveal_timer = QTimer(self)          # parented — dies with the widget
self._reveal_timer.setSingleShot(True)
self._reveal_timer.setInterval(_REVEAL_SECONDS * 1000)
self._reveal_timer.timeout.connect(self._on_reveal_timeout)
```

`ui/_clipboard.py::ClipboardAutoClear` is the precedent for *the shape of the
guard only* — a single-shot `QTimer` whose `timeout` is wired to a **named
method** rather than a lambda, which its docstring justifies as giving "the guard
exactly one implementation". Two deliberate differences: it calls `stop()` then
`start(seconds * 1000)` per use because its delay is settings-driven, where
`_REVEAL_SECONDS` is a constant set once via `setInterval`; and its `timeout`
goes straight to the guard, where this one goes to `_on_reveal_timeout`, which
only unchecks the box so the re-mask travels the same path as a manual uncheck.

The interval is restarted, not extended, on each fresh reveal, and a `_refresh()`
reached any other way does not touch the timer (INV-2).

The timer is a **convenience bound on exposure, not a security boundary** — a
revealed number is on screen for up to `_REVEAL_SECONDS` regardless, and anything
that can read the process's memory can read the value whether it is masked or
not.

**`_refresh()` gains a `VaultLockedError` guard around its service reads**, and
the timer is the whole reason it needs one. `MainWindow._lock()` locks the vault
*before* `_clear_live()` runs, and `_clear_live` deletes the workspace with
`deleteLater()`, so a timeout queued just before a lock can still reach
`_on_reveal_timeout` → `_on_reveal_toggled` → `_refresh()` while the vault is
shut (§6). `_refresh()` swallows it silently, as every `_on_*` handler in this
widget already does. The guard wraps **the reads only** — the
`list_accounts()` / `account_ids_with_pdf_password()` / `account_statuses()`
block — and returns before `self._rows`, `self._with_pw` or the table are
touched, leaving the previous render intact. A guard around the whole body would
let a lock land mid-fill and leave those three half-updated while §4.4's steps
5–6 run against them.

### 4.4 `_on_reveal_toggled`

`self._reveal.toggled` connects to `_on_reveal_toggled`, the one handler that
owns the transition. Its signature is **`@Slot(bool)`**: `QCheckBox.toggled`
carries a `bool`, and this module's convention of `@Slot()` on zero-argument
handlers would be a runtime `TypeError` here under PySide6.

Toggling repopulates the table, which under FIBR-0113's clear-then-fill drops the
current selection (its §3 decision 6), so this handler restores it — and the
order matters, because the selected id must be captured before `_refresh()`
replaces `self._rows`:

1. capture the currently selected account id (via
   `_table_state.selected_index` into `self._rows`), or `None`;
2. set `self._account_number.setEchoMode(...)` — `Normal` if the box just went
   on, `Password` if it went off (INV-3);
3. start the single-shot timer if it went on, stop it if it went off (INV-2);
4. call `_refresh()`, which rebuilds `self._rows` and the table, leaving no
   selection (FIBR-0113 INV-22);
5. if an id was captured, re-select it via `_select_account` **with
   `self._table.blockSignals(True)` around the call**, then unblock. Blocking
   suppresses `itemSelectionChanged`, so `_on_selection_changed` does not fire
   and cannot overwrite half-typed form input from storage (INV-4);
6. call `_apply_forget_gating()` — the one thing step 5 suppressed that still has
   to happen. It is FIBR-0113's gating-only helper (its §3 decision 7), so the
   Forget rule keeps one implementation rather than gaining a third.

`_select_account` is promoted to a production caller here: FIBR-0113 ships it
resolving an account id to a position in `self._rows` before calling
`select_by_index` (its INV-15), used only by tests until step 5 exists.

## 5. Invariants

- **INV-1** — A freshly constructed `AccountsWidget` has reveal off, the toggle
  state is written to no persistent store, and a lock cycle returns it to off.
  *Test:* `tests/features/accounts/test_accounts.py` — a `qtbot` test that (a)
  asserts the checkbox is unchecked on construction; (b) **parses** the window
  INI before and after toggling and asserts no key outside
  **`columns/accounts_table`** changed (a parse, not a byte compare — a byte
  compare cannot exclude a key, and `remember_columns` may legitimately write
  that one); and (c) drives `MainWindow._lock()` then a re-unlock and asserts the
  rebuilt tab's checkbox is unchecked. Leg (c) needs a `MainWindow`, not a bare
  widget — build one, `_enter_unlocked()`, toggle reveal on, `_lock()`,
  re-`unlock()` the service, `_enter_unlocked()` again. It is the only leg in
  this spec that does so (§7), and what it uniquely catches is `_clear_live` ever
  being changed to *reuse* the Accounts tab rather than rebuild it — which legs
  (a) and (b) cannot see.
  *Breaks when:* the toggle is persisted next to the column state in the window
  INI, so a machine left revealed stays revealed across a lock. Excluding the
  whole `columns/` **group** rather than the single `columns/accounts_table`
  **key** would let a flag persisted as `columns/accounts_reveal` pass the leg
  meant to fail on it. **Not covered:** persistence to the *vault* settings store
  (where `clipboard_clear_seconds` lives) — this leg observes the window INI
  only; §11 records that gap.

- **INV-2** — A reveal re-masks on its own after `_REVEAL_SECONDS`; switching it
  off by hand cancels the pending timer so it cannot fire across a later reveal;
  and a `_refresh()` from any other cause leaves the pending interval untouched
  rather than extending it.
  *Test:* `tests/features/accounts/test_accounts.py` — a `qtbot` test driving the
  widget's timer directly rather than waiting `_REVEAL_SECONDS` in real time,
  asserting each clause against a named observable:
  `self._reveal_timer.isSingleShot()` is `True`; after a manual uncheck
  `isActive()` is `False`; and `remainingTime()` is **non-increasing** across an
  unrelated `_refresh()` (an Add) rather than jumping back to the full interval.
  *Breaks when:* the timer is left repeating instead of single-shot, or is not
  stopped on a manual uncheck — a stale timer then re-masks a reveal the user
  started seconds ago, and the box appears to toggle itself. Or `_refresh()`
  restarts it, so editing accounts holds a reveal open indefinitely. Driving the
  timer alone observes none of the three: `isSingleShot` is what a repeating
  timer fails, and only `remainingTime()` can see an extension.

- **INV-3** — The edit form's account-number field is masked whenever reveal is
  off: its echo mode is `Password` with the toggle off and `Normal` with it on,
  and it stays editable in both states.
  *Test:* `tests/features/accounts/test_accounts.py` — select an account with a
  stored number; assert `echoMode()` is `Password` and that **`displayText()`**
  is masked while `text()` still returns the raw value (a `Password` field's
  `text()` is never masked — asserting on it would fail and invite weakening the
  leg); toggle reveal, assert `Normal` and that `displayText()` now equals
  `text()`; type in both states and assert the typed value reaches the service.
  *Breaks when:* only the table cell is revealed and the form field is left in
  `Password` — the user ticks the box, the cell shows the number, and the field
  they are about to copy from still shows dots. The mirror failure (the field
  revealed and the cell not) is INV-5's.

- **INV-4** — Toggling reveal preserves the user's in-progress edit: the selected
  account stays selected, the four form inputs keep whatever the user had typed,
  and the Forget button's enabled state is unchanged.
  *Test:* `tests/features/accounts/test_accounts.py` — select an account, type
  new text into the name and note fields without saving, toggle reveal on and
  off, and assert the selection, all four inputs and the Forget button are as
  they were.
  *Breaks when:* `_on_reveal_toggled` re-selects without blocking the table's
  signals (§4.4 step 5), so `_on_selection_changed` fires and repopulates every
  field from storage — silently discarding what the user was typing. The reveal
  toggle is the one control a user is likely to reach for *mid-edit*, which is
  what makes this reachable rather than theoretical.

- **INV-5** — The Account-number **column** renders the raw stored value while
  reveal is on and returns to `_mask_account_number(account.account_number)` when
  it goes off, for every row.
  *Test:* `tests/features/accounts/test_accounts.py` — two accounts, one with a
  10-character number and one with none; with reveal off assert the column's
  `item.text()` is `"•••• 7890"` and `""` (FIBR-0113 INV-20's state), toggle
  reveal on and assert the first is now the full raw value and the second still
  `""`, toggle off and assert it is masked again.
  *Breaks when:* the fill keeps calling `_mask_account_number` unconditionally,
  so the checkbox changes nothing on the surface the user is looking at — the
  whole of §1. INV-3 does not catch it: the form field would still switch echo
  mode, so a user with a row selected would see the number and conclude the
  feature works.

## 6. Failure modes

- **The auto-hide timer fires around a lock.** The timer is parented to the
  widget, so the widget's destruction takes it down — but `_clear_live` uses
  `deleteLater()`, a *deferred* delete, and `_lock()` locks the vault **before**
  it. So an already-queued timeout can still reach `_on_reveal_timeout` →
  `_on_reveal_toggled` → `_refresh()`, which reads the now-locked vault. §4.3's
  guard is the narrow reason `_refresh()` needs one. §4.1's "reveal cannot
  outlive a lock without any extra code" is about the *checkbox state*, which is
  still true — the guard is about the timeout that can land between the vault
  locking and the widget being deleted.
- **A `_refresh()` while revealed** — triggered by Add, Update, Delete, Forget,
  the reveal toggle itself, or `MainWindow._refresh_tab` on every activation of
  the Accounts tab — re-renders unmasked and does **not** restart the timer, so
  neither editing accounts nor switching tabs can extend the exposure window
  (INV-2).
- **Sorting the Account-number column across a toggle.** That column sorts by
  whatever is displayed — the last 4 while masked, the full value while revealed
  — so toggling reveal can reorder a live sort on it. Accepted and noted rather
  than fixed; sorting a masked column can only ever expose what the mask exposes.
- **A revealed number widens the column.** Masked display is bounded at 9
  characters; a revealed one is not, and the column is user-resizable and
  remembered (FIBR-0113 INV-17), so this is the user's to size.
- **Reveal on, then the tab is left.** `MainWindow._refresh_tab` re-renders on
  the next activation, still revealed, with the timer still running from when the
  box was ticked — so the exposure window is measured from the reveal, not from
  the last look at the tab. That is the intent of decision 3, recorded here so it
  reads as chosen rather than overlooked.

## 7. Tests

Every leg lands in `tests/features/accounts/test_accounts.py`, alongside
FIBR-0113's. There is no new test file and no new fixture directory.

The legs are `qtbot` widget tests over a constructed `AccountsWidget`: reveal
default and non-persistence (INV-1), the auto-hide timer's three clauses (INV-2),
the form field's echo mode (INV-3), the mid-edit preservation guarantee (INV-4),
and the cell's two rendered states (INV-5).

Per `docs/standards/testing.md`, each is run against pre-implementation source
and seen to fail before the implementation is written. `test_accounts.py` exists
and will by then carry FIBR-0113's legs, so this is a real check rather than a
formality: each leg is added, run against the always-masked widget FIBR-0113
ships, and seen to fail before the toggle is written.

`tests/features/accounts/spec.md` gains a `## FIBR-0198 — …` INV block with
`Source:` lines, following the per-item convention **FIBR-0113 §7 owns and
states in full** (four blocks now share that file).

The `qtbot` legs assert behaviour on a constructed widget; they do **not** prove
the tab renders correctly inside `MainWindow`. The one exception is INV-1 leg
(c), which builds a `MainWindow` solely to drive a lock cycle — it still asserts
nothing about rendering.

## 8. Alternatives considered (and rejected)

- **Show account numbers in full, with no mask.** Rejected by the user — see §3
  decision 1. This is the alternative the whole item exists to avoid; it is
  restated here because "add a reveal" and "stop masking" look similar from
  outside and are opposite decisions.
- **Reveal the cell only, leaving the form field in `Password`.** Rejected: the
  form is where a user selects and copies the number, so a reveal that does not
  reach it does not do the job §2 describes. INV-3 locks it.
- **Reveal the form field only, leaving the cell masked.** Rejected: the field
  shows one account, and a user comparing two accounts at the same bank is
  looking at the column. INV-5 locks it.
- **Persist the toggle**, so a user who works revealed does not re-tick it each
  session. Rejected — see §3 decision 2.
- **No auto-hide; the user unticks when done.** Rejected — see §3 decision 3. It
  is the walk-away case that decision 1 is defending against, and it is the one
  case the user cannot untick for.
- **A per-row reveal (an eye button in each Account-number cell)** rather than
  one toggle for the column. Rejected: it narrows the exposure to one row, but a
  `QTableWidgetItem` cannot host a button, so each row would need
  `setCellWidget` — which breaks `_table_state`'s sort and fill contract that
  FIBR-0113 INV-18 and INV-22 depend on. Cost out of proportion to the gain.
- **Extending the timer on activity in the tab**, so an in-progress edit is not
  interrupted by a re-mask. Rejected: it makes the exposure window unbounded in
  exactly the session where someone is at the keyboard, and INV-2's third clause
  is written to forbid it. The user can re-tick the box, which restarts the full
  interval.

## 9. Out of scope

- **The table, the mask helper and the account-number form field** — all
  FIBR-0113's, this spec's blocker.
- **The storage of the value being revealed** — FIBR-0193's.
- Making `_REVEAL_SECONDS` user-configurable, as the clipboard auto-clear delay
  already is. **A decision, not a deferral — no follow-up id.** One fixed
  constant is the shortest correct form of what was asked for, and a settings key
  nobody has asked to change is scaffolding. If it is ever wanted it follows the
  existing `clipboard_clear_seconds` pattern exactly.
- A reveal that survives a lock or a restart — §3 decision 2 rules it out
  permanently; no follow-up id.
- Live language switching for the checkbox label — tracked by FIBR-0017 (P12
  i18n). This is a standing **departure from `coding.md` §5.2**, which asks for
  `changeEvent` / `retranslateUi`: no file under `src/finbreak` has either today,
  so every `tr()` string is bound at construction and the label added here
  inherits that.

## 10. Resource cost

No new external dependency, no new module, no new build target. One `QCheckBox`
and one `QTimer` per `AccountsWidget`, both parented to it.

One cost is **unattended** and so worth naming: every reveal toggle *and* every
auto-hide runs a full `_refresh()`, which is `list_accounts()` +
`account_ids_with_pdf_password()` + `ReconciliationService.account_statuses()` (a
statement-period walk per account) + the money-display reads. That is the same
work a tab activation already does, on a table of one row per account, so it is
accepted rather than optimised into a column-only re-render — but it fires on a
timer rather than on a user action, which is why it is recorded here.
