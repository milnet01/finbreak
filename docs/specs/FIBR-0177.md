# FIBR-0177 — Account-level balance reconciliation

**Status:** DRAFT — pre-cold-eyes.
**Kind:** feature.
**Roadmap:** FIBR-0177 (features-accessibility).
**Depends on:** FIBR-0171 (persisted `statement_periods.closing_balance_minor`,
schema v11) · FIBR-0050 (Standard Bank parser, import-time reconciliation) ·
FIBR-0007 (canonical signed `amount_minor`).

---

## 1. Summary

Give every **cash account** an ongoing, at-a-glance health check: *do the
imported transactions add up to the balance the bank actually stated?* Today the
only reconciliation is a **silent hard gate inside the Standard Bank PDF parser**
(`_verify_checksum` raises `ValueError` and aborts the whole import) — there is no
persistent, visible, per-account "✓ / off by R-X" indicator, and it only runs at
Standard-Bank import time.

This feature generalises that check into a **bank-agnostic, persisted-data**
reconciliation: for each account, walk its statement **closing balances** (now
persisted by FIBR-0171) in date order, and confirm the transactions between each
consecutive pair bridge one closing balance to the next. A gap (a missed import,
a missing period) shows as a discrepancy. The result surfaces as a per-account
marker on the **Accounts** tab, mirroring the existing "🔑 statement password
saved" suffix.

**No new stored balance is invented.** The check is built entirely from data the
app already holds: persisted closing balances + the signed `amount_minor` sums the
transactions repository already computes. **No schema change.**

### The reconciliation identity

For two consecutive balance-bearing statements of one account — closing `C_prev`
as-of date `P_prev`, and closing `C_curr` as-of `P_curr` (`P_prev ≤ P_curr`) — the
transactions dated in the **half-open window `(P_prev, P_curr]`** must bridge them:

```
C_curr  ==  C_prev  +  Σ amount_minor  for occurred_on ∈ (P_prev, P_curr]
```

The sum is exactly `TransactionRepository.sum_after(account_id, P_prev, P_curr)`
(the half-open primitive FIBR-0171 introduced). The window is half-open because a
transaction dated **on** `P_prev` is already inside `C_prev`, and one dated **on**
`P_curr` is inside `C_curr` (INV-2). An account **reconciles** iff *every*
consecutive pair satisfies this identity **exactly** (integer minor units, no
tolerance — matching the SB parser's exact `abs(reconciled) != abs(closing)` gate).

## 2. Design decisions

### D1 — v1 scope: **current + savings accounts only**

The persisted `closing_balance_minor` is stored **as the statement printed it**
(`standard_bank._capture_closing` → `_signed_balance`, the trailing-`-` sign only).
For the different account types that printed convention is **not** uniform:

- **Asset cash accounts** (`current`, `savings`): the printed closing is a
  canonical balance (positive = money you have), the **same convention** as the
  canonical `amount_minor` (debit −, credit +; FIBR-0007). So the identity above
  (`C_prev + Σ`) holds directly.
- **Debt products** (`credit_card`, `home_loan`, `personal_loan`): the printed
  closing is the **amount owed** (positive = debt) — the *opposite* convention.
  This is precisely why `standard_bank._verify_checksum` reconciles Family C
  (credit card) with `opening − total`, not `+`. Applying the asset identity here
  would misreconcile by `2·Σ`.
- **Investment** (`investment`): the balance moves with the **market**, not only
  with transactions, so `C_prev + Σ transactions` legitimately ≠ `C_curr`. Not a
  reconciliation target.
- **`other`**: a grab-bag whose sign/semantics are unknown; excluded to avoid
  false "off" warnings.

v1 therefore reconciles **only `current` and `savings`** — the cash accounts where
transactions fully and canonically determine the balance. Every other type gets a
quiet `NOT_SUPPORTED` status (no marker), and its reconciliation is deferred to v2
(see §6). Rationale: in a money app a **false** "off by R-X" is worse than a
missing check; v1 ships zero false alarms for the common case. (INV-5.)

### D2 — Cross-statement telescoping, exact, over persisted closings

Reconciliation is between **consecutive persisted closing balances**, not against a
per-statement opening balance (no opening balance is persisted anywhere — only the
transient SB parser local, discarded). This is the account-level generalisation of
the SB check: statement N's "opening" is statement N−1's "closing". Comparison is
**exact** on integer minor units — no epsilon anywhere in the codebase, and money
is never silently rounded (FIBR-0007). (INV-1, INV-6.)

### D3 — The statement chain

Per account, the chain is the statement periods whose `closing_balance_minor IS NOT
NULL`, ordered by **`(period_end, id)` ascending** (the balance *date*, tie-broken
by insert order — the same ordering `latest_closing_balances` tie-breaks on).
Statements without a closing balance (CSV / manual imports) are **not** chain
nodes, but their transactions still count inside a bridge window (D5). A new
repository method `closing_balances_for_account(account_id)` returns
`[(period_end, closing_balance_minor), …]` — a sibling of the existing
`latest_closing_balances`. (INV-3.)

### D4 — Status taxonomy

`ReconciliationStatus` (StrEnum):

- **`RECONCILED`** — asset account, ≥2 balance-bearing statements, *every*
  consecutive pair satisfies the identity exactly.
- **`OFF`** — asset account, ≥2 balance-bearing statements, ≥1 pair fails.
- **`NOT_ENOUGH_DATA`** — asset account with **fewer than two** balance-bearing
  statements (nothing to bridge). Never an error. (INV-4.)
- **`NOT_SUPPORTED`** — account type ∉ {`current`, `savings`} (D1). No chain built.

### D5 — Rollup fields (money-safe, integer minor units)

The pure core returns an `AccountReconciliation`:

- `discrepancy_minor: int` — signed **net** `Σ (actual − expected)` over all pairs
  (0 when reconciled).
- `off_pair_count: int` — number of pairs whose `(actual − expected) ≠ 0`.
- `checked_pair_count: int` — number of consecutive pairs examined (= nodes − 1).

**Honesty rule:** status is `RECONCILED` iff *every* per-pair diff is exactly 0 —
**not** iff the net is 0. Two offsetting gaps (net 0, `off_pair_count == 2`) are
`OFF`, never falsely reconciled. (INV-7, INV-12.)

A bridge window that **misses** an entirely un-imported intervening period yields a
non-zero diff → `OFF` — this *is* the "catch import gaps" guarantee (INV-10). A
bridge legitimately sums transactions imported by **any** source (CSV between two
SB/OFX statements is counted) → reconciliation validates across mixed import
sources (INV-11).

### D6 — Surface: Accounts-tab per-account marker

The result surfaces exactly where the analogous per-account flag already lives:
`ui/accounts.py::_refresh` appends a translated suffix to each account row. This
feature adds a reconciliation suffix from `ReconciliationService.account_statuses()`
(a `dict[int, AccountReconciliation]`, mirroring `account_ids_with_pdf_password`):

- `RECONCILED` → `·  ✓ balances reconcile`
- `OFF`, `off_pair_count == 1` → `·  ⚠ off by R{|discrepancy|}`
- `OFF`, `off_pair_count > 1` → `·  ⚠ {n} periods don't reconcile`
- `NOT_ENOUGH_DATA` / `NOT_SUPPORTED` → **no marker** (quiet, like an account with
  no saved password).

Money is formatted through the existing display path (`to_display_decimal` + the
`ui/_amount.py` helper); the "off by" figure is a **magnitude**. The read is
`VaultLockedError`-silent (INV-9). A precise **per-statement** "which period is off"
column on the Statements tab is a deliberate v2 follow-up (§6), not v1 — v1 is the
at-a-glance account health tick the roadmap's layman line promises.

### D7 — No schema change

Everything reuses FIBR-0171's v11 `closing_balance_minor` column and the existing
`sum_after` primitive. **`LATEST_SCHEMA_VERSION` stays 11**; no `_migrate_to_v12`;
the repo-wide `== 11` drift-guard assertions are **untouched** (INV-8). This is a
read-only analytics feature over already-persisted data.

### D8 — Layering: pure core + thin service (mirrors FIBR-0171)

- **Pure** `reconcile_account(account_id, closings, bridge_sums) ->
  AccountReconciliation` — clock-free, I/O-free, **no `Decimal`**, signed integer
  minor units only. `closings` is the ordered `[(period_end, closing_minor)]`;
  `bridge_sums[i]` is `Σ amount_minor` over the window between node `i` and `i+1`.
  Testable in isolation exactly like `project_forecast`.
- **`ReconciliationService(vault)`** composes it: lists accounts, gates type (D1),
  fetches the chain (`closing_balances_for_account`) and the bridges
  (`sum_after` per gap), and calls the pure core. Vault-scoped, mirrors
  `ForecastService` / `RecurringService`.

### D9 — Out-of-scope finding logged, not fixed (stay-in-lane, §11)

Investigating D1 surfaced a **pre-existing latent bug in FIBR-0171's forecast
anchor**: `ForecastService._anchor` sums `latest_closing_balances()` across **all**
account types with `current = balance_minor + roll_minor` (a plain `+`). For a debt
account the persisted closing is in **owed** convention (D1), so `+ roll` moves the
anchor the wrong direction — and it also folds an "owed" figure into a vault-wide
"cash" total as if it were an asset. This is reachable (a credit-card account with a
balance-bearing statement contributes to the anchor). It is **out of FIBR-0177's
lane** — logged as a separate planned `fix` on the ROADMAP (verify-first when
picked up), **not** touched here.

## 3. New / changed models

```python
# models.py
class ReconciliationStatus(StrEnum):
    RECONCILED = "reconciled"
    OFF = "off"
    NOT_ENOUGH_DATA = "not_enough_data"
    NOT_SUPPORTED = "not_supported"

@dataclass
class AccountReconciliation:
    account_id: int
    status: ReconciliationStatus
    discrepancy_minor: int      # signed net Σ(actual − expected); 0 when reconciled
    off_pair_count: int         # pairs with a non-zero diff
    checked_pair_count: int     # consecutive pairs examined (= nodes − 1)
```

Field order pinned (the repo convention: dataclass field order == SELECT column
order where persisted; this one is computed, never stored).

1. **`models.py`** — `ReconciliationStatus` + `AccountReconciliation` (above).
2. **`repositories/statement_periods.py`** — `closing_balances_for_account(
   account_id) -> list[tuple[str, int]]`: `(period_end, closing_balance_minor)` for

   -silent; a small formatting helper for the "off by" magnitude.
5. **`tests/features/reconciliation/`** — `spec.md` + pure-core tests + service
   tests (in-memory vault) + a UI marker test.

## 6. Known limitations (documented, honest)

- **Debt & investment accounts not reconciled in v1** (D1). Credit-card / home-loan
  / personal-loan need the owed-convention identity (`C_prev − bridge`); investment
  needs market-aware handling. Deferred to a v2 roadmap item.
- **Per-account rollup, not per-statement location.** v1 says *whether* an account
  reconciles and by how much; it does not yet point at *which* statement/period is
  off. A per-statement Statements-tab column (which pairs naturally with FIBR-0038
  coverage/gap detection) is the v2 follow-up.
- **CSV-only accounts** (no closing balance ever persisted) → `NOT_ENOUGH_DATA`.
  FIBR-0178(a)/(d) (a manual balance override, a CSV balance-column mapping) would
  let them contribute; out of scope here.
- **Overlapping coverage is fine.** The chain is by balance *date* (`period_end`),
  not coverage span; two statements whose spans overlap still bridge correctly as
  long as transactions aren't double-imported (INV-6 span/cross-source dedup already
  guarantees that). Two statements with the **same** `period_end` but different
  closings reconcile only if those closings are equal (an empty `(P, P]` bridge) —
  which correctly flags a genuine same-date balance disagreement as `OFF`.

## 7. Test plan (`tests/features/reconciliation/`)

**Pure core** (`test_reconcile.py`, no DB, no Qt):
- INV-1: three ascending closings bridged exactly by their sums → `RECONCILED`.
- INV-4: 0 and 1 closings → `NOT_ENOUGH_DATA`; empty never raises.
- INV-6: all-integer, exact — a 1-minor-unit gap → `OFF` (no epsilon swallow).
- INV-7: `discrepancy_minor` / `off_pair_count` / `checked_pair_count` values on a
  mixed reconciled/off chain.
- INV-12: `[+100 gap, −100 gap]` → net 0 but `off_pair_count == 2` → `OFF`.

**Service** (`test_reconciliation_service.py`, in-memory SQLCipher vault):
- INV-1/INV-2: a `current` account with two statements + bridging transactions
  (incl. boundary rows on `P_prev` and `P_curr`) → `RECONCILED`; a boundary-row
  mis-placement falsifier.
- INV-5: a `credit_card` (and a `home_loan`) account → `NOT_SUPPORTED`, regardless
  of its data.
- INV-3: a statement with `NULL` closing (CSV import) is skipped as a node but its
  txns still count in the surrounding bridge.
- INV-10: drop an intervening period's transactions → `OFF` with the right
  `discrepancy_minor`.
- INV-11: CSV transactions between two balance-bearing statements are summed in.
- INV-4: a `savings` account with a single balance-bearing statement →
  `NOT_ENOUGH_DATA`.

**Migration guard** (`test_no_schema_change.py`):
- INV-8: `LATEST_SCHEMA_VERSION == 11`; `12 not in _MIGRATIONS`.

**UI** (`test_reconciliation_marker.py`, `qtbot`):
- INV-9: each status renders the right suffix (or none); the read is
  `VaultLockedError`-silent (no crash on a locked vault).

Reproduce-first: the pure-core INV-1/INV-12 and the service INV-10 gap test are
written **RED** first (feature absent) and drive the implementation.
