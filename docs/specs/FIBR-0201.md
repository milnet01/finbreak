# FIBR-0201 + FIBR-0202 — Multi-select bulk actions on the Transfers and Statements tabs

**Status:** DRAFT — pre-cold-eyes (2026-08-02).
**Kind:** feature.
**Covers:** **FIBR-0201** (bulk-confirm suggested transfers) and **FIBR-0202**
(bulk-delete statements + a Delete all button). One umbrella spec, per
`spec-format.md` §2: both items independently derived the same design — widen a
`SingleSelection` table, resolve ticked rows to domain ids *before* mutating,
and decide a transaction boundary — and specifying them apart risks two
different answers to one question. FIBR-0202's delete-preview trap (§4.4) is the
part that is genuinely its own.
**Source:** ROADMAP FIBR-0201 + FIBR-0202, both `user-request-2026-08-02`.
**Depends on:** FIBR-0117 (`ui/_table_state.py`, the tag/selection seam),
FIBR-0148 (the hand-off delete this batches), FIBR-0149 (the delete-preview
wording this must keep truthful), FIBR-0113 (the re-sort selection hazard).

**Layman:** Two tabs make you click one row at a time. On Transfers you can
accept one suggestion or all of them, with nothing in between — so trusting
eight of twelve means eight clicks. On Statements you delete one import per
click, with no way to clear the lot. This lets you tick several and act on them
together, and adds a Delete all button. The important part is the warning
message: when you delete several statements at once, the current per-statement
wording would tell you **nothing** will be permanently removed while it in fact
destroys transactions (measured — §4.4).

**Contents:** Goal · Problem · Scope decisions · Design (**§4.4 is the
money-critical section**) · Invariants (INV-1..INV-11) · Failure modes · Tests ·
Alternatives rejected · Out of scope · Resource cost · What checks this ·
Cross-doc impact · Cold-eyes loop log.

## 1. Goal

A user who trusts eight of twelve suggested transfers confirms those eight in
one click, and a user cleaning up a bad import run deletes the statements
involved in one action — with a confirmation message that states truthfully what
the batch will destroy.

Nothing about the single-row path changes. `Confirm all` stays. A single delete
keeps its shipped wording and its shipped semantics.

---

## 2. Problem

Both tabs offer one speed, and both refuse a plural selection at the widget
level rather than merely failing to wire one up.

**Transfers** (`ui/transfers.py`): `TransfersWidget._on_confirm` confirms the one
selected candidate; `TransfersWidget._on_confirm_all` confirms every candidate
the detector produced. There is nothing between one and all.

**Statements** (`ui/statements.py`): `StatementsWidget._on_delete` deletes the
one selected statement behind a confirm box. Clearing a bad import run of N
statements means N confirm dialogs, and there is no Delete all.

Three facts grounded against the source, not recalled:

1. **Both tables set `SelectionMode.SingleSelection`.** Seven source files set
   it — `grep -rn "SelectionMode.SingleSelection" src/ | wc -l` → 7 (rules,
   forecast, recurring, statements, accounts, transactions, transfers). Exactly
   two of those are in scope here.

2. **`selected_index` is single-row by construction.** It returns `None` unless
   exactly one row is selected (`ui/_table_state.py`, `selected_index`), and it
   has five UI consumers — `grep -rn "selected_index(" src/ | sed 's/:.*//' |
   sort -u` → `accounts.py`, `recurring.py`, `statements.py`, `transactions.py`,
   `transfers.py`, plus its own definition. So it cannot be widened in place;
   this spec adds a sibling. `selected_index`'s own contract and body are
   untouched, and it keeps callers in both changed files — `_on_reassign`
   (statements) and `_on_unlink` (transfers) stay single-row.

3. **Both tables re-sort on refresh.** `enable_sorting` and `remember_columns`
   are live on both, so a mutation followed by `_refresh()` / `refresh()`
   repopulates and re-sorts. The FIBR-0113 finding applies: a selection held
   across a re-sort can ride its item onto a different row.

### 2.1 The measured trap in a bulk delete

`StatementService.delete_preview` answers *per statement*, and its coverage test
is "does a **remaining** statement of the same account also cover this row?" —
`q.id <> :pid` in `TransactionRepository.delete_split_counts`. During a bulk
delete the other statements in the batch are not remaining, but that query still
counts them as though they were.

Measured 2026-08-02 (probe kept at
`scratchpad/fibr0202-design-probe.py`; three statements on one account — A
covers Jan, B covers Jan–Feb, C covers Feb — and three transactions, deleting
`{A, B}`):

```
before: [('r1', A), ('r2', B), ('r3', A)]
up-front per-call previews: A=(0, 2) B=(0, 1)   summed removed=0 kept=3
batch-aware preview:                            removed=2 kept=1
loop A-then-B: returned 0 + 2 = 2 deleted
after loop:  [('r2', C)]
after loop (B-then-A order): [('r2', C)]
```

Two conclusions, and the second **corrects the ROADMAP bullet**:

- **The confirm message is the defect.** Summing per-statement previews reports
  `removed=0` — "none of these will be permanently removed, they are shared with
  an overlapping statement and will stay" — for an action that in fact destroys
  two transactions irreversibly. This is the money-critical part of the item.
- **The surviving data is NOT order-sensitive.** FIBR-0202's bullet says
  "deleting A then B is not the same as deleting {A,B} as a set". For the
  *reported counts and preview*, true. For the *data*, false as measured: both
  loop orders end identically, and identically to the batch semantics. The
  hand-off re-evaluates on every call, so a row handed to a statement that is
  itself about to be deleted is simply re-evaluated when that one goes; coverage
  by a doomed statement never persists. The bullet's framing of this as "the
  real hazard" is therefore withdrawn here, and the real hazard named above
  takes its place.

That leaves atomicity — not data correctness — as the argument for one
transaction over a loop (§4.5).

## 3. Scope decisions

| # | Decision | Who / why |
|---|---|---|
| D1 | **One umbrella spec, two roadmap ids.** | `spec-format.md` §2; the shared design is the reason the user grouped them (2026-08-02). |
| D2 | **Only two tables widen**: `transfers_suggested` and `statements_table`. `transfers_confirmed` stays single-select. | The items name these two. `transfers_confirmed`'s Unlink is untouched — see §9. |
| D3 | **Reject goes plural too.** | Once the suggested table takes a plural selection, a Reject that silently acts on one of five ticked rows is a worse outcome than supporting it. Same resolve-before-mutate shape, no consumption hazard. |
| D4 | **Bulk confirm reuses `confirm_all`'s existing semantics** — per-decision commits plus a consumed-set — rather than inventing a batch transaction. | `coding.md`/global rule 3(b): `confirm_all` already solves this exact problem. Changing its transaction boundary is a change to shipped behaviour that this item did not ask for. |
| D5 | **Bulk delete IS one owned transaction.** | Not for data correctness (§2.1 measured that a loop converges to the same data) but for atomicity: a failure part-way through a loop leaves a partly-deleted set with no rollback, against a `delete_statement` whose whole contract is atomicity. |
| D6 | **Delete all is the same operation with the selection implied**, not a second code path. | §4.6 — it falls out of the survivor-set predicate with no special case. |
| D7 | **Delete all keeps the existing `QMessageBox.question` confirm**, with wording that states the loss is total — no typed-`DELETE` gate. | The typed gate (FIBR-0030 `StartOverDialog`) is reserved for destroying the whole vault. Proportionate; recorded in §8 as the rejected alternative. |

## 4. Design

### 4.1 The shared seam: `selected_indexes`

Add to `ui/_table_state.py`, beside `selected_index`:

```python
def selected_indexes(table: QTableWidget) -> list[int]:
    """The parallel-list indexes of every selected row, ascending — read from each
    row's tag, so they stay correct after the user re-sorts. Empty when nothing is
    selected. The plural sibling of ``selected_index``, which is deliberately
    single-row (it returns None for a plural selection) and has five callers."""
```

`selected_index` is **not** changed: five UI files depend on its single-row
contract (§2 fact 2).

### 4.2 Resolve before mutating

Every bulk slot resolves the ticked rows to **domain ids** before the first
mutation, and iterates that resolved list:

```python
pairs = [(self._candidates[i].debit.id, self._candidates[i].credit.id)
         for i in selected_indexes(self._suggested)]
```

Never `self._candidates[i]` mid-loop. `_refresh()` rebuilds and re-sorts
`_candidates`, so an index resolved before the mutation and dereferenced after it
can name a different pair (FIBR-0113). The same rule gives statement ids on the
other tab.

### 4.3 Transfers: `confirm_many`, and `confirm_all` becomes its caller

`TransferDetectionService` grows:

```python
def confirm_many(self, pairs: Sequence[tuple[int, int]]) -> int:
    """Confirm each pair in order, skipping any whose debit or credit an earlier
    confirm in this pass consumed; returns the count committed."""

def confirm_all(self) -> int:
    return self.confirm_many(self._transfers().candidate_pairs())
```

The consumed-set logic **moves** into `confirm_many` rather than being copied —
it is `confirm_all`'s body today, and the hazard it guards is not specific to
"all": a user can equally tick two suggestions that share a transaction, and
`_record`'s guard would raise `ValueError` on the second (`_record` raises when
either transaction is already in a confirmed pair). `confirm_many` skips it
instead, exactly as `confirm_all` does, so a bulk confirm never raises at the
user.

`reject_many(pairs) -> int` is added alongside for D3. Rejection consumes
nothing, so it is a plain loop over the existing `_record(..., REJECTED)`; it
lives in the service rather than the widget because the widget never contains
decision logic in this codebase.

### 4.4 Statements: the survivor set — the money-critical change

Both queries in `TransactionRepository` key their coverage test on `q.id <> :pid`
— "any statement other than this one". A batch has to ask "any statement not in
this batch". Both take the batch:

```python
def hand_off_covered(self, statement_period_id: int,
                     deleting: Sequence[int] | None = None) -> int
def delete_split_counts(self, statement_period_ids: Sequence[int],
                        deleting: Sequence[int] | None = None) -> tuple[int, int]
```

`deleting` defaults to the single id, so **today's behaviour is the batch-of-one
case** and no existing caller changes meaning. The predicate becomes
`q.id NOT IN (<deleting>)`.

FIBR-0149's invariant must survive the widening: `delete_split_counts`' `EXISTS`
/ `NOT EXISTS` arms and `hand_off_covered`'s `EXISTS` guard share the coverage
sub-query **byte-for-byte** today, which is what makes the preview unable to
disagree with the delete it describes. The batch form keeps them identical
(INV-7) — the parameter list is what changes, not the predicate.

`StatementService` then grows:

```python
def delete_statements(self, period_ids: Sequence[int]) -> int   # one owned transaction
def delete_preview_many(self, period_ids: Sequence[int]) -> tuple[int, int]
def delete_statement(self, period_id: int) -> int               # unchanged signature
    return self.delete_statements((period_id,))
```

### 4.5 One transaction, and what it buys

`delete_statements` runs one `owned_transaction`: for each id, hand off (against
the survivor set) and delete its orphan rows; then delete the period rows. A
failure anywhere rolls the whole batch back to a re-openable vault, which is the
property a loop of `delete_statement` calls cannot offer (D5). It is **not**
claimed to change what survives — §2.1 measured that it does not, and INV-11
pins that equivalence so a future change to the batch form cannot quietly alter
it.

### 4.6 The aggregate confirm message, and Delete all

One message, from one `delete_preview_many(ids)` call over the whole batch —
never N per-statement previews summed (§2.1). The two shapes mirror today's
wording, with the statement count added:

- `kept > 0`: "Delete %n statement(s)? *R* of their transactions will be
  permanently removed — the rest are shared with an overlapping statement that
  is staying, and will stay. This cannot be undone."
- `kept == 0`: "Delete %n statement(s) and their *R* transactions? This cannot
  be undone."

**Delete all** passes every listed statement id to the same two functions. With
the exclusion set covering every statement, the `EXISTS` guard can never find a
survivor, so `kept` is necessarily 0 and every stamped row is removed — the
`kept == 0` wording is reached with no special case (INV-9). That is also the
case where the loss is total, which is why the second wording says so plainly.

### 4.7 Buttons and enablement

`_on_selection_changed` enables on a non-empty selection
(`bool(selected_indexes(...))`) rather than on `is not None`. `Delete all` is
enabled whenever any statement is listed, mirroring `Confirm all`'s
`bool(self._candidates)`. The Transfers status line already pluralises
(`tr("Confirmed %n transfer(s).", "", n)`); `tr("Rejected.")` becomes the
pluralised form.

## 5. Invariants

| ID | Invariant | What breaks it |
|---|---|---|
| INV-1 | `transfers_suggested` accepts a multi-row selection; `transfers_confirmed` does **not**. | Editing the `setSelectionMode` line in `_make_table`, which both tables share — the one-line fix that silently widens Unlink too. |
| INV-2 | `statements_table` accepts a multi-row selection, and `Delete selected` acts on every ticked row. | Widening the table but leaving `_on_delete` reading `_selected_row()`, which returns `None` for a plural selection — the button would go dead exactly when it is most useful. |
| INV-3 | Every bulk slot resolves ticked rows to domain ids **before** the first mutation. | Dereferencing `self._candidates[i]` / `self._rows[i]` inside the loop, after a refresh has re-sorted them (FIBR-0113). |
| INV-4 | `confirm_many` is consumption-safe: given two ticked candidates sharing a transaction, exactly one is confirmed, the count is 1, and no `ValueError` reaches the user. | Looping `confirm()` in the widget — `_record` raises on the second pair. |
| INV-5 | `confirm_all()` and `confirm_many(candidate_pairs())` are the same call; `confirm_all`'s shipped behaviour and count are unchanged. | Copying the consumed-set logic into `confirm_many` instead of moving it, leaving two implementations to drift. |
| INV-6 | A bulk delete's confirm message is computed from **one** batch-aware preview, never from summed per-statement previews. | The §2.1 measurement: summing says `removed=0` where the truth is 2 — a dialog that promises nothing is destroyed, then destroys. |
| INV-7 | The batch preview's coverage sub-query and the batch hand-off's `EXISTS` guard remain byte-for-byte identical. | Widening one to `NOT IN` and not the other, so the preview describes a delete that no longer matches it (FIBR-0149's invariant, carried forward). |
| INV-8 | A bulk delete is one owned transaction: a failure part-way leaves **no** statement deleted and the vault re-openable. | Looping `delete_statement`, each with its own commit. |
| INV-9 | Delete all reaches the `kept == 0` wording with no special case, because every statement is in the exclusion set. | Special-casing Delete all to skip the preview, or excluding only the "selected" ones. |
| INV-10 | `delete_statement(pid)` keeps its signature, its return value and its semantics — the batch-of-one case. | Changing the default of `deleting`, which would alter every existing caller (9 references in `src/`, 2 test files). |
| INV-11 | For any batch, the surviving transactions and their statement stamps match what today's per-call loop produces. | A batch hand-off that picks a different covering statement, or hands a row to a statement inside the batch. |

## 6. Failure modes

- **A vault lock mid-batch.** Every slot already catches `VaultLockedError` and
  returns; with a batch the catch must wrap the whole call, not each iteration,
  or a lock half-way leaves the status line reporting a count that did not land.
- **A ticked row that vanished.** Not reachable: resolution and mutation happen
  in one synchronous slot with no event-loop turn between them.
- **An empty selection.** Both bulk slots return early on an empty resolved list,
  as the single-row slots do on `None`.
- **A batch spanning accounts.** The coverage predicate is per-account
  (`q.account_id = transactions.account_id`), so statements on different accounts
  cannot affect each other's hand-off. No special handling.

  (INV-9).

Per `testing.md`, each leg is written red first. INV-3's leg must apply a sort
that actually reorders the rows, or it passes against an implementation that
indexes as it goes.

## 8. Alternatives considered (and rejected)

- **Widen `selected_index` to return a list.** Five call sites would need
  updating for a behaviour none of them wants; the single-row contract is what
  four of the five tabs rely on.
- **One transaction for bulk confirm (a `confirm_many` that owns a `BEGIN`).**
  Rejected: `confirm_all` is per-decision-commit today (D6 of FIBR-0011), and
  changing that is a behaviour change to shipped code this item did not ask for.
  A partial confirm is already the accepted outcome there, and the returned count
  tells the user what landed.
- **A loop of `delete_statement` calls, documented as order-dependent.**
  Rejected on atomicity (D5), not on data: §2.1 measured that the data converges.
  Had the measurement not been run, this option would have been rejected for the
  wrong reason — which is why the measurement is in the spec.
- **A typed-`DELETE` confirmation for Delete all** (the FIBR-0030
  `StartOverDialog` pattern). Rejected as disproportionate: that gate exists for
  destroying the vault itself, and statements are re-importable from their source
  files. The wording carries the warning instead (D7).

## 9. Out of scope

- **Bulk Unlink** on `transfers_confirmed` (D2). It stays single-select; a
  follow-up item if the asymmetry bothers users in practice.
- **Undo.** Neither item asks for it, and the statements delete has never had it.
- **The other five `SingleSelection` tables** (rules, forecast, recurring,
  accounts, transactions) — untouched.
- **Select-all keyboard affordance** beyond what `MultiSelection` gives free.

## 10. Resource cost

No new tables, no migration, no new dependency. The batch queries replace `= :pid`
with `NOT IN (<n ids>)` over the same indexes; N is the number of statements a
user ticks (single digits in practice, bounded by the statements they have
imported). The one behavioural cost is that a bulk delete holds one transaction
for the whole batch instead of N short ones — bounded by the same N, on a local
SQLite file with no concurrent writer.

## 12. Cross-doc impact

- **ROADMAP FIBR-0202** — its point 3 ("the batch is order-sensitive, and this is
  the real hazard") is corrected by §2.1: the data is not order-sensitive; the
  preview is what breaks. Annotate the bullet rather than rewrite it, so the
  measurement is visible.
- **ROADMAP FIBR-0201** — its open design question (service `confirm_many` vs a
  widget loop) is answered by D4/§4.3; annotate with the answer.
- **`tests/features/transfers/spec.md`, `tests/features/statements/spec.md`,
  `tests/features/table_state/spec.md`** — new invariant rows.
- **CHANGELOG** — two Added entries, one per roadmap id, on ship.
- **FIBR-0149** — its preview-wording contract is extended, not replaced; note
  the batch form against it.
- **FIBR-0148** — its hand-off gains the `deleting` parameter; note that the
  single-statement contract is the batch-of-one case.
