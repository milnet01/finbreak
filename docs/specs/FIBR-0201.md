## 1. Goal

A user who trusts eight of twelve suggested transfers confirms those eight in
one click, and a user cleaning up a bad import run deletes the statements
involved in one action — with a confirmation message that states truthfully what
the batch will destroy.

Nothing about the single-**selection** behaviour changes: with one row selected,
every action does exactly what it does today. The slots themselves do change —
`_on_confirm`, `_on_reject` and `_on_delete` become bulk slots reading
`selected_indexes` (D3, §4.8) — and `TransferDetectionService.confirm()` /
`reject()` keep no caller in `src/` afterwards, though both stay as the
single-pair API their tests exercise. `Confirm all` stays. A delete of one
statement keeps today's confirm strings **verbatim** (D9, INV-14) and today's
semantics (INV-12).

## 2. Problem

Both tabs offer one speed, and both refuse a plural selection at the widget
level rather than merely failing to wire one up.

**Transfers** (`ui/transfers.py`): `TransfersWidget._on_confirm` confirms the one
selected candidate; `TransfersWidget._on_confirm_all` confirms every candidate
the detector produced. There is nothing between one and all.

**Statements** (`ui/statements.py`): `StatementsWidget._on_delete` deletes the
one selected statement behind a confirm box. Clearing a bad import run of N
statements means N confirm dialogs, and there is no Delete all.

Four facts grounded against the source, not recalled:

1. **Both tables set `SelectionMode.SingleSelection`.** Seven source files set
   it — `grep -rl "SelectionMode.SingleSelection" src/ | wc -l` → 7 (rules,
   forecast, recurring, statements, accounts, transactions, transfers). Exactly
   two tables are in scope here, and one caveat matters: `transfers.py`'s single
   `setSelectionMode` line lives in `TransfersWidget._make_table`, which builds
   **both** transfer tables, so the naive edit widens the confirmed table too
   (INV-1).

2. **`selected_index` is single-row by construction.** It returns `None` unless
   exactly one row is selected (`ui/_table_state.py`, `selected_index`), and it
   has five UI callers — `grep -rn "selected_index(" src/ | cut -d: -f1 | sort
   -u` → `accounts.py`, `recurring.py`, `statements.py`, `transactions.py`,
   `transfers.py`, plus its own definition. So it cannot be widened in place;
   this spec adds a sibling. `selected_index`'s contract and body are untouched,
   and **all five** callers keep it — including both changed files, where
   `_on_reassign` (statements) and `_on_unlink` (transfers) stay single-row.

3. **Both tables re-sort on refresh.** `enable_sorting` and `remember_columns`
   are live on both, so a mutation followed by `_refresh()` / `refresh()`
   repopulates and re-sorts. The FIBR-0113 finding applies: a selection held
   across a re-sort can ride its item onto a different row.

4. **`StatementsWidget._on_selection_changed` drives two buttons from one
   flag** — `has_selection = self._selected_row() is not None` sets both
   `_reassign_button` and `_delete_button`. Change account is single-row and
   stays so, which is why the enablement rule cannot simply be relaxed for both
   (INV-7).

### 2.1 The measured trap in a bulk delete

`StatementService.delete_preview` answers *per statement*, and its coverage test
is "does a **remaining** statement of the same account also cover this row?" —
`q.id <> :pid` in `TransactionRepository.delete_split_counts`. During a bulk
delete the other statements in the batch are not remaining, but that query still
counts them as though they were.

Measured 2026-08-02. The seed is stated in full here because §7 requires the
tests to reproduce it and no probe script is committed: **one account; three
statement periods on it** — A covers 2026-01-01…01-31, B covers
2026-01-01…02-28, C covers 2026-02-01…02-28 — and **three transactions**, r1
(2026-01-10) and r3 (2026-01-20) stamped to A, r2 (2026-02-10) stamped to B.
The batch under test is `{A, B}`.

```
before: [('r1', A), ('r2', B), ('r3', A)]
up-front per-call previews: A=(0, 2) B=(0, 1)   summed removed=0 kept=3
batch-aware preview:                            removed=2 kept=1
loop A-then-B: returned 0 + 2 = 2 deleted;  after: [('r2', C)]
loop B-then-A:                              after: [('r2', C)]
```

**What was executed** was the two loop orders and both preview computations. A
batch *delete* was not run (nothing implements one yet), and no confirm message
was rendered — the numbers below are the previews' return values, and the wording
they would drive is quoted from the shipped source. Read both conclusions as the
measurement bounds them.

- **The confirm message is the defect, and it is measured.** Summing
  per-statement previews reports `removed=0`, which drives the shipped
  `kept > 0` branch — verbatim: *"Delete this statement? %n of its
  transaction(s) will be permanently removed — the rest are shared with an
  overlapping statement and will stay. This cannot be undone."* — so the user is
  told **0** will be removed for an action that in fact destroys two
  transactions irreversibly. The batch-aware query reports the truth,
  `removed=2`. This is the money-critical part of the item.
- **Loop ORDER does not affect the surviving data.** FIBR-0202's bullet says
  "deleting A then B is not the same as deleting {A,B} as a set". For the
  *reported counts and preview*, true and measured. For the *data*, both loop
  orders were measured identical. The mechanism is that the hand-off
  re-evaluates on every call, so a row handed to a statement that is itself
  about to be deleted is simply re-evaluated when that one goes; coverage by a
  doomed statement never persists. **That the batch form also lands there is an
  assertion, not a measurement** — INV-13 is what establishes it, over more than
  one seed. The bullet's framing of order-sensitivity as "the real hazard" is
  withdrawn here; the message defect above takes its place.

That leaves atomicity — not data correctness — as the argument for one
transaction over a loop (D5, §4.6).

## 4. Design

### 4.1 The shared seam: `selected_indexes`

Add to `ui/_table_state.py`, beside `selected_index`:

```python
def selected_indexes(table: QTableWidget) -> list[int]:
    """The parallel-list indexes of every selected row, sorted ascending **by
    index value** (i.e. in the order the rows were inserted, NOT their current
    visual order — the two differ after a sort). An untagged row contributes
    nothing (where ``selected_index`` returns None for one). Empty when nothing
    is selected. The plural sibling of ``selected_index``, which is deliberately
    single-row and is used in five files."""
```

The ordering is normative, not incidental: it is the order `confirm_many`
consumes, so it decides which of two conflicting pairs wins (INV-4).

`selected_index` is **not** changed: five UI files depend on its single-row
contract (§2 fact 2).

**`select_by_index` must clear the selection first.** Measured 2026-08-02:
`QTableWidget.selectRow` *replaces* the selection under `SingleSelection` but
*adds* to it under `MultiSelection` — `selectRow(0)` then `selectRow(2)` yields
`[2]` in the first mode and `[0, 2]` in the second. `select_by_index` therefore
becomes additive on the widened tables the moment D8 lands, which silently
changes the shipped, test-facing `StatementsWidget._select_period` from "select
this statement" into "also select this statement". It gains a
`table.clearSelection()` before the `selectRow`, restoring its single-row
meaning; `tests/features/` helpers that select two rows call `selectRow`
directly rather than through it (INV-15).

It is a shared helper called from **three** files — `grep -rn
"select_by_index(" src/ | grep -v "def "` → `transactions.py`, `accounts.py`,
`statements.py` — so the change reaches two tables this spec does not widen.
That is safe and worth stating rather than assuming: both stay
`SingleSelection`, where `selectRow` already replaces the selection, so the
added `clearSelection()` is a no-op for them.

### 4.2 Resolve before mutating

Every bulk slot resolves the selected rows to **domain ids** before the first
mutation, and iterates that resolved list:

```python
pairs = [(self._candidates[i].debit.id, self._candidates[i].credit.id)
         for i in selected_indexes(self._suggested)]
```

Never `self._candidates[i]` mid-loop. `_refresh()` rebuilds and re-sorts
`_candidates`, so an index resolved before the mutation and dereferenced after it
can name a different pair (FIBR-0113). The same rule gives statement ids on the
other tab.

### 4.3 Transfers: `confirm_many`, and `confirm_all` becomes its caller

`TransferDetectionService` grows:

```python
def confirm_many(self, pairs: Sequence[tuple[int, int]]) -> int:
    """Confirm each pair in the given order, skipping any whose debit or credit
    an earlier confirm in this pass consumed; returns the count committed."""

def confirm_all(self) -> int:
    return self.confirm_many(self._transfers().candidate_pairs())
```

The consumed-set logic **moves** into `confirm_many` rather than being copied —
it is `confirm_all`'s body today, and the hazard it guards is not specific to
"all": a user can equally select two suggestions that share a transaction.

**`confirm_many` calls `add_decision` directly, exactly as `confirm_all` does
today — not `_record`.** This is load-bearing for INV-4, and what it costs is
bounded: read against source 2026-08-02, `_record`'s entire body is two guards
(`is_confirmed` on either id, `pair_decided` on the pair) followed by an
unmodified `repo.add_decision(debit_id, credit_id, status.value)` — **it does not
canonicalise, reorder or dedupe the pair**, so bypassing it changes what is
*rejected*, never what is *written*. Both guards raise `ValueError`: the
consumed-set covers the first case by skipping, and the second cannot arise for
pairs resolved from the live candidate list, since `candidates()` is built from
`candidate_pairs()`, which excludes any transaction already in a confirmed pair
and any pair already confirmed or rejected. Routing through `_record` would
convert a skip into an exception at the user.

**Canonical ordering is not at risk**, which is the obvious worry about skipping
a guard: `TransferRepository.add_decision` canonicalises internally
(`low, high = min(...), max(...)` before the `INSERT`), so a `(debit, credit)`
pair is stored in canonical order whether or not `_record` was involved.
`pair_decided` canonicalises the same way, so the guard `confirm_many` skips is
itself order-insensitive.

`candidates()` also preserves `candidate_pairs()`' order and `_candidates` is
parallel to the table rows, so INV-4's "earlier one wins" is well-defined:
`selected_indexes` returns insertion-index order, which is that order.

`reject_many(pairs) -> int` is added alongside for D3. Rejection consumes
nothing, so it is a plain loop recording `TransferStatus.REJECTED` for each pair
via `add_decision`, on the same reasoning: a rejection of an already-decided pair
is not reachable from a live candidate list, and a raise at the user is the wrong
outcome if it ever were (INV-6). It lives in the service rather than the widget
because the widget never contains decision logic in this codebase.

### 4.4 Statements: one coverage predicate, widened to a set

Both queries in `TransactionRepository` key their coverage test on `q.id <> :pid`
— "any statement other than this one". A batch has to ask "any statement not in
this batch".

**The exclusion test appears at FOUR sites, not two** — `grep -c "q.id <> :pid"
src/finbreak/repositories/transactions.py` → 4:

| Query | Site | What it does |
|---|---|---|
| `hand_off_covered` | the `SET` correlated **picker** (`… ORDER BY q.period_start, q.id LIMIT 1`) | chooses *which* statement a row is handed to |
| `hand_off_covered` | the `EXISTS` **guard** | decides *whether* a row is handed off at all |
| `delete_split_counts` | the `NOT EXISTS` arm | counts `removed` |
| `delete_split_counts` | the `EXISTS` arm | counts `kept` |

The picker is the dangerous one and it is easy to miss, because it is not
`EXISTS`-shaped. Widen only the guard and the picker still says `q.id <> :pid` —
so it can re-stamp a row to a statement **inside the batch**, which §4.6 then
deletes: either the non-cascade FK trips and the whole batch rolls back, or the
row is lost. That is INV-13's own stated breaker, so a spec that unified only two
sites would have specified the bug it forbids.

FIBR-0149's invariant is that all four share the coverage predicate
**byte-for-byte**, which is what makes the preview unable to disagree with the
delete it describes. Four inline literals can be compared by eye today; once each
carries an N-placeholder run they cannot, and no test could assert it. So the
predicate becomes **one module-level builder returning the shared `WHERE`
fragment** — not an `EXISTS`-shaped sub-query, which the picker could not use:

```python
def _coverage_where_sql(ids: Sequence[int]) -> tuple[str, dict[str, int]]:
    """The shared 'same account, covers this row, and NOT one of the statements
    being deleted' WHERE fragment, plus the parameter dict that binds it.

    The single source of the predicate: all FOUR sites interpolate the SQL
    element — hand_off_covered's SET picker and EXISTS guard, and both of
    delete_split_counts' counting arms — so the preview cannot describe a delete
    that does not match it, and no row is ever handed to a statement in the
    batch (INV-9). Returning the params with the SQL keeps the :del0…:del{n-1}
    naming in ONE place; built separately they drift. Requires ids to be
    non-empty (see below)."""
```

**Placeholder style is pinned to named parameters** (`:pid`, `:del0 …
:del{n-1}`). `sqlite3` refuses mixed named and qmark binding in one statement,
and `hand_off_covered` keeps a scalar `:pid` in its outer `WHERE`, so an
interpolated `?` list would break it. The builder owns the naming rule
normatively and returns the parameter dict alongside the SQL, so the text and
the binding cannot drift apart in two places.

**`n == 0` is a precondition failure, not an edge case to render.** An empty
exclusion list would emit `q.id NOT IN ()`, which SQLite rejects as a syntax
error, so the builder requires `n >= 1`. Both batch service methods return early
before reaching it: `delete_statements(())` returns `0` and
`delete_preview_many(())` returns `(0, 0)`, without opening a transaction. The
widget slots already return early on an empty selection (§6); this makes the
service contract say so too, rather than relying on its callers.

**The SQL becomes module-level constants, so INV-9 has a surface to assert
against.** Today both statements are inline literals inside their methods, and a
test cannot obtain "the emitted SQL" to compare. Each query is built by a
module-level function (`_hand_off_sql(ids)`, `_split_counts_sql(ids)`) that the
repository methods execute and a test can import and call directly.

The repository methods then become (signatures only — bodies omitted):

```python
def hand_off_covered(self, statement_period_id: int,
                     deleting: Sequence[int]) -> int: ...
    # Its OUTER WHERE stays scalar (= :pid): it hands off ONE statement's rows,
    # while `deleting` excludes the whole batch from the coverage test.

def delete_split_counts(self, statement_period_ids: Sequence[int]) -> tuple[int, int]: ...
    # the ids ARE the exclusion set; there is no second parameter to disagree with.
    # Its OUTER WHERE widens to IN (<ids>) — it previews the whole batch at once.
```

`deleting` is **required, with no default.** A default of `(statement_period_id,)`
would look like it preserves the single-statement path, but after this change no
caller ever omits the argument: `delete_statement` delegates to
`delete_statements`, which always passes the batch explicitly — including the
batch-of-one, which passes a one-element list rather than relying on a default.
A default nothing exercises is a path no test covers and a future reader trusts.

`hand_off_covered` genuinely needs both arguments — it hands off the rows of
**one** statement while excluding **the whole batch**. `delete_split_counts` does
not: in every use the previewed set and the excluded set are the same list, so a
second parameter would be an API with no defined behaviour when the two differ.

**`statement_period_id` must itself be a member of `deleting`.** It is the one
precondition that is not obvious from the signature, and breaking it recreates
the bug §4.4 exists to prevent: with the statement absent from its own exclusion
list, the `SET` picker can re-stamp a row straight back onto the statement being
deleted, which the period-delete then orphans or FK-trips (INV-9).

**`delete_split_counts` has exactly one caller today** — `grep -rn
"delete_split_counts" src/ | grep -v "def "` → 1, `StatementService.delete_preview`
— and after this change its sole caller is `delete_preview_many`, with
`delete_preview(pid)` delegating to that rather than reaching the repository
itself. The scalar call site therefore disappears; nothing else in `src/` is
affected.

`StatementService` then grows (signatures only — bodies omitted):

```python
def delete_statements(self, period_ids: Sequence[int]) -> int: ...
    # ONE owned transaction. Returns the TOTAL transactions deleted across the
    # batch, so the batch-of-one returns exactly what delete_statement does today.
def delete_preview_many(self, period_ids: Sequence[int]) -> tuple[int, int]: ...
def delete_statement(self, period_id: int) -> int: ...
    # returns self.delete_statements((period_id,)) — signature and result unchanged
def delete_preview(self, period_id: int) -> tuple[int, int]: ...
    # returns self.delete_preview_many((period_id,)) — signature and result unchanged
```

**The confirm text is built by a pure helper, not inline in the slot.**
`StatementsWidget._confirm_text(self, removed: int, kept: int, statements: int)
-> str` returns the finished message and nothing else; `_on_delete` passes it to
`QMessageBox.question`. Without that seam the invariants guarding the
money-critical wording (INV-14, INV-16) would have to observe a string produced
*inside* a blocking modal — `_on_delete` uses `QMessageBox.question` directly,
not the non-blocking `show_modal` that `_on_reassign` uses — and neither leg
could be written without monkeypatching Qt.

It is a **method, not a module-level function**, so the strings keep going
through `self.tr` in the `StatementsWidget` translation context, which is what
INV-14's byte-for-byte claim about today's strings depends on. Its legs build the
widget under `qtbot` and call it directly; no dialog is opened.

### 4.5 The confirm message — money-critical

One message, from **one** `delete_preview_many(ids)` call over the whole batch —
never N per-statement previews summed (§2.1, INV-8).

**Qt binds one numerus per string, and a second `%n` silently repeats the
first.** Measured 2026-08-02 with `QCoreApplication.translate`:

```
translate("X", "Delete %n statement(s) and %n transaction(s)?", "", 2)
  -> "Delete 2 statement(s) and 2 transaction(s)?"
```

Both placeholders took the same `n`. So the failure mode is not a compile error
an implementer would notice — it is a plausible-looking wrong transaction count
in the one dialog whose entire purpose is stating the true one. The mechanism is
therefore pinned: **`%n` binds the transaction count** (as today's strings do, so
the pluralisation that matters is the one on the number being destroyed), and the
statement count is interpolated separately with `str.format`, which composes
cleanly with a pluralised `%n` (measured in the same run). The two strings, for
N > 1:

- `kept > 0`:
  `tr("Delete {k} statements? %n of their transaction(s) will be permanently "
  "removed — the rest are shared with a statement that is staying, and will "
  "survive with it. This cannot be undone.", "", removed).format(k=len(ids))`
- `kept == 0`:
  `tr("Delete {k} statements and every one of their %n transaction(s)? Nothing "
  "is shared with a statement that is staying, so all of them are permanently "
  "removed. This cannot be undone.", "", removed).format(k=len(ids))`

The `kept == 0` string must state the totality explicitly, because that is the
branch **Delete all** always reaches (§4.7) and it is the case where the loss is
complete — D7 promises exactly this wording and nothing else carries it.

**The branches are ordered, and `removed == 0` is reachable.** `list_statements`
deliberately keeps zero-linked statements in the list (count 0, FIBR-0052
INV-7b), so a batch of empty imports would otherwise render "every one of their 0
transaction(s)". `_confirm_text` tests them in this order — the first match wins,
and stating the order is the point, since two of the four conditions overlap:

| # | Condition | Message |
|---|---|---|
| 1 | `statements == 1` | today's two shipped strings, byte-for-byte (D9, INV-14) |
| 2 | `removed == 0 and kept == 0` | "Delete {k} statements? They have no transactions linked to them." |
| 3 | `kept > 0` | the shared-rows string above — including when `removed == 0`, which honestly reads "0 of their transaction(s) will be permanently removed" because that is exactly what happens |
| 4 | otherwise (`removed > 0, kept == 0`) | the total-loss string above |

Row 1 comes first so a one-statement delete can never reach a batch string, and
row 2 before row 3 so an empty-import batch is not told about sharing that is not
happening.

Two constraints on the mechanism:

- **`.format()` runs on the translated string**, so a translator who introduces a
  stray `{` or `}` raises at the confirm dialog. Any future translation must keep
  `{k}` intact and add no other braces; if that proves fragile, swap to a `%1`
  token and `str.replace`, which cannot raise.
- **For N == 1 the two shipped strings in `_on_delete` are used unchanged** (D9,
  INV-14). That includes `Delete all` when exactly one statement is listed: it is
  a one-statement delete and reads as one. Intended — the batch wording exists
  for the case the singular grammar cannot express.

### 4.6 One transaction, and what it buys

`delete_statements` runs one `owned_transaction`: for each id, hand off (against
the survivor set) and delete its orphan rows; then delete the period rows. A
failure anywhere rolls the whole batch back to a re-openable vault, which is the
property a loop of `delete_statement` calls cannot offer (D5). It is **not**
claimed to change what survives; INV-13 pins the equivalence so a future change
to the batch form cannot quietly alter it.

### 4.7 Delete all

**Delete all** passes every listed statement id to the same two functions. With
the exclusion set covering every statement, the `EXISTS` guard can never find a
survivor, so `kept` is necessarily 0 and every stamped row is removed — the
`kept == 0` wording is reached with no special case (INV-11). That is also the
case where the loss is total, which is why that wording says so plainly.

### 4.8 Buttons and enablement

- `_delete_button` and the transfers `Confirm` / `Reject` buttons enable on a
  **non-empty** selection (`bool(selected_indexes(...))`).
- **`_reassign_button` (Change account) enables only on exactly one selected
  row** — `len(selected_indexes(self._table)) == 1`. It is single-row by design
  (§2 fact 2) and today shares one `has_selection` flag with Delete (§2 fact 4);
  relaxing both together would leave Change account clickable and silently
  no-op, because `_on_reassign` reads `_selected_row()`, which returns `None` for
  a plural selection. INV-7.
- **`Delete all`** is a new `QPushButton` with `objectName`
  `button_delete_all_statements` — every button in `StatementsWidget` carries one
  and the `qtbot` legs locate widgets by it. Enabled whenever any statement is
  listed, mirroring `Confirm all`'s `bool(self._candidates)`.
- The Transfers status line already pluralises
  (`tr("Confirmed %n transfer(s).", "", n)`). `tr("Rejected.")` gains a plural
  form for n > 1 — `tr("Rejected %n transfer(s).", "", n)` — and **keeps
  `tr("Rejected.")` verbatim at n == 1**. This is D9's rule applied to the other
  tab: "Rejected 1 transfer(s)." is the same regression as "Delete 1
  statement(s)?", and §1 promises single-selection behaviour is unchanged
  (INV-14).
- When `confirm_many` skips a pair because an earlier confirm consumed one of its
  transactions, the status line **names the skip** rather than silently reporting
  a smaller number: `tr("Confirmed %n transfer(s).", "", n)` gains a second
  sentence, `tr("%n suggestion(s) were skipped — they share a transaction with a
  transfer you just confirmed.", "", skipped)`, shown only when `skipped > 0`,
  where `skipped = len(pairs) - confirmed` — `confirm_many` returns the committed
  count and the widget knows how many it asked for, so no wider return is
  needed. A
  user who deliberately selected five rows and got three is owed the reason;
  under `Confirm all` the same drop is invisible by design, which is why it never
  needed saying before (§6).

## 6. Failure modes

- **A vault lock mid-batch.** Every slot already catches `VaultLockedError` and
  returns; with a batch the catch must wrap the whole call, not each iteration,
  or a lock half-way leaves the status line reporting a count that did not land.
- **A non-lock exception mid-confirm.** `confirm_many` commits per decision
  (D4), so an unexpected raise part-way leaves the earlier confirmations
  committed and loses the count — the hazard ROADMAP FIBR-0201's open question
  named. Accepted, because it is `confirm_all`'s shipped behaviour today and
  narrowing it is out of scope; recorded here rather than left implicit.
- **Resolved ids held across a modal confirm.** The two tabs differ and the spec
  must not flatten them. On **transfers** there is no event-loop turn between
  resolution and mutation, so nothing can intervene. On **statements** there
  is: `_on_delete` calls the blocking `QMessageBox.question` between the preview
  and the delete, and the shipped code already comments that box as the place
  where "an idle auto-lock can fire while this (nested, untracked) confirm box is
  open". So a bulk delete holds N resolved ids across that window, and the
  existing `VaultLockedError` catch around `delete_statements` is what covers
  it — it must wrap the batch call, not each id. The preview shown to the user
  may also be one lock-and-unlock stale, which is the same exposure the shipped
  single delete already has and is not widened here.
- **An empty selection.** Both bulk slots return early on an empty resolved list,
  as the single-row slots do on `None`, and both batch service methods return
  early too (§4.4) rather than trusting their callers.
- **A selection the user made that is partly skipped.** `confirm_many` drops a
  pair whose transaction an earlier confirm consumed (INV-4). Under `Confirm all`
  that is invisible by design; under an explicit selection the user chose five
  and got three, so the status line names the skipped count (§4.8). The skip is
  the correct outcome — a transaction belongs to at most one transfer — but a
  silent one would read as a bug.
- **A batch spanning accounts.** The coverage predicate is per-account
  (`q.account_id = transactions.account_id`), so statements on different accounts
  cannot affect each other's hand-off. No special handling — and §7 requires a
  seed that exercises it.

## 8. Alternatives considered (and rejected)

- **Widen `selected_index` to return a list.** Five call sites would need
  updating for a behaviour none of them wants; all five rely on the single-row
  contract, including the two files this spec changes (§2 fact 2).
- **`ExtendedSelection` instead of `MultiSelection`** (D8). It is the desktop
  convention, but it requires Ctrl/Shift to select more than one row — knowledge
  this app's stated audience should not need for its headline new interaction.
  Revisit if users report that plain-click toggling loses them a selection.
- **One transaction for bulk confirm.** Rejected: `confirm_all` is
  per-decision-commit today (FIBR-0011 D6), and changing that is a behaviour
  change to shipped code this item did not ask for. A partial confirm is already
  the accepted outcome there, and the returned count tells the user what landed
  (with the caveat in §6).
- **A loop of `delete_statement` calls, documented as order-dependent.**
  Rejected on atomicity (D5), not on data: §2.1 measured that loop order does not
  change what survives. Had that not been measured, this option would have been
  rejected for the wrong reason — which is why the measurement is in the spec.
- **A typed-`DELETE` confirmation for Delete all** (the FIBR-0030
  `StartOverDialog` pattern). Rejected as disproportionate: that gate exists for
  destroying the vault itself, and statements are re-importable from their source
  files. The wording carries the warning instead (D7).
- **A second parameter on `delete_split_counts`** so the previewed set and the
  excluded set could differ. Rejected: no described use needs them to differ, and
  a parameter pair with undefined divergent behaviour is an API an implementer
  has to guess at (§4.4).

## 9. Out of scope

- **Bulk Unlink** on `transfers_confirmed` (D2). It stays single-select; a
  follow-up item if the asymmetry bothers users in practice.
- **Undo.** Neither item asks for it, and the statements delete has never had it.
- **A checkbox column.** `MultiSelection` toggles whole rows on click; no
  per-row checkbox widget is added, and the design language is "selected rows".
- **The other `SingleSelection` tables** (rules, forecast, recurring, accounts,
  transactions) — untouched.
- **A select-all keyboard affordance** beyond what `MultiSelection` gives free.
- **A progress affordance for a very large Delete all** (§10) — no evidence yet
  that it is needed, and no defensible threshold to pin.
- **What the selection contains after a bulk action.** Both tabs rebuild and
  re-sort on refresh, which drops the selection today; that is unchanged here and
  not specified as a behaviour either way.

## 10. Resource cost

No new tables, no migration, no new dependency. The two queries are edited
differently, and conflating them is how the hand-off breaks (§4.4):

- **`hand_off_covered`** keeps its outer `WHERE statement_period_id = :pid`
  scalar — it still hands off one statement's rows — and widens its **two**
  coverage sites from `q.id <> :pid` to `q.id NOT IN (:del0 … :del{n-1})`.
- **`delete_split_counts`** widens both: its outer `WHERE` becomes
  `statement_period_id IN (…)` because it previews the whole batch, and its two
  counting arms take the same coverage change.

All of it runs over the same indexes. N is the number of statements in the batch,
bounded above by the number the user has ever imported (`Delete all` is the
ceiling). Named parameters bind once however many times the name appears, so a
hand-off call binds **N + 1** parameters (up from 1 today) across its 2N + 1
textual occurrences, and a preview binds **N**. SQLite's default
`SQLITE_MAX_VARIABLE_NUMBER` is 32766 (it was 999 before 3.32, 2020) — far above
any plausible statement count either way, so no smaller bound is assumed.

The one behavioural cost is that a bulk delete holds one transaction for the
whole batch instead of N short ones — bounded by the same N, on a local SQLite
file with no concurrent writer.

**No latency budget is set, deliberately.** `Delete all` runs synchronously in a
Qt slot over every statement the user has imported, so a large enough vault would
block the UI. No number is pinned because none can be justified from evidence
this project has: the existing single delete is already synchronous, nobody has
reported a slow one, and a threshold invented here would be a figure no test
could defend. If it bites, the fix is a busy cursor or a progress dialog, and it
is a follow-up item rather than a silent assumption (§9).
