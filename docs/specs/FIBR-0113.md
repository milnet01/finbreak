# FIBR-0113 — Show accounts in a sortable 5-column table with a masked account number

**Status:** spec draft (2026-07-28).
**Kind:** feature.
**Source:** ROADMAP FIBR-0113 (user-request-2026-07-12, screenshot). FIBR-0084
scope-checked; its remaining surfaces split to FIBR-0192. The storage half of
this item's original draft split to FIBR-0193 on 2026-07-28 (§13).
**Blocked by:** FIBR-0193 (this table renders and edits `Account.account_number`
and `Account.note`, which that item creates).
**Pairs with:** FIBR-0084 (§9 — this spec unblocks its Accounts surface only and
does **not** close it; FIBR-0192 is its blocker), FIBR-0117 (§2 — shipped the
`_table_state` seam this reuses), FIBR-0005 / FIBR-0128 / FIBR-0177 (§12 — this
spec amends invariants in all three).

**Layman:** The Accounts tab becomes a proper table — Name, Type, Account
number, Note and Status — that you can sort, resize and reorder, instead of one
cramped line per account; account numbers are hidden behind dots until you ask
to see them, and hide themselves again shortly after.

## 1. Goal

The Accounts tab lists each account as a row in a real table with five sortable
columns — Name, Type, Account number, Note, Status — whose widths and order the
user can change and which finbreak remembers. The two optional per-account
fields FIBR-0193 stores (a reference account number and a free-text note) gain
their first user-facing surface: they can be entered and edited on the tab. The
account number is masked on screen by default, and a reveal lapses back to
masked after `_REVEAL_SECONDS` without the user doing anything.
Accounts also gains a header for the first time, so it can finally join the
shared remembered-column scheme — one of the three surfaces FIBR-0084 needs;
the other two are FIBR-0192's (§9).

## 2. Problem

`src/finbreak/ui/accounts.py::AccountsWidget` renders accounts into a
`QListWidget`, building one string per row in
`AccountsWidget._refresh()`: `f"{account.name} — {label}"`, then
concatenating up to two suffixes onto it — the remembered-statement-password
marker, and `AccountsWidget._reconciliation_suffix()`'s FIBR-0177 output
(`✓ balances reconcile`, `⚠ off by {money}`, `⚠ {n} periods don't reconcile`).

Three consequences:

1. **Nothing is sortable or scannable.** A list item is one opaque string, so a
   user with a dozen accounts cannot bring the accounts that fail to reconcile
   to the top — which is the only reason that marker exists.
2. **The two new stored fields have nowhere to appear.** FIBR-0193 adds
   `Account.account_number` and `Account.note`, but a one-line list item has no
   room for them and the add/edit form has no inputs for them, so a user with
   two "Cheque" accounts at different banks still cannot tell them apart.
3. **Accounts cannot join the remembered-column-layout scheme.**
   `src/finbreak/ui/_table_state.py::remember_columns()` (shipped by FIBR-0117)
   already delivers most of what FIBR-0084 asks for — `setSectionsMovable(True)`, header
   `saveState`/`restoreState` into the plaintext window INI keyed by
   `objectName`, re-saved on resize / reorder / re-sort — and is already called
   by Statements, Transactions, Rules, Recurring, Transfers and the
   import-wizard preview. A `QListWidget` has no header, so Accounts cannot
   participate at all.

Fixing consequence 3 does **not** finish FIBR-0084 — three further gaps remain,
enumerated once in §9 and owned by FIBR-0192, which is FIBR-0084's blocker.
`ui/categories.py::CategoriesWidget` is excluded permanently: its `QTreeWidget`
sets `setHeaderHidden(True)` over a single column, so there is nothing to resize
or reorder. That is this document's one statement of the Categories exclusion;
§8 and §9 point here.

## 3. Scope decisions

Settled with the user on 2026-07-28 (1–5, 8) or by the author from §2 (6, 7):

1. **Five columns, with Status as its own column** — not four columns with the
   markers left glued to the Name cell. Chosen so the reconciliation warnings
   become sortable (consequence 1 above).
2. **The account number is masked by default with an explicit reveal toggle** —
   not shown in full, and not masked with no way to see it. The exposure being
   defended against is shoulder-surfing and screenshots, not storage: the value
   already sits inside the SQLCipher vault, encrypted at rest.
3. **The add/edit form stays inline on the tab**, relaid from one row to a
   two-row grid — not moved into an Add/Edit dialog. Preserves the current
   type-a-name-and-hit-Add flow.
4. **Reveal is session-scoped**, never persisted — a reveal that survives a
   restart is a reveal the user did not ask for that day.
5. **A reveal auto-hides after `_REVEAL_SECONDS` (30).** Decision 2 defends
   against someone seeing the screen; a reveal left on indefinitely gives that
   back the moment the user walks away. 30 seconds is taken from the existing
   `clipboard_clear_seconds` default — the app's other "sensitive thing visible
   for a bounded time" control, recorded in `docs/security-model.md` T13 — so
   the two exposure windows match rather than each being invented. A fixed
   constant, not a setting: see §9.
6. **`_refresh()` clears the table before filling it** (author, after cold-eyes
   loop 5). `AccountsWidget._refresh()` today opens with `self._list.clear()`,
   so the selection already drops on every repopulate; clear-then-fill preserves
   that behaviour in the table. The alternative — `StatementsWidget.refresh`'s
   `setRowCount(len(rows))` + `setItem` reuse-rows shape, which this spec
   otherwise takes as its precedent — does **not** clear the selection, and
   under an active sort the surviving selection rides its item through the
   re-sort and lands on a **different account**. §8 records the reproduction.
   INV-22 locks the cleared-selection property; §4.4 pins the mechanism.
7. **The Forget-button rule lives in its own gating-only helper,
   `_apply_forget_gating()`** (author, after cold-eyes loop 5). It is called from
   three sites — `_on_selection_changed`, the end of `_refresh()`, and
   `_on_reveal_toggled`'s step 6 — so the rule has one implementation. The
   sibling this spec copies (`StatementsWidget.refresh` ending with
   `self._on_selection_changed()`) works there only because that widget's
   handler toggles two buttons and touches nothing else; `AccountsWidget`'s also
   repopulates the form from storage, so copying the line verbatim would make
   every `_refresh()` overwrite whatever the user was typing.
8. **FIBR-0084's remaining surfaces are split out, not carried here** (user,
   after cold-eyes loop 2). Folding them in made this spec the largest source of
   its own review defects. FIBR-0192 owns them; FIBR-0084 stays open until it
   ships.

## 4. Design

### 4.1 Masking

A module-level helper in `ui/accounts.py`:

```python
_MASK = "•" * 4

def _mask_account_number(value: str | None) -> str:
    """Display form: a mask plus the last 4 characters for a value longer than
    4; a bare mask for a value of 1-4 characters (its "last 4" would be all of
    it); an empty cell when there is no number at all."""
    if not value:
        return ""
    return f"{_MASK} {value[-4:]}" if len(value) > 4 else _MASK
```

A `QCheckBox` — `self._reveal`, labelled "Show account numbers" — sits on its
own row between the table and the form. It is constructed unchecked and its
state is never written to `QSettings`, to the vault settings, or anywhere else.

Reveal governs **two** surfaces, not one — the table column and the edit form's
account-number field. The form is the easy one to forget: selecting a row
populates it, so a form showing the raw value would put the number on screen
whenever anyone clicks an account, defeating decision 2 on the same screen that
masks the column. So the form field's echo mode follows the toggle:
`self._account_number.setEchoMode(QLineEdit.EchoMode.Password)` when reveal is
off, `Normal` when on — the field stays fully editable either way, exactly like
any password box (user, 2026-07-28). It is constructed `Password` in `__init__`,
and **`_on_reveal_toggled` sets the echo mode explicitly** (§4.3's step list);
it is deliberately *not* set from `_on_selection_changed`, which §4.3 suppresses
across the reveal re-selection and which therefore does not run on the one
transition INV-16 governs.

The form field always carries the **raw stored value** —
`_mask_account_number` is for the table cell only and must never reach the form,
or an Update would write `"•••• 7890"` back into the vault as the account
number. Masking in the form is echo mode alone; the underlying `text()` stays
real. The **table cell** is masked by text substitution rather than echo mode,
because a `QTableWidgetItem` has none. INV-20 locks the cell, INV-16 the field —
two surfaces, two invariants, because an implementation that masks one and not
the other satisfies decision 2 nowhere.

Checking the box also starts a single-shot timer that re-masks on expiry.
`ui/_clipboard.py::ClipboardAutoClear` is the precedent for *the shape of the
guard only* — a single-shot `QTimer` whose `timeout` is wired to a **named
method** rather than a lambda, which its docstring justifies as giving "the
guard exactly one implementation". Two deliberate differences: it calls `stop()`
then `start(seconds * 1000)` per use because its delay is settings-driven, where
`_REVEAL_SECONDS` is a constant set once via `setInterval`; and its `timeout`
goes straight to the guard, where this one goes to `_on_reveal_timeout`, which
only unchecks the box so the re-mask travels the same path as a manual uncheck.

```python
_REVEAL_SECONDS = 30

self._reveal_timer = QTimer(self)          # parented — dies with the widget
self._reveal_timer.setSingleShot(True)
self._reveal_timer.setInterval(_REVEAL_SECONDS * 1000)
self._reveal_timer.timeout.connect(self._on_reveal_timeout)
```

`self._reveal.toggled` connects to `_on_reveal_toggled`, whose ordered steps are
given in §4.3 — it is the one handler that owns the reveal transition. The
interval is restarted, not extended, on each fresh reveal, and a `_refresh()`
reached any other way does not touch the timer (INV-11).

The timer is a **convenience bound on exposure, not a security boundary** — a
revealed number is on screen for up to `_REVEAL_SECONDS` regardless, and
anything that can read the process's memory can read the value whether it is
masked or not.

Reveal cannot outlive a lock without any extra code:
`main_window.py::MainWindow._lock()` calls `_clear_live()`, which destroys the
whole workspace (its INV-3), and `_build_workspace()` constructs a fresh
`AccountsWidget` on the next unlock — so the checkbox returns to unchecked.
This is a property to *test*, not to implement.

### 4.2 The table

`AccountsWidget._list` (`QListWidget`) becomes `AccountsWidget._table`
(`QTableWidget`), built the way `ui/statements.py::StatementsWidget` builds
`statements_table` — the closest sibling, also five columns:

```python
self._table = QTableWidget(0, 5)
self._table.setObjectName("accounts_table")
self._table.setHorizontalHeaderLabels([
    self.tr("Name"), self.tr("Type"), self.tr("Account number"),
    self.tr("Note"), self.tr("Status"),
])
self._table.setEditTriggers(QAbstractItemView.EditTrigger.NoEditTriggers)
self._table.setSelectionBehavior(QAbstractItemView.SelectionBehavior.SelectRows)
self._table.setSelectionMode(QAbstractItemView.SelectionMode.SingleSelection)
enable_sorting(self._table)      # before remember_columns, as in the sibling
remember_columns(self._table)
```

`self._rows: list[Account]` and `self._with_pw: set[int]` are initialised empty
in `__init__` **before** the table is constructed and its selection signal
connected — as `StatementsWidget.__init__` does for its own parallel list — so a
selection signal emitted during construction or the first fill cannot reach an
unset attribute.

**The fill is clear-then-fill** (§3 decision 6). `_refresh()` reads the vault,
then inside `_table_state.fill_guard(...)` calls `self._table.setRowCount(0)`
before `setRowCount(len(self._rows))` and the per-row `setItem` /
`_table_state.tag_row(table, row, index)` calls. The leading `setRowCount(0)`
is the load-bearing line — §8's rejected reuse-rows alternative owns the
mechanism and the reproduction, and INV-22 locks the result.

`_refresh()` **ends with `self._apply_forget_gating()`** (§3 decision 7), not
with `self._on_selection_changed()`. The gating must be re-applied because a
cleared selection has to disable the Forget button (the FIBR-0128 D3 gating
depends on that), but the form must **not** be repopulated — `_on_add` clears
the three `QLineEdit`s immediately before calling `_refresh()`, and a trailing
`_on_selection_changed()` would undo that clear on every add, update, delete,
forget, and every activation of the Accounts tab through
`MainWindow._refresh_tab`.

**The `VaultLockedError` guard wraps the service reads only, before any
mutation.** `_refresh()` swallows it silently, as every `_on_*` handler in this
widget already does: `MainWindow._lock()` locks the vault *before*
`_clear_live()` runs, and `_clear_live` deletes the workspace with
`deleteLater()`, so an auto-hide timeout queued just before a lock can still
reach `_refresh()` while the vault is shut (§6). Guarding only the reads — the
`list_accounts()` / `account_ids_with_pdf_password()` /
`account_statuses()` block — and returning before `self._rows`, `self._with_pw`
or the table are touched leaves the previous render intact. A guard around the
whole body would let a lock land mid-fill and leave those three half-updated
while §4.3's steps 5–6 run against them.

Row-identity handling follows the `_table_state` contract the sibling tabs use,
because sorting breaks a naive visual-row lookup:

- `_on_selection_changed`, `_on_update`, `_on_delete` and `_on_forget_password`
  resolve the target through `_table_state.selected_index(self._table)` into
  `self._rows`, replacing today's `self._list.currentItem()` +
  `item.data(_ACCOUNT_*_ROLE)` reads. These four are the complete set of
  `currentItem()` readers; `_on_add` correctly has none. The four
  `_ACCOUNT_*_ROLE` constants and their `setData` calls are deleted.
  **This deletion is a correctness requirement, not tidying:**
  `_ACCOUNT_ID_ROLE` is `Qt.ItemDataRole.UserRole` and so is
  `_table_state._ROW_INDEX_ROLE`, so any surviving
  `setData(_ACCOUNT_ID_ROLE, account.id)` on a column-0 item overwrites the row
  tag, and `selected_index` then returns a **database id used as an index into
  `self._rows`** — off-by-one at best, `IndexError` or the wrong account at
  worst. §6 records the mirror-image hazard on the test side.
  `self._rows` carries three of the four facts — id, name and type are all on
  `Account`. The fourth is **not**: the has-a-saved-statement-password flag
  behind `_ACCOUNT_HAS_PW_ROLE` comes from
  `AccountService.account_ids_with_pdf_password()` and deliberately does not
  live on `Account` (FIBR-0193 INV-4 keeps the credential out of every listing).
  So `_refresh()` also stores `self._with_pw: set[int]` from that same call, and
  `_apply_forget_gating` gates the Forget button on `account.id in self._with_pw`.
  Dropping this member silently disables the FIBR-0128 D3 gating.
- `_select_account(account_id)` **maps the id to a position first**:
  `select_by_index` matches the insertion index written by `tag_row`, not a
  database id, and the two are not interchangeable. It finds the index of the
  `Account` in `self._rows` whose `id` matches and calls `select_by_index` with
  that index. An **absent id leaves the current selection unchanged** — it does
  not clear it, matching `select_by_index`, which simply returns on no match.
  This method was previously test-only; this spec promotes it to a production
  caller (`_on_reveal_toggled`).
- The selection signal moves from `currentItemChanged` to the table's
  `itemSelectionChanged`.

The Status cell is a `_table_state.SortableItem` whose sort key is a severity
rank, so clicking the header groups problems rather than ordering strings:
`0` = `ReconciliationStatus.OFF`, `1` = the quiet statuses
(`NOT_ENOUGH_DATA` / `NOT_SUPPORTED`), `2` = `RECONCILED`. Its text composes the
reconciliation marker and the 🔑 saved-password marker in that order, joined by
`" · "` and omitting absent parts:
`" · ".join(part for part in (recon_text, key_text) if part)`. That order is a
**deliberate reversal** of today's list line, which appends the 🔑 marker first
and the reconciliation suffix second: the column is sorted by reconciliation
severity, so the reconciliation text leads the cell it is sorted by.

Those marker strings live in four `self.tr(...)` literals in
`_reconciliation_suffix()` and `_refresh()`, each currently beginning with a
`"  ·  "` separator for list-line concatenation. Moving them into a cell means
**editing those four translatable literals** to drop the leading separator —
translation-catalogue churn, not a `removeprefix` hack at the call site.
`_reconciliation_suffix()` keeps its name even though its output is now part of
a cell rather than a suffix; renaming it would touch FIBR-0177's citations for
no behavioural gain.

The other four cells are plain `QTableWidgetItem`s: Name, Type and Note sort
lexically, which is correct. The Account number column sorts by whatever is
displayed — the last 4 while masked, the full value while revealed — so
toggling reveal can reorder a live sort on that column. That is acceptable and
noted rather than fixed; sorting a masked column can only ever expose what the
mask exposes.

### 4.3 The form

`add_row` (today one `QHBoxLayout` of name / type / Add / Update) becomes a
`QGridLayout` of two rows: Name and Type on the first, Account number and Note
on the second, with Add and Update at the end of the second row. Everything else
on the tab is kept verbatim — the `actions` row (`_delete_button`,
`_forget_pw_button`, the stretch, and the `show_done`-gated `_done_button`), the
`_error` label, and the `done` signal — so FIBR-0052 INV-12's tab-mode gating is
untouched. Both new
`QLineEdit`s get `setAccessibleName` alongside their placeholder, matching the
existing `_name` field — a placeholder disappears on typing and is not a
reliable accessible name (WCAG 1.3.1 / 3.3.2). `_on_selection_changed`
populates all four inputs when an account is selected and **leaves them
untouched when the selection clears**, matching today's behaviour — which
clear-then-fill makes load-bearing, since every `_refresh()` now clears the
selection.

`_on_add` clears the three `QLineEdit`s — name, account number, note — and
**leaves the Type picker on its current selection**, as today. "Clear" is not
applied to the `QComboBox`: `QComboBox.clear()` removes its *items*, which would
destroy the seven type entries and the token-behind-label contract `__init__`
builds.

`_on_add` and `_on_update` pass the raw field text to the service, which
normalises it (FIBR-0193 §4.2).

`_apply_forget_gating()` is the whole of the Forget rule:

```python
def _apply_forget_gating(self) -> None:
    """Enable Forget only for a selected account that has a saved statement
    password (FIBR-0128 D3). Gating ONLY — it never touches the form, so a
    _refresh() cannot overwrite in-progress input."""
    index = selected_index(self._table)
    account = self._rows[index] if index is not None else None
    self._forget_pw_button.setEnabled(
        account is not None and account.id in self._with_pw
    )
```

`_on_selection_changed` calls it first, then early-returns on no selection, then
populates the four inputs — the same order today's handler uses, so a cleared
selection still disables the button rather than leaving it stale-enabled.

Toggling reveal repopulates the table, which under clear-then-fill drops the
current selection (§3 decision 6), so `_on_reveal_toggled` restores it — and the
order matters, because the selected id must be captured before `_refresh()`
replaces `self._rows`. Its signature is **`@Slot(bool)`**: `QCheckBox.toggled`
carries a `bool`, and this module's convention of `@Slot()` on zero-argument
handlers would be a runtime `TypeError` here under PySide6.

1. capture the currently selected account id (via `selected_index` into
   `self._rows`), or `None`;
2. set `self._account_number.setEchoMode(...)` — `Normal` if the box just went
   on, `Password` if it went off (INV-16);
3. start the single-shot timer if it went on, stop it if it went off (INV-11);
4. call `_refresh()`, which rebuilds `self._rows` and the table, leaving no
   selection (INV-22);
5. if an id was captured, re-select it via `_select_account` **with
   `self._table.blockSignals(True)` around the call**, then unblock. Blocking
   suppresses `itemSelectionChanged`, so `_on_selection_changed` does not fire
   and cannot overwrite half-typed form input from storage (INV-19);
6. call `_apply_forget_gating()` — the one thing step 5 suppressed that still
   has to happen. It is the same helper `_on_selection_changed` and `_refresh()`
   use, so the rule has one implementation, not three.

`_refresh()` itself does **not** re-select — doing so would make `_on_add`'s
field-clearing useless, because the re-selection would repopulate the form with
the account just added.

## 5. Invariants

INV-1 to INV-4 and INV-10 are **withdrawn to FIBR-0193**, INV-13 and INV-14
**to FIBR-0192**; all seven keep their ids and are listed at the end of this
section. The live set is therefore non-contiguous by design (spec-format §3.7 —
never renumber).

- **INV-5** — `_mask_account_number` returns a mask plus the last 4 characters
  for a value longer than 4, a bare mask with no digits for a value of 1–4
  characters, and an empty string for `None` or `""`.
  *Test:* `tests/features/accounts/test_accounts.py`, over
  `_mask_account_number` — `"1234567890"`, `"12345"` (the shortest value taking
  the last-4 branch), `"1234"`, `"123"`, `""`, `None`.
  *Breaks when:* the helper slices `value[-4:]` unconditionally, so a 3-digit
  number renders in full — the mask leaks exactly the values it is shortest
  for.

- **INV-6** — A freshly constructed `AccountsWidget` has reveal off, the toggle
  state is written to no persistent store, and a lock cycle returns it to off.
  *Test:* `tests/features/accounts/test_accounts.py` — a `qtbot` test that (a)
  asserts the checkbox is unchecked on construction; (b) **parses** the window
  INI before and after toggling and asserts no key outside
  **`columns/accounts_table`** changed (a parse, not a byte compare — a byte
  compare cannot exclude a key, and `remember_columns` may legitimately write
  that one); and (c) drives `MainWindow._lock()` then a re-unlock and asserts
  the rebuilt tab's checkbox is unchecked. Leg (c) needs a `MainWindow`, not a
  bare widget — build one, `_enter_unlocked()`, toggle reveal on, `_lock()`,
  re-`unlock()` the service, `_enter_unlocked()` again. It is the single leg in
  this spec that does so (§7 and §11's "constructed standalone" notes both carry
  the exception), and what it uniquely catches is `_clear_live` ever being
  changed to *reuse* the Accounts tab rather than rebuild it — which legs (a)
  and (b) cannot see.
  *Breaks when:* the toggle is persisted next to the column state in the window
  INI, so a machine left revealed stays revealed across a lock. Excluding the
  whole `columns/` **group** rather than the single `columns/accounts_table`
  **key** would let a flag persisted as `columns/accounts_reveal` pass the leg
  meant to fail on it. **Not covered:** persistence to the *vault* settings store
  (where `clipboard_clear_seconds` lives) — this leg observes the window INI
  only; §11 records that gap.

- **INV-7** — After the user sorts by any column, Update, Delete and Forget
  statement password act on the account the user has selected, not on the
  parallel-list entry sitting at that visual row index.
  *Test:* `tests/features/accounts/test_accounts.py` — fill several accounts,
  sort **descending by Name**, select a row, then drive **each of the three
  handlers in turn** and assert the *stored effect* landed on the selected
  account: `_on_update` renames that account (and no other) as read back through
  `AccountService.list_accounts()`; `_on_delete` removes that account and leaves
  the rest; `_on_forget_password` clears that account's saved password and
  leaves another account's intact.
  *Breaks when:* a handler reads `self._table.currentRow()` as an index into
  `self._rows` instead of calling `_table_state.selected_index`. Asserting only
  that `selected_index` resolves correctly would **not** catch this — that
  helper is already covered by `tests/features/table_state/`, and the broken
  handler never calls it, so the leg would pass in exactly the state it names.
  This is the money-adjacent one: it deletes the wrong account silently.

- **INV-8** — The table's `objectName` is `accounts_table`, distinct from every
  other table passed to `remember_columns`.
  *Test:* `tests/features/table_state/test_table_state.py`, extending the
  existing objectName coverage.
  *Breaks when:* the `objectName` is left unset, so the saved header state
  lands under the empty `"columns/"` key shared with any other unnamed table
  and the two cross-corrupt each other's layout — the FIBR-0012 defect.

- **INV-9** — The Status column orders by reconciliation **severity**, not by
  its rendered string: an ascending sort puts every `OFF` account above every
  quiet account, and every quiet account above every `RECONCILED` one. Its
  **text** composes the reconciliation marker first and the 🔑 marker second,
  `" · "`-joined, absent parts omitted — a deliberate reversal of today's order
  (§4.2).
  *Test:* `tests/features/accounts/test_accounts.py`, over **five** accounts
  covering all three ranks and both quiet shapes: an `OFF` account, a quiet
  account with **no** marker at all (empty cell), a quiet account with the 🔑
  marker **only**, a `RECONCILED` account, and a `RECONCILED` account with a 🔑.
  Assert the full ascending row order is OFF → quiet → quiet → RECONCILED →
  RECONCILED, and separately assert the composed text for all four
  marker × key combinations.
  *Breaks when:* the cell is a plain `QTableWidgetItem` and orders by codepoint.
  A two-rank assertion cannot detect that: `⚠` is U+26A0 (9888) and `✓` is
  U+2713 (10003), so a lexical sort **already** puts OFF above RECONCILED and
  passes. Only the middle rank discriminates — an empty cell sorts *first*
  lexically but *between* by rank, and a 🔑-only cell (U+1F511) sorts *last*
  lexically but *middle* by rank — which is why both quiet shapes are required.

- **INV-11** — A reveal re-masks on its own after `_REVEAL_SECONDS`; switching
  it off by hand cancels the pending timer so it cannot fire across a later
  reveal; and a `_refresh()` from any other cause leaves the pending interval
  untouched rather than extending it.
  *Test:* `tests/features/accounts/test_accounts.py` — a `qtbot` test driving
  the widget's timer directly rather than waiting `_REVEAL_SECONDS` in real
  time, asserting each clause against a named observable:
  `self._reveal_timer.isSingleShot()` is `True`; after a manual uncheck
  `isActive()` is `False`; and `remainingTime()` is **non-increasing** across an
  unrelated `_refresh()` (an Add) rather than jumping back to the full interval.
  *Breaks when:* the timer is left repeating instead of single-shot, or is not
  stopped on a manual uncheck — a stale timer then re-masks a reveal the user
  started seconds ago, and the box appears to toggle itself. Or `_refresh()`
  restarts it, so editing accounts holds a reveal open indefinitely. Driving the
  timer alone observes none of the three: `isSingleShot` is what a repeating
  timer fails, and only `remainingTime()` can see an extension.

- **INV-12** — Typing an account number and a note into the form and pressing
  Add stores both and clears the form; re-selecting that account repopulates
  both form fields with the **normalised stored value** (FIBR-0193's
  `_normalise_optional` strips, so `" 1234 "` comes back as `"1234"` — not
  verbatim what was typed).
  *Test:* `tests/features/accounts/test_accounts.py` — a `qtbot` test typing
  into both new fields, pressing Add, then asserting in order: (a) the three
  `QLineEdit`s are empty and the Type picker still holds its prior selection
  (the post-Add state, which the `_refresh()` that follows must not undo);
  (b) the new row's **Note** cell carries the normalised value; (c) the new
  row's **Account-number** cell carries `_mask_account_number(value)` — the
  masked form, because reveal is off (INV-6), **not** the typed value; and
  (d) after re-selecting the row, both form fields carry the normalised value.
  *Breaks when:* the two `QLineEdit`s are built and laid out but never read by
  `_on_add` / `_on_update`, or never written by `_on_selection_changed`. Every
  other invariant here passes in that state — the user types a note, presses
  Add, and it vanishes with no error. Asserting the typed value in the
  *Account-number cell* would invert the leg: it would fail against a correct
  implementation and pass only against one that renders the number unmasked,
  shipping §3 decision 2 broken with every other invariant green.

- **INV-15** — `_select_account(account_id)` selects the row displaying that
  account, whatever the current sort order — it resolves the id to a position
  in `self._rows` rather than passing the id to `select_by_index`, and selects
  nothing for an unknown id.
  *Test:* `tests/features/accounts/test_accounts.py` — fill several accounts,
  sort descending by Name, call `_select_account` with a known id, assert the
  selected row's Name cell is that account's; then call it with an absent id and
  assert the selection is **unchanged** (not cleared — §4.2).
  *Breaks when:* the id is passed straight to
  `_table_state.select_by_index`, which matches the **insertion index** written
  by `tag_row`. Ids are 1-based database keys and indices are 0-based
  positions, so the two silently disagree: the edit form is pre-loaded from a
  different account than the one the caller asked for. INV-7 does not catch
  this — it covers the handlers that resolve *out of* a selection, not the one
  that creates one.

- **INV-16** — The edit form's account-number field is masked whenever reveal is
  off: its echo mode is `Password` with the toggle off and `Normal` with it on,
  and it stays editable in both states.
  *Test:* `tests/features/accounts/test_accounts.py` — select an account with a
  stored number; assert `echoMode()` is `Password` and that **`displayText()`**
  is masked while `text()` still returns the raw value (a `Password` field's
  `text()` is never masked — asserting on it would fail and invite weakening the
  leg); toggle reveal, assert `Normal` and that `displayText()` now equals
  `text()`; type in both states and assert the typed value reaches the service.
  *Breaks when:* only the table cell is masked and the form is left plain. The
  form fills on every row selection, so the number would be on screen for the
  whole of any edit — defeating §3 decision 2 on the same screen that masks the
  column, and in any screenshot taken while editing.

- **INV-17** — The Accounts table's columns are user-reorderable and its layout
  survives a rebuild: after moving and resizing a section, a freshly constructed
  `AccountsWidget` restores that order and those widths.
  *Test:* `tests/features/table_state/test_table_state.py`, alongside the
  existing per-table round-trip coverage.
  *Breaks when:* `remember_columns` is never called on the table — in which case
  every other invariant here still passes while §1's headline promise, and the
  whole of §2 consequence 3, silently go unfixed. INV-8 does not catch this: it
  asserts only that the `objectName` string is right, which is true of a table
  nobody registered.

- **INV-18** — Repopulating the table while a sort is active never mis-pairs
  cells: every row's five cells belong to the same account after a refresh.
  *Test:* `tests/features/accounts/test_accounts.py` — with several accounts
  whose column orderings differ, sort by Name ascending and again descending,
  refresh under each, and assert row-wise that all five cells (Name, Type,
  Account number, Note, Status) resolve to one account.
  *Breaks when:* the fill is not wrapped in `_table_state.fill_guard`. With
  sorting enabled Qt re-sorts on each `setItem`, so a row acquires cells from
  whichever account occupied that visual position mid-fill — the same hazard
  that keeps `enable_sorting` off the Forecast table (§9), and the reason every
  sorted table in this codebase wraps its fill.

- **INV-19** — Toggling reveal preserves the user's in-progress edit: the
  selected account stays selected, the four form inputs keep whatever the user
  had typed, and the Forget button's enabled state is unchanged.
  *Test:* `tests/features/accounts/test_accounts.py` — select an account, type
  new text into the name and note fields without saving, toggle reveal on and
  off, and assert the selection, all four inputs and the Forget button are as
  they were.
  *Breaks when:* `_on_reveal_toggled` re-selects without blocking the table's
  signals (§4.3 step 5), so `_on_selection_changed` fires and repopulates every
  field from storage — silently discarding what the user was typing. The reveal
  toggle is the one control a user is likely to reach for *mid-edit*, which is
  what makes this reachable rather than theoretical.

- **INV-20** — The Account-number **column** renders
  `_mask_account_number(account.account_number)` while reveal is off and the raw
  stored value while reveal is on, for every row.
  *Test:* `tests/features/accounts/test_accounts.py` — two accounts, one with a
  10-character number and one with none; assert the column's `item.text()` is
  `"•••• 7890"` and `""` respectively with reveal off, toggle reveal on and
  assert the first is now the full raw value, toggle off and assert it is masked
  again.
  *Breaks when:* `_refresh()` writes `account.account_number` into the cell
  unconditionally, so the number is on screen from the moment the tab opens.
  §3 decision 2 is this spec's central security decision and the cell is its
  primary surface; INV-5 covers only the pure helper, INV-16 only the form
  field, and INV-6 only the checkbox — INV-16's own *Breaks when* ("only the
  table cell is masked and the form is left plain") assumes cell masking is
  guaranteed somewhere, and without this invariant it is not.

- **INV-21** — The table is click-sortable: `isSortingEnabled()` is `True` on a
  constructed widget, and clicking a header section reorders the rows.
  *Test:* `tests/features/accounts/test_accounts.py` — assert
  `self._table.isSortingEnabled()`, then fill three accounts, call
  `horizontalHeader().sectionClicked` on the Name section (or
  `sortByColumn`) and assert the Name-column order reverses on a second click.
  *Breaks when:* `enable_sorting(self._table)` is omitted from `__init__`. Every
  other invariant here still passes — `QTableWidget.sortItems()` works whether
  or not `setSortingEnabled` was ever called, so INV-7 / INV-9 / INV-15 /
  INV-18's "sort descending by Name" steps all succeed while the user cannot
  click a header at all, which is §2 consequence 1, the headline motivation.
  This is the same gap INV-17 closes for the sibling `remember_columns` call.

- **INV-22** — `_refresh()` leaves the table with **no selection**, whatever
  sort is active — so no stale selection can survive a repopulate and resolve
  to a different account.
  *Test:* `tests/features/accounts/test_accounts.py` — with three accounts whose
  name order differs from their insertion order, sort descending by Name, then
  for **each** visual row in turn: select it, call `_refresh()`, and assert
  `_table_state.selected_index(self._table)` is `None` and
  `self._table.selectedItems()` is empty.
  *Breaks when:* the fill omits the leading `setRowCount(0)` and reuses rows the
  way `StatementsWidget.refresh` does — §8 owns the mechanism and the measured
  drift. **Every row must be driven, not one:** the middle row of a three-row
  descending sort is the sort's fixed point and does not drift, so a single-row
  leg passes in the broken state.

## 6. Failure modes

- **Existing widget tests break on the `QListWidget` → `QTableWidget` swap.**
  Several legs of `tests/features/accounts/test_accounts.py` walk
  `widget._list`, and two of them read `item.data(Qt.ItemDataRole.UserRole)` as
  the account id — `_table_state._ROW_INDEX_ROLE` **is**
  `Qt.ItemDataRole.UserRole`, so after the rewrite the same call returns a row
  index and the assertions go quietly wrong instead of failing loudly. (§4.2
  records the same collision's source-side half.) Every such leg is re-pointed
  at the table as part of this work (§12).
- **`tests/features/reconciliation/test_reconciliation_marker.py` needs its row
  lookup re-derived, not re-pointed.** Its module docstring says "The suffix is
  asserted on the `QListWidgetItem` text", and its `_row_text` helper finds a row
  by testing `if name_substr in text` against `widget._list.item(i).text()` —
  i.e. it matches the account **name** and reads the **marker** out of the *same
  string*. Once name and status are separate cells there is no such string: the
  helper must find the row by its Name cell and then read the Status cell. A
  mechanical `_list` → `_table` swap will not compile into anything meaningful.
- **A vault at v12 with no `account_number` / `note` columns.** Not this item's
  failure mode — FIBR-0193 owns the migration and is this spec's blocker. If
  this table ships first, `Account` has no such attributes and `_refresh()`
  raises `AttributeError` on the first row. Stated so the ordering is a recorded
  dependency rather than an assumption.
- **A stale saved column layout.** `accounts_table` has no saved state on first
  run, so the header takes its defaults. A layout saved by a future build with
  a different column count restores partially — `restoreState` returns `True`
  and leaves the column count alone. There is no escape hatch today: Reset
  layout does not clear column state, which is FIBR-0192's (§9). A user hitting
  this before that ships must delete the `columns/accounts_table` key by hand.
- **The auto-hide timer fires around a lock.** The timer is parented to the
  widget, so the widget's destruction takes it down — but `_clear_live` uses
  `deleteLater()`, a *deferred* delete, and `_lock()` locks the vault **before**
  it. So an already-queued timeout can still reach `_on_reveal_timeout` →
  `_on_reveal_toggled` → `_refresh()`, which reads the now-locked vault. Every
  other handler in this widget already swallows `VaultLockedError` silently;
  `_refresh()` gains the same guard around its service reads (§4.2), which is
  the narrow reason it needs one. §4.1's "reveal cannot outlive a lock without
  any extra code" is about the *checkbox state*, which is still true — the guard
  is about the timeout that can land between the vault locking and the widget
  being deleted.
- **A `_refresh()` while revealed** — triggered by Add, Update, Delete, Forget,
  the reveal toggle itself, or `MainWindow._refresh_tab` on every activation of
  the Accounts tab — re-renders unmasked and does **not** restart the timer, so
  neither editing accounts nor switching tabs can extend the exposure window
  (INV-11).
- **Switching away from the Accounts tab mid-edit and back.**
  `MainWindow._refresh_tab` calls `self._accounts_tab._refresh()` on every
  activation, so the selection is dropped (INV-22) while the form keeps whatever
  was typed — the user returns to a populated form with nothing selected, and
  Update does nothing until they re-select. This matches today's behaviour
  exactly (today's `_refresh()` calls `self._list.clear()`), so it is recorded
  as a known consequence of decision 6 rather than a regression, and is out of
  scope (§9).
- **An account number long enough to widen the column.** Masked display is
  bounded at 9 characters, and the column is user-resizable and remembered, so
  a long number costs nothing while masked and is the user's problem to size
  while revealed. A pathologically long **note** (FIBR-0193 §4.1 imposes no cap)
  widens its column the same way; it is display-only, so the cost is layout, not
  correctness.
- **Sorting with an empty Status cell.** An account with no reconciliation
  marker *and* no saved password renders `""` with severity rank 1, so it sorts
  between the failures and the reconciled accounts rather than clumping at one
  end by string order. An account with a saved password but a quiet
  reconciliation status renders the 🔑 marker alone, still at rank 1. INV-9
  requires both shapes precisely because they are the only discriminating cases.

disambiguated by per-invariant `Source: FIBR-0128 INV-N` lines. This spec's
invariants follow that same existing convention: a block under a
`## FIBR-0113 — …` heading with `Source:` lines. FIBR-0193 adds one the same way.
Two notes on this block: its ids are **non-contiguous** (INV-5–INV-9, INV-11,

spec-format §3.7 forbids renumbering; and those headings are **unnumbered**, so
`testing.md` §2.3's citation form (`# INV-3 from spec.md § 2.1`) resolves here by
heading *name*, not by section number.

Per `docs/standards/testing.md`, every one of these is run against
pre-implementation source and seen to fail before the implementation is written.
That is trivially true for legs in a file that does not yet exist; for these,
which extend two existing files, it is a real check — each leg is added, run
against the current `QListWidget` widget, and seen to fail before the rewrite.

The `qtbot` legs assert behaviour on a constructed widget; they do **not**
prove the tab renders correctly inside `MainWindow`. The one exception is
INV-6 leg (c), which builds a `MainWindow` solely to drive a lock cycle — it
still asserts nothing about rendering.

## 8. Alternatives considered (and rejected)

- **Four columns, markers left on the Name cell.** Rejected by the user: the
  reconciliation warning stays unsortable, which is consequence 1.
- **Six columns, splitting the password marker from the reconciliation
  marker.** Rejected by the user as too wide for two rarely-set flags.
- **Show account numbers in full.** Rejected by the user — see §3 decision 2
  for the reasoning.
- **Mask with no reveal.** Rejected: a user who needs the full number to pay
  someone would have to open the vault file to get it back.
- **Move editing into an Add/Edit dialog.** Rejected by the user: more work,
  and it adds a click to every edit for a form that still fits on the tab.
- **`_refresh()` reusing rows, as `StatementsWidget.refresh` does.** Rejected on
  evidence, not preference — this was the draft's design until cold-eyes loop 5.
  Reproduced against real Qt with three accounts (`Alpha`, `Mid`, `Zed`) under a
  Name-descending sort (`docs/reviews/FIBR-0113-selection-drift-repro.py`):
  selecting visual row 0 left `selected_index` resolving to `Alpha` where it had
  been `Zed`, and row 2 resolved to `Zed` where it had been `Alpha`. Row 1 — the
  sort's fixed point — did not drift, which is why INV-22 drives every row.
  Clear-then-fill was verified to clear the selection. See §3 decision 6.
  **Code-side note:** `StatementsWidget.refresh` carries this same latent drift
  today, harmlessly, because its `_on_selection_changed` toggles two buttons and
  touches no form. Tracked separately as **FIBR-0194** — not fixed here, because
  this is a docs change and that is a different widget.
- **`_refresh()` ending with `self._on_selection_changed()`, copying the
  sibling verbatim.** Rejected — see §3 decision 7: the two handlers do
  different amounts of work, so the line that is harmless in `StatementsWidget`
  makes every refresh clobber the form here.
- **Re-selecting the previous account inside `_refresh()`** so the selection
  survives a tab switch. Rejected: it would repopulate the form with the account
  just added, defeating `_on_add`'s field-clearing, and it changes today's
  behaviour (§6). Only `_on_reveal_toggled` re-selects, because only it must
  preserve a mid-edit state.
- **A generic column-customisation layer for FIBR-0084.** Rejected: it already
  exists as `remember_columns` and covers six tables. Building a second one
  would duplicate it — `coding.md` §1.3 prefers reuse and permits justified
  duplication, and there is no justification here.
- **Convert Categories' tree too, for FIBR-0084 completeness.** Rejected — see
  §2's closing paragraph, which owns the reason.
- **Carrying FIBR-0084's remaining surfaces here** (the Forecast table, the
  Home dashboard trees, the Reset-layout gap). Rejected — see §3 decision 8.
- **Carrying the schema and repository work here.** Rejected — see §13; it is
  FIBR-0193, and it ships first.

## 9. Out of scope

- **The two new columns' storage** — the migration, `models.Account`, and the
  repository and service signatures. Tracked by **FIBR-0193**, this spec's
  blocker.
- Finishing FIBR-0084 — its three remaining gaps, enumerated here as the single
  home for that list: (1) the Forecast events table has no column persistence;
  (2) the Home dashboard breakdown trees have none either; (3) Reset layout does
  not clear saved column state. Tracked by **FIBR-0192**, which is FIBR-0084's
  blocker. That bullet also carries the two hazards found while scoping it: the
  Forecast fill is not wrapped in `fill_guard`, so sorting must not be enabled
  there without wrapping it first (the hazard INV-18 locks on *this* table); and
  `remember_columns` is typed for `QTableWidget`, so the Home trees need the
  parameter widened.
- Making `_REVEAL_SECONDS` user-configurable, as the clipboard auto-clear delay
  already is. **A decision, not a deferral — no follow-up id.** One fixed
  constant is the shortest correct form of what was asked for, and a settings
  key nobody has asked to change is scaffolding. If it is ever wanted it
  follows the existing `clipboard_clear_seconds` pattern exactly.
- Preserving the selection across a tab switch (§6). **A decision, not a
  deferral — no follow-up id.** It matches today's behaviour, and changing it
  would require `_refresh()` to re-select, which §8 rejects.
- Column customisation on the Categories tree — **a permanent decision, not a
  deferral, so no follow-up id**; see §2 for the reason.
- The latent selection drift in `StatementsWidget.refresh` — tracked by
  **FIBR-0194** (§8).
- Live language switching for the new widgets — tracked by FIBR-0017 (P12
  i18n). This is a standing **departure from `coding.md` §5.2**, which asks for
  `changeEvent` / `retranslateUi` from P02: no file under `src/finbreak` has
  either today, so every `tr()` string is bound at construction and the labels
  added here inherit that. Recorded as a departure rather than left silent,
  since the spec records its other two: `testing.md` on the non-contiguous
  `spec.md` INV block (§7), and spec-format §2's mandatory plan (§12).

## 10. Resource cost

No new external dependency, no new module, no new build target. One `QTimer`
per `AccountsWidget`, parented to it. The parallel `self._rows: list[Account]`
and `self._with_pw: set[int]` replace per-item `setData` storage of the same
facts — but not identically: the old scheme stashed four scalars per row (id,
name, type, has-pw), where `self._rows` retains whole `Account` objects, which
additionally carry `created_at`, `account_number` and `note`. Still bounded by
the account count, and still a handful of rows in any real vault.

One cost is **unattended** and so worth naming: every reveal toggle *and* every
auto-hide runs a full `_refresh()`, which is `list_accounts()` +
`account_ids_with_pdf_password()` + `ReconciliationService.account_statuses()` (a
statement-period walk per account) + the money-display reads. That is the same
work a tab activation already does, on a table of one row per account, so it is
accepted rather than optimised into a column-only re-render — but it fires on a
timer rather than on a user action, which is why it is recorded here.
