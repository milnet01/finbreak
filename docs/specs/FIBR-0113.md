# FIBR-0113 — Show accounts in a sortable 5-column table, account number masked

**Status:** spec draft (2026-07-30).
**Kind:** feature.
**Source:** ROADMAP FIBR-0113 (user-request-2026-07-12, screenshot). FIBR-0084
scope-checked; its remaining surfaces split to FIBR-0192. The storage half of
this item's original draft split to FIBR-0193 on 2026-07-28, and the reveal half
to FIBR-0198 on 2026-07-30 (§13).
**Blocked by:** FIBR-0193 (this table renders and edits `Account.account_number`
and `Account.note`, which that item creates).
**Blocker for:** FIBR-0198 (§9 — it reveals the number this item masks, and
needs this item's table, mask helper, form field and gating helper to exist).
**Pairs with:** FIBR-0084 (§9 — this spec unblocks its Accounts surface only and does
**not** close it; FIBR-0192 is its blocker), FIBR-0117 (§2 — shipped the
`_table_state` seam this reuses), FIBR-0005 / FIBR-0128 / FIBR-0177 (§12 — this
spec amends invariants in all three).

**Layman:** The Accounts tab becomes a proper table — Name, Type, Account
number, Note and Status — that you can sort, resize and reorder, instead of one
cramped line per account. Account numbers show as dots plus the last four
digits, enough to tell two accounts apart without putting the whole number on
screen.

## 1. Goal

The Accounts tab lists each account as a row in a real table with five sortable
columns — Name, Type, Account number, Note, Status — whose widths and order the
user can change and which finbreak remembers. The two optional per-account
fields FIBR-0193 stores (a reference account number and a free-text note) gain
their first user-facing surface: they can be entered and edited on the tab. The
account number is masked wherever it is displayed; FIBR-0198 adds the way to
reveal it.
Accounts also gains a header for the first time, so it can finally join the
shared remembered-column scheme — one of the three surfaces FIBR-0084 needs;
the other two are FIBR-0192's (§9).

## 2. Problem

`src/finbreak/ui/accounts.py::AccountsWidget` renders accounts into a
`QListWidget`, building one string per row in
`AccountsWidget._refresh()`: `f"{account.name} — {label}"`, then
concatenating up to two suffixes onto it — the remembered-statement-password
marker, and `AccountsWidget._reconciliation_suffix()`'s FIBR-0177 output
(`✓ balances reconcile`, `⚠ off by {money}`, `⚠ {n} periods don't reconcile`).

Three consequences:

1. **Nothing is sortable or scannable.** A list item is one opaque string, so a
   user with a dozen accounts cannot bring the accounts that fail to reconcile
   to the top — which is the only reason that marker exists.
2. **The two new stored fields have nowhere to appear.** FIBR-0193 adds
   `Account.account_number` and `Account.note`, but a one-line list item has no
   room for them and the add/edit form has no inputs for them, so a user with
   two "Cheque" accounts at different banks still cannot tell them apart.
3. **Accounts cannot join the remembered-column-layout scheme.**
   `src/finbreak/ui/_table_state.py::remember_columns()` (shipped by FIBR-0117)
   already delivers most of what FIBR-0084 asks for, and is already called by
   Statements, Transactions, Rules, Recurring, Transfers and the import-wizard
   preview. A `QListWidget` has no header, so Accounts cannot participate at
   all.

Fixing consequence 3 does **not** finish FIBR-0084 — three further gaps remain,
enumerated once in §9 and owned by FIBR-0192, which is FIBR-0084's blocker.
`ui/categories.py::CategoriesWidget` is excluded permanently: its `QTreeWidget`
sets `setHeaderHidden(True)` over a single column, so there is nothing to resize
or reorder. That is this document's one statement of the Categories exclusion;
§8 and §9 point here.

## 3. Scope decisions

Settled with the user on 2026-07-28 (1–3, 8), or by the author from §8's Qt
reproduction (6) and from FIBR-0198's third call site for the gating helper (7).
Decisions **4 and 5** — reveal being session-scoped, and its auto-hide delay —
went to FIBR-0198 with the reveal on 2026-07-30, where they are **its decisions
2 and 3**, and are not restated here. The
numbering is left non-contiguous rather than closed up for the same reason §5's
is: the numbers are permanent handles, cited from §13's frozen loop log, and
renumbering the survivors would silently redirect every one of those citations.

1. **Five columns, with Status as its own column** — not four columns with the
   markers left glued to the Name cell. Chosen so the reconciliation warnings
   become sortable (consequence 1 above).
2. **The account number is masked wherever it is displayed.** The exposure being
   defended against is shoulder-surfing and screenshots, not storage: the value
   already sits inside the SQLCipher vault, encrypted at rest. This document
   owns that reasoning; FIBR-0198 cites it rather than restating it. Masked with
   *no* way to see it is not the end state — §8 records why, and FIBR-0198 adds
   the reveal control on top of this item.
3. **The add/edit form stays inline on the tab**, relaid from one row to a
   two-row grid — not moved into an Add/Edit dialog. Preserves the current
   type-a-name-and-hit-Add flow.
6. **`_refresh()` clears the table before filling it** (author, after cold-eyes
   loop 5). `AccountsWidget._refresh()` today opens with `self._list.clear()`,
   so the selection already drops on every repopulate; clear-then-fill preserves
   that behaviour in the table. The alternative — `StatementsWidget.refresh`'s
   reuse-rows shape, which this spec otherwise takes as its precedent — lets a
   surviving selection ride its item through a re-sort and land on a **different
   account**. §8 owns the mechanism and the reproduction; INV-22 locks the
   cleared-selection property; §4.2 pins the mechanism in code.
7. **The Forget-button rule lives in its own gating-only helper,
   `_apply_forget_gating()`** (author, after cold-eyes loop 5). It is called from
   three sites so the rule has one implementation; §4.3 owns the helper, its
   body and its call sites.
8. **FIBR-0084's remaining surfaces are split out, not carried here** (user,
   after cold-eyes loop 2). Folding them in made this spec the largest source of
   its own review defects. FIBR-0192 owns them; FIBR-0084 stays open until it
   ships.

## 4. Design

### 4.1 Masking

A module-level helper in `ui/accounts.py`:

```python
_MASK = "•" * 4

def _mask_account_number(value: str | None) -> str:
    """Display form: a mask plus the last 4 characters for a value longer than
    4; a bare mask for a value of 1-4 characters (its "last 4" would be all of
    it); an empty cell when there is no number at all."""
    if not value:
        return ""
    return f"{_MASK} {value[-4:]}" if len(value) > 4 else _MASK
```

Masking governs **two** surfaces, not one — the table column and the edit form's
account-number field — and the two use different mechanisms. This paragraph is
this document's one statement of that; INV-20 and §4.3 point here.

- **The table cell** is masked by text substitution, because a
  `QTableWidgetItem` has no echo mode: `_refresh()` writes
  `_mask_account_number(account.account_number)` into it (`INV-20 amended by
  FIBR-0198`, which makes the write conditional on its reveal toggle).
- **The form field** is masked by echo mode alone:
  `self._account_number.setEchoMode(QLineEdit.EchoMode.Password)` in `__init__`,
  and nothing in this item changes it (FIBR-0198's toggle is what makes it
  switchable). The field stays fully editable, exactly like any password box.
  The form is the surface easy to forget: selecting a row populates it, so a
  plain field would put the number on screen whenever anyone clicks an account,
  defeating §3 decision 2 on the same screen that masks the column.

The form field always carries the **raw stored value** — `_mask_account_number`
is for the table cell only and must never reach the form, or an Update would
write `"•••• 7890"` back into the vault as the account number.

### 4.2 The table

`AccountsWidget._list` (`QListWidget`) becomes `AccountsWidget._table`
(`QTableWidget`), built the way `ui/statements.py::StatementsWidget` builds
`statements_table` — the closest sibling, also five columns:

```python
self._table = QTableWidget(0, 5)
self._table.setObjectName("accounts_table")
self._table.setHorizontalHeaderLabels([
    self.tr("Name"), self.tr("Type"), self.tr("Account number"),
    self.tr("Note"), self.tr("Status"),
])
self._table.setEditTriggers(QAbstractItemView.EditTrigger.NoEditTriggers)
self._table.setSelectionBehavior(QAbstractItemView.SelectionBehavior.SelectRows)
self._table.setSelectionMode(QAbstractItemView.SelectionMode.SingleSelection)
enable_sorting(self._table)      # sibling's order; nothing here depends on it
remember_columns(self._table)
```

`self._rows: list[Account]` and `self._with_pw: set[int]` are initialised empty
in `__init__` **before** the table is constructed and its selection signal
connected — as `StatementsWidget.__init__` does for its own parallel list — so a
selection signal emitted during construction or the first fill cannot reach an
unset attribute.

**The fill is clear-then-fill** (§3 decision 6). `_refresh()` reads the vault
and re-assigns `self._rows` and `self._with_pw` **before** entering the guard
(as `StatementsWidget.refresh` does), then inside
`_table_state.fill_guard(...)` calls `self._table.setRowCount(0)`
before `setRowCount(len(self._rows))` and the per-row `setItem` /
`_table_state.tag_row(table, row, index)` calls. The leading `setRowCount(0)`
is the load-bearing line — §8 owns the rejected reuse-rows alternative and the
reproduction, and INV-22 locks the result.

`_refresh()` **ends with `self._apply_forget_gating()`** (§4.3), not with
`self._on_selection_changed()`. **At this call site the two are equivalent**,
and saying otherwise would be wrong: the fill has just cleared the selection
(INV-22), so the sibling's trailing handler would take its no-selection early
return and touch no field. The helper is used anyway because the *rule* needs
one implementation across all three of its call sites, and the third —
FIBR-0198's reveal handler — fires with a selection **live**, where
`_on_selection_changed` would repopulate the form from storage over whatever
the user was typing. §4.3 owns the helper.

The fill also writes the row tags in the right order: `_table_state.tag_row`
reads `table.item(row, 0)` and **silently no-ops when column 0 has no item**,
so it is called *after* that row's `setItem` calls, exactly as
`StatementsWidget.refresh` does. Called first, it tags nothing, every
`selected_index` returns `None`, and every handler no-ops with no error
anywhere — INV-7 goes red, but only after the implementer has debugged a table
that ignores selection entirely.

Row-identity handling follows the `_table_state` contract the sibling tabs use,
because sorting breaks a naive visual-row lookup:

- `_on_selection_changed`, `_on_update`, `_on_delete` and `_on_forget_password`
  resolve the target through `_table_state.selected_index(self._table)` into
  `self._rows`, replacing today's `self._list.currentItem()` +
  `item.data(_ACCOUNT_*_ROLE)` reads. These four are the complete set of
  `currentItem()` readers; `_on_add` correctly has none. The
  `_ACCOUNT_*_ROLE` constants and their `setData` calls are deleted — **six of
  them, not four** (`amended by FIBR-0193`, which adds `_ACCOUNT_NUMBER_ROLE`
  and `_ACCOUNT_NOTE_ROLE` at `UserRole + 4` / `+ 5` and ships first).
  **This deletion is a correctness requirement, not tidying:**
  `_ACCOUNT_ID_ROLE` is `Qt.ItemDataRole.UserRole` and so is
  `_table_state._ROW_INDEX_ROLE`, so a surviving
  `setData(_ACCOUNT_ID_ROLE, account.id)` written on a column-0 item **after**
  that row's `tag_row` call overwrites the row tag, and `selected_index` then returns a **database id used as an index into
  `self._rows`** — off-by-one at best, `IndexError` or the wrong account at
  worst. §6 records the mirror-image hazard on the test side.
  `self._rows` carries three of the four facts — id, name and type are all on
  `Account`. The fourth is **not**: the has-a-saved-statement-password flag
  behind `_ACCOUNT_HAS_PW_ROLE` comes from
  `AccountService.account_ids_with_pdf_password()` and deliberately does not
  live on `Account` (FIBR-0193 INV-4 keeps the credential out of every listing).
  So `_refresh()` also stores `self._with_pw: set[int]` from that same call, and
  `_apply_forget_gating` gates the Forget button on `account.id in self._with_pw`.
  Dropping this member silently disables the FIBR-0128 D3 gating.
- `_select_account(account_id)` **maps the id to a position first**:
  `select_by_index` matches the insertion index written by `tag_row`, not a
  database id, and the two are not interchangeable. It finds the index of the
  `Account` in `self._rows` whose `id` matches and calls `select_by_index` with
  that index. An **absent id leaves the current selection unchanged** — the
  id→index lookup misses, so `select_by_index` is never reached and nothing
  clears the selection. (`select_by_index` also returns silently on its own no
  match, so the behaviour is the same either way.)
  It stays test-only in this item; FIBR-0198's reveal handler is its first
  production caller.
- The selection signal moves from `currentItemChanged` to the table's
  `itemSelectionChanged`.
- `_on_delete` and `_on_forget_password` **keep their target resolved above the
  `QMessageBox.question` call**, acting on the captured `Account` afterwards
  rather than re-resolving below the dialog — which is what today's code does,
  and is easy to lose in a rewrite. It costs nothing here and there is nothing
  in *this* item that can invalidate a selection mid-confirm; the reason it
  matters is FIBR-0198 §4.5, whose auto-hide timer fires inside the confirm's
  nested event loop. Stated here because this is the item that rewrites the two
  handlers, and it ships first.

The Status cell is a `_table_state.SortableItem` whose sort key is a severity
rank, so clicking the header groups problems rather than ordering strings:
`0` = `ReconciliationStatus.OFF`, `1` = the quiet statuses
(`NOT_ENOUGH_DATA` / `NOT_SUPPORTED`), `2` = `RECONCILED`. Its text composes the
reconciliation marker and the 🔑 saved-password marker in that order, joined by
`" · "` and omitting absent parts:
`" · ".join(part for part in (recon_text, key_text) if part)`. That order is a
**deliberate reversal** of today's list line, which appends the 🔑 marker first
and the reconciliation suffix second: the column is sorted by reconciliation
severity, so the reconciliation text leads the cell it is sorted by.

Those marker strings live in four `self.tr(...)` literals in
`_reconciliation_suffix()` and `_refresh()`, each currently beginning with a
`"  ·  "` separator for list-line concatenation. Moving them into a cell means
**editing those four translatable literals** to drop the leading separator —
translation-catalogue churn, not a `removeprefix` hack at the call site.
`_reconciliation_suffix()` keeps its name even though its output is now part of
a cell rather than a suffix; renaming it would touch FIBR-0177's citations for
no behavioural gain.

The other four cells are plain `QTableWidgetItem`s: Name, Type and Note sort
lexically, which is correct. The **Note** cell renders `account.note or ""` —
`Account.note` is `str | None` and `QTableWidgetItem(None)` raises `TypeError`,
so the no-note case (which includes the seeded `Default` account, and therefore
the first fill of almost every vault) has to be handled at the cell. The sibling
does the same for its own optional column (`StatementsWidget.refresh`'s
`source_filename or ""`). The **Type** cell carries the translated label —
`self._type_labels.get(account.type, account.type)`, exactly as today's list
line builds it — not the stored token, or the column ships `credit_card` where
the list showed "Credit card". The Account number column sorts by what is
displayed — the last 4 — which is all a masked column can order by.

### 4.3 The form

`add_row` (today one `QHBoxLayout` of name / type / Add / Update) becomes a
`QGridLayout` of two rows: Name and Type on the first, Account number and Note
on the second, with Add and Update at the end of the second row. Everything else
on the tab is kept verbatim — the `actions` row (`_delete_button`,
`_forget_pw_button`, the stretch, and the `show_done`-gated `_done_button`), the
`_error` label, and the `done` signal — so FIBR-0052 INV-12's tab-mode gating is
untouched. Both new
`QLineEdit`s get `setAccessibleName` alongside their placeholder, matching the
existing `_name` field — a placeholder disappears on typing and is not a
reliable accessible name (WCAG 1.3.1 / 3.3.2). The account-number field is
constructed in `Password` echo mode (§4.1). `_on_selection_changed`
populates all four inputs when an account is selected and **leaves them
untouched when the selection clears**, matching today's behaviour — which
clear-then-fill makes load-bearing, since every `_refresh()` now clears the
selection.

`_on_add` clears the three `QLineEdit`s — name, account number, note — and
**leaves the Type picker on its current selection**, as today. "Clear" is not
applied to the `QComboBox`: `QComboBox.clear()` removes its *items*, which would
destroy the seven type entries and the token-behind-label contract `__init__`
builds.

`_on_add` and `_on_update` pass the raw field text to the service as
`account_number=` / `note=` — FIBR-0193 §4.2 makes both **keyword-only**, so a
positional call raises `TypeError`. The service normalises them.

`_apply_forget_gating()` (§3 decision 7) is the whole of the Forget rule:

```python
def _apply_forget_gating(self) -> None:
    """Enable Forget only for a selected account that has a saved statement
    password (FIBR-0128 D3). Gating ONLY — it never touches the form, so a
    _refresh() cannot overwrite in-progress input."""
    index = selected_index(self._table)
    account = self._rows[index] if index is not None else None
    self._forget_pw_button.setEnabled(
        account is not None and account.id in self._with_pw
    )
```

Two sites call it in this item — `_on_selection_changed` and the end of
`_refresh()`; FIBR-0198's reveal handler is the third, and it is the one that
makes a separate helper necessary rather than tidy. That handler runs with a
selection **live**, so the sibling's shape there (`StatementsWidget.refresh`
ending with `self._on_selection_changed()`) would repopulate all four inputs
from storage mid-edit. The sibling gets away with it because its handler
toggles two buttons and touches nothing else; `AccountsWidget`'s also fills the
form. A gating-only helper is form-safe at every call site, which is why all
three use it rather than two of them using it and one not.

`_on_selection_changed` calls it first, then early-returns on no selection, then
populates the four inputs — the same order today's handler uses, so a cleared
selection still disables the button rather than leaving it stale-enabled.

`_refresh()` does **not** re-select after filling — doing so would make
`_on_add`'s field-clearing useless, because the re-selection would repopulate
the form with the account just added (§8).

## 5. Invariants

Eleven ids are **withdrawn** to other specs and listed at the end of this
section. The live set is therefore non-contiguous by design (spec-format §3.7 —
never renumber). Every live invariant's catcher is tabulated once in §11; the
*Test:* lines below give the leg, not a second copy of the file map.

Four legs (INV-7, INV-15, INV-18, INV-22) share one setup — **several accounts
under a descending Name sort** — because each is asserting that a visual
position is not an index into `self._rows`. A descending sort is what creates
that gap and it is sufficient on its own: `AccountRepository.list_all()` ends
`ORDER BY name COLLATE NOCASE, id`, so `self._rows` is *always* name-ascending
and every visual position differs from its index except the fixed point. (Do
not write the setup as "insertion order differs from name order" — the
repository's ordering makes that unachievable.) It is stated once here and referred to below as *the sorted
setup*. Every account in it carries a **distinct type, account number and
note** as well as a distinct name: without that, two accounts sharing a default
type and empty optional fields render identical cells in three of the five
columns, and INV-18's row-wise pairing check silently degrades to a Name and
Status check.

- **INV-5** — `_mask_account_number` returns a mask plus the last 4 characters
  for a value longer than 4, a bare mask with no digits for a value of 1–4
  characters, and an empty string for `None` or `""`.
  *Test:* `tests/features/accounts/test_accounts.py` — a pure-function leg over `_mask_account_number` — `"1234567890"`,
  `"12345"` (the shortest value taking the last-4 branch), `"1234"`, `"123"`,
  `""`, `None`.
  *Breaks when:* the helper slices `value[-4:]` unconditionally, so a 3-digit
  number renders in full — the mask leaks exactly the values it is shortest
  for.

- **INV-7** — After the user sorts by any column, Update, Delete and Forget
  statement password act on the account the user has selected, not on the
  parallel-list entry sitting at that visual row index.
  *Test:* `tests/features/accounts/test_accounts.py` — the sorted setup, with
  **two** accounts carrying a saved statement password and a **third** account
  as the Delete target; then drive **each of the three handlers in turn,
  re-selecting the target by id (`_select_account`) before each drive**. The
  Delete target must be that third account: aim all three drives at one account
  and the Delete removes it, the next `_select_account` misses (an absent id
  leaves the selection unchanged, and `_refresh()` has just cleared it), and the
  Forget drive early-returns — red against a correct implementation again. The re-selection is not optional: every one of the three
  handlers ends in `self._refresh()`, which leaves no selection (INV-22), so
  handlers 2 and 3 would otherwise take their no-selection early return and do
  nothing — the leg would go red against a correct implementation, and the
  obvious repair (stop clearing the selection) turns INV-22 red instead. Assert
  the *stored effect*
  landed on the selected account: `_on_update`, with a **new** name typed into
  the form first (selection pre-populates it with the current one, so without
  that the rename is unobservable), renames that account and no other as read back through `AccountService.list_accounts()`; `_on_delete`
  removes that account and leaves the rest; `_on_forget_password` clears that
  account's saved password and leaves another account's intact.
  *Breaks when:* a handler reads `self._table.currentRow()` as an index into
  `self._rows` instead of calling `_table_state.selected_index`. Asserting only
  that `selected_index` resolves correctly would **not** catch this — that
  helper is already covered by `tests/features/table_state/`, and the broken
  handler never calls it, so the leg would pass in exactly the state it names.
  This is the money-adjacent one: it deletes the wrong account silently.

- **INV-8** — The table's `objectName` is `accounts_table`, distinct from every
  other table passed to `remember_columns`.
  *Test:* `tests/features/table_state/test_table_state.py`, extending its existing
  objectName coverage.
  *Breaks when:* the `objectName` is left unset, so the saved header state
  lands under the empty `"columns/"` key shared with any other unnamed table
  and the two cross-corrupt each other's layout — the FIBR-0012 defect.

- **INV-9** — The Status column orders by reconciliation **severity**, not by
  its rendered string: an ascending sort puts every `OFF` account above every
  quiet account, and every quiet account above every `RECONCILED` one. Its
  **text** composes the reconciliation marker first and the 🔑 marker second,
  `" · "`-joined, absent parts omitted — a deliberate reversal of today's order
  (§4.2).
  *Test:* `tests/features/accounts/test_accounts.py` — over **five** accounts covering all three ranks and both quiet shapes:
  an `OFF` account, a quiet account with **no** marker at all (empty cell), a
  quiet account with the 🔑 marker **only**, a `RECONCILED` account, and a
  `RECONCILED` account with a 🔑. Assert the full ascending row order is OFF →
  quiet → quiet → RECONCILED → RECONCILED — as **rank grouping**, not as an
  exact five-name sequence, since intra-rank order among the two quiet and the
  two reconciled rows is unspecified. Then separately assert the composed cell
  text for all four marker × key combinations by **exact equality**, not by
  substring: a substring check (`"✓" in text`) passes on a cell that still
  carries the `"  ·  "` prefix §4.2 removes from the four `tr()` literals.
  *Breaks when:* the cell is a plain `QTableWidgetItem` and orders by codepoint.
  A two-rank assertion cannot detect that: `⚠` is U+26A0 (9888) and `✓` is
  U+2713 (10003), so a lexical sort **already** puts OFF above RECONCILED and
  passes. Only the middle rank discriminates — an empty cell sorts *first*
  lexically but *between* by rank, and a 🔑-only cell (U+1F511) sorts *last*
  lexically but *middle* by rank — which is why both quiet shapes are required.

- **INV-12** — Typing an account number and a note into the form and pressing
  Add stores both and clears the form; re-selecting that account repopulates
  both form fields with the **normalised stored value** (FIBR-0193's
  `_normalise_optional` strips, so `" 1234 "` comes back as `"1234"` — not
  verbatim what was typed), with the account-number field still masked.
  *Test:* `tests/features/accounts/test_accounts.py` — a `qtbot` test that
  **first selects an existing row** (so the `_refresh()` that follows genuinely
  fires the selection-cleared path §4.3 mandates, rather than starting from no
  selection where no `itemSelectionChanged` is emitted at all), then types a
  **new, unused name** over the one that selection just loaded — plus both new
  fields — and presses Add. The fresh name is load-bearing: `_on_add` passes
  `self._name.text()` straight to `add_account`, which rejects a duplicate
  (FIBR-0005 INV-3) and returns *before* clearing the form, so a leg that reuses
  the selected account's name fails its own step (a). Then assert, in order: (a) the three
  `QLineEdit`s are empty and the Type picker
  still holds its prior selection (the post-Add state, which the `_refresh()`
  that follows must not undo); (b) the new row — located **by its Name
  cell**, as INV-20 does, since a fill under an active sort puts it at no
  predictable index — has a **Note** cell carrying the
  normalised value; (c) that row's **Account-number** cell carries
  `_mask_account_number(value)` — the masked form, **not** the typed value; and
  (d) after re-selecting the row, both form fields' `text()` carry the
  normalised value while the account-number field's `echoMode()` is still
  `Password` and its `displayText()` **differs from** its `text()` (the echo
  character is platform-dependent, so there is no literal to assert). Leg (d)
  also asserts the echo
  mode on a **freshly constructed widget, before any selection** — the
  construction-time half of §4.1, and the only leg that observes it. Finally
  (e): re-select a row, type a new name **without saving**, call `_refresh()`
  directly, and assert `self._name.text()` still carries the typed value. That
  is the only leg that falsifies §4.3's leaves-them-untouched clause — leg (a)
  cannot, because it asserts the fields are *empty* at a point where `_on_add`
  has already cleared them, so a handler that **clears** the form on a cleared
  selection passes it identically while silently wiping in-progress input on
  every tab activation.
  *Breaks when:* the two `QLineEdit`s are built and laid out but never read by
  `_on_add` / `_on_update`, or never written by `_on_selection_changed`. Every
  other invariant here passes in that state — the user types a note, presses
  Add, and it vanishes with no error. Leg (d)'s echo-mode clause catches the
  second failure: a field built plain rather than `Password` puts the raw number
  on screen on every row selection, which is §3 decision 2 broken on the form
  surface while INV-20 keeps the column honest. Asserting the typed value in the
  *Account-number cell* would invert leg (c): it would fail against a correct
  implementation and pass only against one that renders the number unmasked.

- **INV-15** — `_select_account(account_id)` selects the row displaying that
  account, whatever the current sort order — it resolves the id to a position
  in `self._rows` rather than passing the id to `select_by_index`, and selects
  nothing for an unknown id.
  *Test:* `tests/features/accounts/test_accounts.py` — the sorted setup; call
  `_select_account` with a known id **whose value differs from that account's
  index in `self._rows`** (pick it explicitly — the seeded `Default` account has
  `id == 1` and can easily sit at index 1, where the id-passed-straight-through
  bug selects the same row and the leg passes green); assert the selected row's
  Name cell is that account's; then call it with an absent id
  and assert the selection is **unchanged** (not cleared — §4.2).
  *Breaks when:* the id is passed straight to
  `_table_state.select_by_index`, which matches the **insertion index** written
  by `tag_row`. Ids are 1-based database keys and indices are 0-based
  positions, so the two silently disagree: the edit form is pre-loaded from a
  different account than the one the caller asked for. INV-7 does not catch
  this — it covers the handlers that resolve *out of* a selection, not the one
  that creates one.

- **INV-17** — The Accounts table's columns are user-reorderable and its layout
  survives a rebuild: after moving and resizing a section, a freshly constructed
  `AccountsWidget` restores that order and those widths.
  *Test:* `tests/features/table_state/test_table_state.py`, alongside its existing
  per-table round-trip coverage, whose
  `test_columns_are_movable_and_order_persists_across_rebuild` is the direct
  precedent.
  *Breaks when:* `remember_columns` is never called on the table — in which case
  every other invariant here still passes while §1's headline promise, and the
  whole of §2 consequence 3, silently go unfixed. INV-8 does not catch this: it
  asserts only that the `objectName` string is right, which is true of a table
  nobody registered.

- **INV-18** — Repopulating the table while a sort is active never mis-pairs
  cells: every row's five cells belong to the same account after a refresh.
  *Test:* `tests/features/accounts/test_accounts.py` — the sorted setup, run **both** ascending and descending, refreshing
  under each; assert row-wise that all five cells (Name, Type, Account number,
  Note, Status) resolve to one account.
  *Breaks when:* the fill is not wrapped in `_table_state.fill_guard`. With
  sorting enabled Qt re-sorts on each `setItem`, so a row acquires cells from
  whichever account occupied that visual position mid-fill — the same hazard
  that keeps `enable_sorting` off the Forecast table (§9), and the reason every
  sorted table in this codebase wraps its fill.

- **INV-20** — The Account-number **column** renders
  `_mask_account_number(account.account_number)` for every row, whatever the
  sort order and whatever the user is doing. (`INV-20 amended by FIBR-0198`, which
  narrows this to its reveal-off state.)
  *Test:* `tests/features/accounts/test_accounts.py` — two accounts, one with a
  10-character number — `"1234567890"`, as INV-5 uses, since the asserted
  literal pins its last four — and one with none, each row located **by its Name
  cell**
  (an empty Account-number cell is otherwise indistinguishable from a mis-filled
  one); assert the column's `item.text()` is `"•••• 7890"` and `""`
  respectively, on the first fill and again after a `_refresh()` driven by an
  Add.
  *Breaks when:* `_refresh()` writes `account.account_number` into the cell
  unconditionally, so the number is on screen from the moment the tab opens.
  §3 decision 2 is this spec's central security decision and the cell is its
  primary surface; INV-5 covers only the pure helper, and INV-12 leg (d) only
  the form field.

- **INV-21** — The table is click-sortable: `isSortingEnabled()` is `True` on a
  constructed widget, and clicking a header section reorders the rows.
  *Test:* `tests/features/accounts/test_accounts.py` — assert
  `self._table.isSortingEnabled()`, then fill three accounts and drive the header
  the way a click does: `horizontalHeader().setSortIndicator(0, ...)` twice, once
  per order, asserting the Name-column order reverses. **Not `sortByColumn`** —
  that sorts whether or not sorting was ever enabled, so it passes in the exact
  broken state below; the `isSortingEnabled()` assertion and the sort-indicator
  path are the two clauses that discriminate.
  *Breaks when:* `enable_sorting(self._table)` is omitted from `__init__`. Every
  other invariant here still passes — `QTableWidget.sortItems()` works whether
  or not `setSortingEnabled` was ever called, so INV-7 / INV-15 / INV-18 /
  INV-22's "sort descending by Name" steps all succeed while the user cannot
  click a header at all, which is §2 consequence 1, the headline motivation.
  This is the same gap INV-17 closes for the sibling `remember_columns` call.

- **INV-22** — `_refresh()` leaves the table with **no selection**, whatever
  sort is active — so no stale selection can survive a repopulate and resolve
  to a different account.
  *Test:* `tests/features/accounts/test_accounts.py` — the sorted setup at exactly three accounts, then for **each** visual
  row in turn: select it, call `_refresh()`, and assert
  `_table_state.selected_index(self._table)` is `None` and
  `self._table.selectedItems()` is empty.
  *Breaks when:* the fill omits the leading `setRowCount(0)` and reuses rows the
  way `StatementsWidget.refresh` does — §8 owns the mechanism and the measured
  drift. Every row is driven because it is cheap and mirrors §8's reproduction —
  **not** because a single row would miss the breach: under the reuse-rows fill
  no row's selection is dropped, so either assertion goes red whichever row is
  chosen. (The fixed-point argument belongs to §8's *drift* property — which
  account a surviving selection resolves to — not to this no-selection one.)

## 6. Failure modes

- **Existing widget tests break on the `QListWidget` → `QTableWidget` swap.**
  Several legs of `tests/features/accounts/test_accounts.py` walk
  `widget._list`, and two of them read `item.data(Qt.ItemDataRole.UserRole)` as
  the account id — `_table_state._ROW_INDEX_ROLE` **is**
  `Qt.ItemDataRole.UserRole`, so after the rewrite the same call returns a row
  index and the assertions go quietly wrong instead of failing loudly. (§4.2
  records the same collision's source-side half.) **Three legs read the 🔑 marker out of
  the row's single text string** — each testing `_PW_MARKER_PHRASE in
  widget._list.item(i).text()` — and **two of them are the same two legs just
  named**, so those two carry both faults at once. §4.2 moves the marker into
  the **Status** cell, so re-pointing them at column 0 reads the Name cell and
  never finds the phrase. All three are re-derived off column 4 (the two
  dual-fault legs losing their `UserRole` id read in the same edit); the
  remaining `_list` walkers are re-pointed (§12).
- **A third leg must be re-derived, not re-pointed — and it is a security
  guard.** `test_INV1_widget_never_renders_or_reads_the_secret` sweeps a
  **literal** role list — `AccessibleTextRole`, `UserRole`, `+1`, `+2`, `+3` —
  over every `widget._list` item, asserting the password sentinel appears under
  none of them. Re-pointed mechanically at the table it keeps passing while
  checking far less than it reads as checking. Of the five roles it names, only
  `+2` and `+3` genuinely go unwritten; `AccessibleTextRole` is a Qt built-in
  this spec never touches, and `UserRole` / `+1` are **re-purposed** by
  `_table_state` into `_ROW_INDEX_ROLE` and `_SORT_KEY_ROLE` — row mechanics
  that could never hold a password. So the sweep degrades to column 0's text and
  tooltip plus two roles it cannot fail on, while the four *other* columns —
  including the Account-number cell — go unswept entirely. It has to be
  re-derived to sweep what the new implementation actually renders: every cell's
  `text()` and `toolTip()` across all five columns, plus the two `_table_state`
  roles. A guard that still passes while covering less is worse than the
  quietly-wrong assertions above, because it produces no signal at all.
- **`tests/features/reconciliation/test_reconciliation_marker.py` needs its row
  lookup re-derived, not re-pointed.** Its module docstring says "The suffix is
  asserted on the `QListWidgetItem` text", and its `_row_text` helper finds a row
  by testing `if name_substr in text` against `widget._list.item(i).text()` —
  i.e. it matches the account **name** and reads the **marker** out of the *same
  string*. Once name and status are separate cells there is no such string: the
  helper must find the row by its Name cell and then read the Status cell. A
  mechanical `_list` → `_table` swap will not compile into anything meaningful.
- **A vault at v12 with no `account_number` / `note` columns.** Not this item's
  failure mode — FIBR-0193 owns the migration and is this spec's blocker. If
  this table ships first, `Account` has no such attributes and `_refresh()`
  raises `AttributeError` on the first row. Stated so the ordering is a recorded
  dependency rather than an assumption.
- **A stale saved column layout.** `accounts_table` has no saved state on first
  run, so the header takes its defaults. A layout saved by a future build with
  a different column count restores partially — `restoreState` returns `True`
  and leaves the column count alone. There is no escape hatch today: Reset
  layout does not clear column state, which is FIBR-0192's (§9). A user hitting
  this before that ships must delete the `columns/accounts_table` key by hand.
- **Switching away from the Accounts tab mid-edit and back.**
  `MainWindow._refresh_tab` calls `self._accounts_tab._refresh()` on every
  activation, so the selection is dropped (INV-22) while the form keeps whatever
  was typed — the user returns to a populated form with nothing selected, and
  Update does nothing until they re-select. This matches today's behaviour
  exactly (today's `_refresh()` calls `self._list.clear()`), so it is recorded
  as a known consequence of decision 6 rather than a regression, and is out of
  scope (§9).
- **An account number long enough to widen the column.** Masked display is
  bounded at 9 characters, and the column is user-resizable and remembered, so
  a long number costs nothing. A pathologically long **note** (FIBR-0193 §4.1
  imposes no cap) widens its column; it is display-only, so the cost is layout,
  not correctness.
- **Sorting with an empty Status cell.** An account with no reconciliation
  marker *and* no saved password renders `""` with severity rank 1, so it sorts
  between the failures and the reconciled accounts rather than clumping at one
  end by string order. An account with a saved password but a quiet
  reconciliation status renders the 🔑 marker alone, still at rank 1. INV-9
  requires both shapes precisely because they are the only discriminating cases.

Per `docs/standards/testing.md`, every leg is run against pre-implementation
source and seen to fail before the implementation is written. Because these legs
extend two existing files rather than creating one, that is a real check: each
is added, run against the current `QListWidget` widget, and seen to fail before

The `qtbot` legs assert behaviour on a constructed widget; they do **not**
prove the tab renders correctly inside `MainWindow`. No leg in this spec builds
one.

## 8. Alternatives considered (and rejected)

- **Four columns, markers left on the Name cell.** Rejected by the user: the
  reconciliation warning stays unsortable, which is consequence 1.
- **Six columns, splitting the password marker from the reconciliation
  marker.** Rejected by the user as too wide for two rarely-set flags.
- **Show account numbers in full.** Rejected by the user — see §3 decision 2
  for the reasoning.
- **Mask with no reveal, permanently.** Rejected: a user who needs the full
  number to pay someone would have to open the vault file to get it back. That
  is why FIBR-0198 follows this item rather than the mask being the end state.
- **Move editing into an Add/Edit dialog.** Rejected by the user: more work,
  and it adds a click to every edit for a form that still fits on the tab.
- **`_refresh()` reusing rows, as `StatementsWidget.refresh` does.** Rejected on
  evidence, not preference — this was the draft's design until cold-eyes loop 5.
  Reproduced against real Qt with three accounts (`Alpha`, `Mid`, `Zed`) under a
  Name-descending sort (`docs/reviews/FIBR-0113-selection-drift-repro.py`):
  selecting visual row 0 left `selected_index` resolving to `Alpha` where it had
  been `Zed`, and row 2 resolved to `Zed` where it had been `Alpha`. Row 1 — the
  sort's fixed point — did not drift, which is why INV-22 drives every row.
  Clear-then-fill was verified to clear the selection. This bullet owns the
  mechanism; §3 decision 6, §4.2 and INV-22 point here.
  **Code-side note:** `StatementsWidget.refresh` carries this same latent drift
  today, harmlessly, because its `_on_selection_changed` toggles two buttons and
  touches no form. Tracked separately as **FIBR-0194** — not fixed here, because
  this is a docs change and that is a different widget.
- **`_refresh()` ending with `self._on_selection_changed()`, copying the
  sibling verbatim.** Rejected, though **not** because it would misbehave at
  that call site — under clear-then-fill the handler early-returns on the
  cleared selection and touches no field, so the two are equivalent there. It
  is rejected because it does not generalise: the same rule has to run from
  FIBR-0198's reveal handler with a selection live, where the copied line
  repopulates the form over a half-typed edit. §4.3 owns the reasoning.
- **Re-selecting the previous account inside `_refresh()`** so the selection
  survives a tab switch. Rejected: it would repopulate the form with the account
  just added, defeating `_on_add`'s field-clearing, and it changes today's
  behaviour (§6).
- **A generic column-customisation layer for FIBR-0084.** Rejected: it already
  exists as `remember_columns` and covers six tables. Building a second one
  would duplicate it — `coding.md` §1.3 prefers reuse and permits justified
  duplication, and there is no justification here.
- **Convert Categories' tree too, for FIBR-0084 completeness.** Rejected — see
  §2's closing paragraph, which owns the reason.
- **Carrying FIBR-0084's remaining surfaces here** (the Forecast table, the
  Home dashboard trees, the Reset-layout gap). Rejected — see §3 decision 8.
- **Carrying the schema and repository work here.** Rejected — see §13; it is
  FIBR-0193, and it ships first.
- **Carrying the reveal control here.** Rejected — see §13; it is FIBR-0198, and
  it ships after. Shipping the table alone regresses nothing: the number is
  masked on both surfaces from the first fill.

## 10. Resource cost

No new external dependency, no new module, no new build target. The parallel
`self._rows: list[Account]` and `self._with_pw: set[int]` replace per-item
`setData` storage of the same facts — but not identically: the old scheme
stashed four scalars per row (id, name, type, has-pw), where `self._rows`
retains whole `Account` objects, which additionally carry `created_at`,
`account_number` and `note`. Still bounded by the account count, and still a
handful of rows in any real vault.

`_refresh()` itself is unchanged in cost — `list_accounts()` +
`account_ids_with_pdf_password()` + `ReconciliationService.account_statuses()`
(a statement-period walk per account) + the money-display reads, exactly as
today, on every add, update, delete, forget and tab activation.
