# FIBR-0172 — Spending alerts

**Status:** DRAFT — pre-cold-eyes.
**Kind:** feature.
**Roadmap:** FIBR-0172 (features-accessibility).
**Depends on:** FIBR-0142 (recurring detection — `RecurringService`,
`recurring_decisions`) · FIBR-0012/0143 (Home dashboard + `ReportingService`) ·
FIBR-0007 (canonical signed `amount_minor`) · ADR-0006 (suggest-then-confirm,
persisted per-item decisions).

---

## 1. Summary

A quiet, dismissable **notice layer** on the Home dashboard that flags three
changes worth a glance — without nagging:

- **(a) New recurring charge** — a subscription/debit-order-shaped stream that has
  recently appeared and been detected, that the user hasn't yet decided on.
- **(b) Category spike** — a spending category whose spend is well above its own
  recent norm (≥ N× its rolling average).
- **(c) Missed expected debit** — a *confirmed* recurring payment whose next
  occurrence is overdue (didn't post when expected).

Each alert is **user-dismissable**, and a dismissal **persists** (survives restart)
so the same notice doesn't nag again. The layer is **non-intrusive**: an alerts
card that only appears when there is something to say, sitting above the dashboard
breakdown; no modal, no toast, no blocking.

Everything is computed from data the app already holds — the FIBR-0142 recurring
detector, the FIBR-0012 reporting aggregates, and the transactions table. The one
new piece of stored state is a small **dismissals** table (schema **v12**).

## 2. Design decisions

### D1 — Three pure detectors + a composing service (mirrors FIBR-0171/0177)

Each alert kind is a **pure** detector function (clock-free, integer minor units,
no `Decimal`) fed prepared inputs; `AlertService(vault).alerts(today)` gathers the
inputs (from `RecurringService`, `ReportingRepository`, the category + transactions
repos), calls the detectors, assembles `SpendingAlert`s, **filters out dismissed
ones**, and returns them newest-signal-first. The Home dashboard renders them. This
is the same pure-core/thin-service split FIBR-0171 (`project_forecast`) and
FIBR-0177 (`reconcile_account`) use.

### D2 — (a) New recurring charge

Source: `RecurringService.snapshot(today)` returns `(suggested, confirmed,
summary)` (FIBR-0142). A **new-recurring** alert is raised for each stream in
**`suggested`** (detected but **un-decided** — a confirmed stream is already known
to the user, and a dismissed one is already hidden by the recurring decision store)
with:

- `direction == Direction.OUT` (a *charge*; new recurring **income** is out of
  scope for v1 — see §6), and
- `first_seen >= _recency_start(today)` where `_recency_start` is the **first day of
  the previous calendar month** — i.e. the stream's earliest occurrence landed in
  the current or previous month ("recently appeared").

Rationale for the recency gate: detection needs ≥3 occurrences (FIBR-0142), so a
stream is only *detectable* once it has some history; gating on a recent `first_seen`
distinguishes a **newly-begun** subscription from a long-standing one, and — because
`first_seen` is the stream's *earliest* charge — importing old history never makes an
old subscription look new. (INV-1, INV-2.)

Payload: `label = merchant`, `amount_minor = ` the stream's representative charge
(`RecurringItem.amount` → signed minor via the exponent), `on = None`.
Key: `new_recurring:{merchant_key}` (permanent per stream — see D5). (INV-3.)

### D3 — (b) Category spike

**Window (correctness — no partial-month distortion):** the comparison uses the
**most recent *complete* calendar month** (`_last_complete_month(today)` = the month
before `today`'s month) as "current", against the **rolling average of the K=3
complete months before it**. Comparing the in-progress current month against full
prior months would be apples-to-oranges (a day-5 total vs full months), so v1
evaluates only whole months. (A real-time day-clipped variant is a v2 refinement,
§6.) (INV-4.)

**Series:** per **spending** (expenditure/OUT) category, a per-month spend total is
built by bucketing `ReportingRepository.rows_in_range(month_start, month_end,
account_ids=None)` on `category_id` and summing the **magnitudes of OUT rows**
(`-amount_minor` where `amount_minor < 0`), for each of the 4 months in the window
(`_last_complete_month` + the 3 before it). Category display names come from the
category repository; the `None` (uncategorised) bucket is **excluded** from spike
detection (too noisy to be actionable). (INV-5.)

**Rule:** raise a **category-spike** alert for a category iff
`current_minor >= _SPIKE_FACTOR * average_minor` **and** `average_minor >=
_MIN_BASELINE`, where:

- `_SPIKE_FACTOR = 2` (≥ 2× the recent average),
- `average_minor = round(mean of the 3 prior complete months' spend)` for that
  category (integer; `ROUND_HALF_EVEN`, the codebase money-rounding convention), and
- `_MIN_BASELINE = 50 * 10**exponent` (≈ 50 major units) — a floor that suppresses
  trivial-category noise (a category averaging small change would trip any ratio).
  Documented heuristic; tunable, and a v2 Settings control (§6).

Payload: `label = category_name`, `amount_minor = current_minor`, `baseline_minor =
average_minor`, `on = None`. The UI renders the ratio `current / baseline`.
Key: `category_spike:{category_id}:{YYYY-MM of the complete month}` (per category
**per month** — dismissing June's spike does not suppress July's). (INV-6, INV-7.)

### D4 — (c) Missed expected debit

Source: `RecurringService.snapshot(today).confirmed` — **confirmed** OUT streams
only (a missed *unconfirmed* stream is noise; the user has affirmed they rely on
these). For each confirmed `RecurringItem` with `direction == Direction.OUT`, the
expected next charge is `next_expected` (already `_add_cadence(last_seen, cadence)`,
FIBR-0142). The debit is **overdue** iff:

```
next_expected + timedelta(days=_MISS_GRACE) < today
```

with `_MISS_GRACE = 3` days (a small buffer so a payment 1–2 days late isn't
flagged). The upper bound is **implicit**: `RecurringService`'s activeness filter
(`_ACTIVE_GRACE = 2` intervals) already drops a stream from `confirmed` once it has
been silent for more than ~2 cadence intervals, so a long-dead stream naturally
stops alerting rather than nagging forever. (INV-8, INV-9.)

Payload: `label = merchant`, `amount_minor = ` the stream's representative charge,
`on = next_expected` (the date the debit was due). Key:
`missed_debit:{merchant_key}:{next_expected ISO}` (per **expected occurrence** — a
later missed occurrence, on a new date, alerts afresh). (INV-10.)

### D5 — Dismissal persistence (schema v12)

A new table records dismissed alert keys, keyed on a single **opaque stable
identity** so a dismissal follows the *thing*, not a transaction id:

```sql
CREATE TABLE alert_dismissals (
    id         INTEGER PRIMARY KEY,
    alert_key  TEXT NOT NULL UNIQUE,
    created_at TEXT NOT NULL
);
```

This mirrors the `recurring_decisions` / `transfer_pairs` decision-table idiom
(ADR-0006): a small table, `UNIQUE` on the identity, one insert per dismissal, the
service the sole producer of keys. `AlertDismissalRepository` exposes
`dismissed_keys() -> set[str]`, `dismiss(alert_key)` (idempotent upsert:
`INSERT … ON CONFLICT(alert_key) DO NOTHING`), and (for un-dismiss / tests)
`clear(alert_key)`. `AlertService.alerts(today)` drops any assembled alert whose
`key` is in `dismissed_keys()`. Because each kind's key encodes the right scope
(D2/D3/D4), a dismissal persists exactly as long as it should: a new-recurring
dismissal is permanent per stream, a spike dismissal is per-month, a missed-debit
dismissal is per-occurrence. (INV-11, INV-12, INV-13.)

### D6 — Migration v12

`_migrate_to_v12` creates `alert_dismissals` inside `with owned_transaction(conn):`,
ending with `UPDATE schema_version SET version = 12` (the established pattern —
migrations.py). **`LATEST_SCHEMA_VERSION` is bumped 11 → 12**, and **every**
schema-version drift-guard assertion across the suite that pins `== 11` (or
`schema_version == 11`) is updated to `12` in the **same** change — the migration
and its guards ship together (§7 lists them). A new table legitimately ripples these
guards; that is the guard system working as intended. (INV-14.)

### D7 — Money-safe, integer minor units

All alert arithmetic is signed integer minor units; the only rounding is the
category average's integer mean (`ROUND_HALF_EVEN`, the codebase convention). No
`Decimal` and no float in the detectors. `amount_minor` for a recurring stream is
recovered from `RecurringItem.amount` (a positive display `Decimal`) via
`int((amount * 10**exponent).to_integral_value())` — the exact idiom
`ForecastService._to_input` uses — with the OUT sign applied for display only (the
alert carries a positive magnitude for the label). Exponent via
`read_minor_unit_exponent(conn)`. (INV-15.)

### D8 — `today` injection

`AlertService.alerts(today: date)` takes `today` as a parameter (no default), the
`RecurringService`/`ForecastService` seam — so alert logic is hermetically testable.
The Home view passes `date.today()` at the call site, exactly as it already does for
`RecurringService.summary(date.today())`. (INV-16.)

### D9 — Surface: a non-intrusive dashboard alerts card

A new `AlertsCard` widget (a plain `QWidget`/`QFrame` matching the existing dashboard
card idiom — `objectName` set for tests, no new toast/banner framework) is inserted
into `HomeView._build_dashboard` **above the selectors row** (the most-visible,
least-disruptive slot). It is **hidden entirely when there are no alerts**
(`setVisible(False)`), so a healthy dashboard shows nothing new. When present, each
alert is one row: a translated summary label + a **Dismiss** (`✕`) button whose click
calls `AlertService.dismiss(key)` then refreshes. The **service returns structured
`SpendingAlert`s; the view builds the translated strings** (the FIBR-0138 pattern —
labels are injected/rendered in the QObject view, never hard-coded English in the
service). `HomeView.__init__` gains an `AlertService` constructor arg (wired in
`main_window.py`, mirroring how `RecurringService` was threaded in). Rendering a
locked vault is not reachable here (the dashboard shows only post-unlock, like the
recurring card). (INV-17, INV-18.)

### D10 — Constants (documented defaults, one home)

Module-level in `services/alerts.py`, so v2 can lift them into Settings (§6):
`_SPIKE_FACTOR = 2`, `_SPIKE_WINDOW = 3` (prior complete months averaged),
`_MIN_BASELINE_MAJOR = 50` (→ `_MIN_BASELINE = 50 * 10**exponent`),
`_MISS_GRACE = 3` (days). Recency for (a) is derived (first day of the previous
month), not a constant. All are cited in the INV tests so a change is a conscious,
test-visible edit.

## 3. New / changed models

```python
# models.py
class AlertKind(StrEnum):
    NEW_RECURRING = "new_recurring"
    CATEGORY_SPIKE = "category_spike"
    MISSED_DEBIT = "missed_debit"

@dataclass
class SpendingAlert:
    kind: AlertKind
    key: str                 # opaque stable dismissal identity (D5)
    label: str               # merchant (a/c) or category name (b)
    amount_minor: int        # a: charge magnitude; b: this-period spend; c: expected charge
    baseline_minor: int      # b: rolling-average spend; a/c: 0 (unused)
    on: date | None          # c: the due date that was missed; a/b: None
```

Field order pinned (repo convention). All money positive-magnitude integers (the UI
owns sign/format). `baseline_minor`/`on` are the only kind-specific fields; the UI
switches on `kind` to render.

## 6. Known limitations (documented, honest)

- **New recurring *income* not flagged (v1).** (a) is OUT-only (the layman ask is
  "a new subscription starts"). A new recurring salary/credit is a natural v2 add.
- **Category spike uses the last *complete* month, not real-time.** A mid-month
  overspend surfaces after month close (a whole-month vs whole-months comparison is
  the only apples-to-apples one without proration). A real-time day-of-month-clipped
  variant is a v2 refinement.
- **Thresholds are fixed constants** (`_SPIKE_FACTOR`, `_SPIKE_WINDOW`,
  `_MIN_BASELINE_MAJOR`, `_MISS_GRACE`). A Settings panel to tune them is v2 (the
  constants live in one module for that reason, D10).
- **Missed-debit is bounded by the recurring activeness window.** A debit missed for
  more than ~2 cadence intervals ages the stream out of `confirmed`, so a very stale
  miss stops alerting rather than nagging — acceptable (the alert is most useful when
  fresh) but means re-opening the app months later won't resurface an old miss.
- **`_MIN_BASELINE` is a digit-count floor, not currency-value-normalised** (50 ×
  10^exponent). Fine for the SA/Rand primary use; a currency-aware floor is v2.

**Repository** (`test_alert_dismissals.py`, in-memory vault):
- INV-12: `dismiss` idempotent (double-dismiss = one row), `dismissed_keys()` round
  trip, `clear` removes.

**Service** (`test_alert_service.py`, in-memory SQLCipher vault):
- INV-1/2: a recent suggested OUT stream → a new-recurring alert; a confirmed/IN/old
  one → none.
- INV-4/5: seed 4 months of categorised OUT transactions so the **last complete
  month** is 2× the prior-3 average for one category → a spike alert for it; the
  in-progress month's rows never affect the result.

  suggested/IN one → none.
- INV-11/13: dismiss each kind's key → that alert vanishes from `alerts(today)` while

  non-empty → one row per alert with the right translated summary.
