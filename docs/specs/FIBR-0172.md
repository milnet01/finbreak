# FIBR-0172 — Spending alerts

**Status:** DRAFT — pre-cold-eyes.
**Kind:** feature.
**Roadmap:** FIBR-0172 (features-accessibility).
**Depends on:** FIBR-0142 (recurring detection — `RecurringService`,
`recurring_decisions`) · FIBR-0012/0143 (Home dashboard + `ReportingService`) ·
FIBR-0007 (canonical signed `amount_minor`) · ADR-0006 (suggest-then-confirm,
persisted per-item decisions).

---

## 1. Summary

A quiet, dismissable **notice layer** on the Home dashboard that flags three
changes worth a glance — without nagging:

- **(a) New recurring charge** — a subscription/debit-order-shaped stream that has
  recently appeared and been detected, that the user hasn't yet decided on.
- **(b) Category spike** — a spending category whose spend is well above its own
  recent norm (≥ N× its rolling average).
- **(c) Missed expected debit** — a *confirmed* recurring payment whose next
  occurrence is overdue (didn't post when expected).

Each alert is **user-dismissable**, and a dismissal **persists** (survives restart)
so the same notice doesn't nag again. The layer is **non-intrusive**: an alerts
card that only appears when there is something to say, sitting above the dashboard
breakdown; no modal, no toast, no blocking.

Everything is computed from data the app already holds — the FIBR-0142 recurring
detector, the FIBR-0012 reporting aggregates, and the transactions table. The one
new piece of stored state is a small **dismissals** table (schema **v12**).

---

## 2. Design decisions

### D1 — Three pure detectors + a composing service (mirrors FIBR-0171/0177)

Each alert kind is a **pure** detector function (clock-free, **integer minor units
only — no `Decimal`, no float**, INV-15) that takes a list of **prepared integer
inputs** (§3) and **returns `list[SpendingAlert]`** — the detector builds the
alert's `key` + payload (so INV-3/INV-10 keys are pure, testable without a DB). The
thin `AlertService(vault).alerts(today)` does everything impure: it **prepares** each
detector's inputs (reading `RecurringService` / `ReportingRepository` / the category
+ transfer repos, and doing the **only** `Decimal → minor` conversion — on
`RecurringItem.amount` — so the detectors never see a `Decimal`, D7), calls the three
detectors, concatenates, applies the deterministic order below, and **filters out
dismissed** alerts. The Home dashboard renders them. Same pure-core/thin-service
split as FIBR-0171 (`project_forecast`) and FIBR-0177 (`reconcile_account`).

**Deterministic order (INV-19).** `alerts(today)` returns alerts sorted by a fixed
**urgency-then-size** comparator — *not* by date (the model has no common signal
date). The sort key is `(_KIND_ORDER[kind], -amount_minor, label)` where
`_KIND_ORDER = {MISSED_DEBIT: 0, NEW_RECURRING: 1, CATEGORY_SPIKE: 2}` (a missed
payment is the most actionable; a spike the most FYI). **Deterministic** — a stable
sort over the detectors' deterministic input order (equal keys keep a reproducible
order; the key is not a strict total order), so the same inputs + `today` yield the
same ordered list (INV-16, INV-19).

### D2 — (a) New recurring charge

Source (service side): the service calls `RecurringService.snapshot(today)` **once**
and unpacks the plain 3-tuple `suggested, confirmed, _ = snapshot(today)` (FIBR-0142
— it is a bare `tuple`, so index/unpack; there is no `.suggested`/`.confirmed`
attribute). It prepares a `NewRecurringInput` (§3) for each stream in **`suggested`**
(detected but **un-decided** — a confirmed stream is already known, a dismissed one
already hidden by the recurring decision store) with `direction == Direction.OUT` (a
*charge*; new recurring **income** is out of scope for v1 — §6), converting
`RecurringItem.amount` (a `Decimal`) to a **positive minor magnitude** once (D7) and
carrying the stream's `occurrences`. Pure detector:

```
detect_new_recurring(items: list[NewRecurringInput]) -> list[SpendingAlert]
```

raises an alert for each input that has only recently crossed the detection
threshold:

```
occurrences  <=  _NEW_MAX_OCCURRENCES
```

with `_NEW_MAX_OCCURRENCES = 4` (D10).

**Why gate on `occurrences`, not a date window (the subtle part).** Detection needs
≥3 occurrences (FIBR-0142 `_MIN_OCCURRENCES = 3`), so a just-detected stream has
`occurrences == 3`; as it keeps charging, `occurrences` grows. Gating on
`occurrences ≤ 4` therefore captures precisely "a stream that has *just* become
recurring" — **cadence-agnostically**, with **no date-window boundary to get wrong**.
(An earlier draft gated on `first_seen ≥ today − k·interval`; that is fragile — the
per-cadence *accept band* lets day-gaps exceed the nominal interval, so the worst-case
`first_seen` of a still-active, freshly-detected monthly stream falls *outside* any
fixed-`k` nominal window, silently dropping the flagship case. `occurrences` sidesteps
the whole boundary analysis.) An old subscription with a long history has a large
`occurrences` → never flagged as new; and the `suggested` set is already
activeness-filtered, so only *active* streams reach the detector. (INV-1, INV-2.)

Payload: `label = merchant`, `amount_minor = ` the positive charge magnitude,
`baseline_minor = 0`, `on = None`. Key: `new_recurring:{merchant_key}` (permanent per
stream — see D5). (INV-3.)

### D3 — (b) Category spike

**Window (correctness — no partial-month distortion):** the comparison uses the
**most recent *complete* calendar month** (`_last_complete_month(today)` — reuse
FIBR-0012's `_prev_month`/`_month_bounds` so the year boundary is handled, never a
naive `month − 1`) as "current", against the **rolling average of the `_SPIKE_WINDOW
= 3` complete months before it**. Comparing the in-progress current month against
full prior months would be apples-to-oranges (a day-5 total vs full months), so v1
evaluates only whole months. (A real-time day-clipped variant is a v2 refinement,
§6.) (INV-4.)

**Series (service side):** per **spending** (expenditure/OUT) category, a per-month
spend total is built by bucketing `ReportingRepository.rows_in_range(start_iso,
end_iso, account_ids=None)` — note the args are **ISO strings** (`month_start
.isoformat()`, `month_end.isoformat()`), not `date` objects — on `category_id`,
summing the **magnitudes of OUT rows** (`-amount_minor` where `amount_minor < 0`),
for each of the 4 months in the window (`_last_complete_month` + the 3 before it).
**Confirmed transfers are excluded** — the service skips any `txn_id ∈
TransferDetectionService.confirmed_transfer_txn_ids()`, the **same `_excluded()` set
`ReportingService.spending_by_category` applies** — so a categorised inter-account
transfer is not miscounted as spend and the spike's numbers agree with the dashboard
donut for that month (a wrong-total bug otherwise). The `None` (uncategorised) bucket
is **excluded** from spike detection (too noisy to be actionable). Category display
names come from `CategoryRepository`. The series is **vault-wide** (`account_ids =
None`) — alerts are a dashboard-level nudge, not scoped by the account selector (like
the unscoped recurring card), so a spike total matches the donut only when no account
filter is active. (INV-5.)

**Pure detector:**

```
detect_category_spikes(items: list[CategorySpikeInput], month: str,
                       min_baseline: int) -> list[SpendingAlert]
```

where each `CategorySpikeInput` carries `category_id`, `category_name`,
`current_minor`, and `prior_minor: tuple[int, ...]` (the 3 prior months' spend). It
raises a **category-spike** alert iff `current_minor >= _SPIKE_FACTOR * average_minor`
**and** `average_minor >= min_baseline`, where:

- `_SPIKE_FACTOR = 2` (≥ 2× the recent average),
- `average_minor = (sum(prior_minor) + len(prior_minor) // 2) // len(prior_minor)` —
  an **integer round-half-up** of the mean, using integer arithmetic only (no
  `Decimal`, no float — money-safe, INV-15; the earlier `ROUND_HALF_EVEN` framing was
  dropped because it is vacuous for the odd `_SPIKE_WINDOW = 3` and would tempt a
  float division). `prior_minor` empty ⇒ no alert (nothing to average), and
- `min_baseline = _MIN_BASELINE_MAJOR * 10**exponent` (the service computes it from
  the vault exponent and passes it in, so the detector stays exponent-free);
  `_MIN_BASELINE_MAJOR = 50` (≈ 50 major units) — a floor suppressing trivial-category
  noise. Documented heuristic; a v2 Settings control (§6).

Payload: `label = category_name`, `amount_minor = current_minor`, `baseline_minor =
average_minor`, `on = None`. The UI renders the ratio `current / baseline`.
Key: `category_spike:{category_id}:{month}` (`month` = the complete month's `YYYY-MM`;
per category **per month** — dismissing June's spike does not suppress July's).
(INV-6, INV-7.)

### D4 — (c) Missed expected debit

Source (service side): the `confirmed` list unpacked from `snapshot(today)` (D2 —
the same single snapshot call; `snapshot` is a 3-tuple, so use the unpacked
`confirmed`, **not** a non-existent `.confirmed` attribute) — **confirmed** OUT
streams only (a missed *unconfirmed* stream is noise; the user has affirmed they rely
on these). The service prepares a `MissedDebitInput` (§3) for each confirmed
`RecurringItem` with `direction == Direction.OUT`, converting `amount` (a `Decimal`)
to a positive minor magnitude (D7). `next_expected` is FIBR-0142's already-computed
`_add_cadence(last_seen, cadence)`. Pure detector:

```
detect_missed_debits(items: list[MissedDebitInput], today: date) -> list[SpendingAlert]
```

flags an input **overdue** iff:

```
next_expected + timedelta(days=_MISS_GRACE) < today
```

with `_MISS_GRACE = 3` days (D10 — a small buffer so a debit ≤ 3 days late isn't
flagged; it fires at 4+ days late). The upper bound is **implicit** and lives in the
*service's* input prep, not the detector: `RecurringService`'s activeness filter
(`_ACTIVE_GRACE = 2` intervals) already drops a stream from `confirmed` once it has
been silent for more than ~2 cadence intervals, so a long-dead stream never reaches
the detector — it stops alerting rather than nagging forever. (INV-8, INV-9.)

Payload: `label = merchant`, `amount_minor = ` the positive charge magnitude,
`baseline_minor = 0`, `on = next_expected` (the date the debit was due). Key:
`missed_debit:{merchant_key}:{next_expected ISO}` (per **expected occurrence** — a
later missed occurrence, on a new date, alerts afresh). (INV-10.)

### D5 — Dismissal persistence (schema v12)

A new table records dismissed alert keys, keyed on a single **opaque stable
identity** so a dismissal follows the *thing*, not a transaction id:

```sql
CREATE TABLE alert_dismissals (
    id         INTEGER PRIMARY KEY,
    alert_key  TEXT NOT NULL UNIQUE,
    created_at TEXT NOT NULL
);
```

This mirrors the `recurring_decisions` / `transfer_pairs` decision-table idiom
(ADR-0006): a small table, `UNIQUE` on the identity, one insert per dismissal, the
service the sole producer of keys. `AlertDismissalRepository` exposes
`dismissed_keys() -> set[str]`, `dismiss(alert_key)` (idempotent upsert:
`INSERT … ON CONFLICT(alert_key) DO NOTHING`), and (for un-dismiss / tests)
`clear(alert_key)`. `AlertService.alerts(today)` drops any assembled alert whose
`key` is in `dismissed_keys()`. Because each kind's key encodes the right scope
(D2/D3/D4), a dismissal persists exactly as long as it should: a new-recurring
dismissal is permanent per stream, a spike dismissal is per-month, a missed-debit
dismissal is per-occurrence. (INV-11, INV-12, INV-13.)

### D6 — Migration v12

`_migrate_to_v12` creates `alert_dismissals` inside `with owned_transaction(conn):`,
ending with `UPDATE schema_version SET version = 12` (the established pattern —
migrations.py). **`LATEST_SCHEMA_VERSION` is bumped 11 → 12**, and **every**
schema-version drift-guard assertion across the suite that pins `== 11` (or
`schema_version == 11`) is updated to `12` in the **same** change — the migration
and its guards ship together (§7 lists them). A new table legitimately ripples these
guards; that is the guard system working as intended. (INV-14.)

**One guard needs *rework*, not a numeric bump (INV-14a).**
`tests/features/reconciliation/test_no_schema_change.py` (FIBR-0177) asserts **both**
`LATEST_SCHEMA_VERSION == 11` *and* `12 not in _MIGRATIONS` — the latter has **no
`== 11`** to sweep, so a blind search-replace leaves it red. FIBR-0177's INV-8 meant
"*reconciliation* adds no schema change of its own", which stays true — but its
mechanism (an absolute-version pin) can't express that once *another* feature bumps
the version. So this change: (i) updates the version assertion to `== 12`; (ii)
advances the future-migration guard to `13 not in _MIGRATIONS` (still "no
unregistered next version"); and (iii) reworks the now-stale **names + docstrings**:
the test functions `test_INV8_schema_version_unchanged_at_11` /
`test_INV8_no_v12_migration_registered` (both misleading once they assert `== 12` /
`13 not in _MIGRATIONS`) are renamed, their docstrings updated, and
`reconciliation/spec.md` INV-8 prose (drop "no `_migrate_to_v12`"; note the schema has
since advanced to v12 via FIBR-0172, unrelated to reconciliation). This is the only
`not in _MIGRATIONS` guard in the suite.

### D7 — Money-safe, integer minor units

The **pure detectors** are `Decimal`-free and float-free — integer minor units only.
The single `Decimal → minor` conversion lives in the **service's input prep** (so a
detector never sees a `Decimal`, closing the INV-15 hole for the (a)/(c) paths):
`RecurringItem.amount` (a positive display `Decimal`) → a positive minor magnitude
via `int((amount * 10**exponent).to_integral_value())` — the exact idiom
`ForecastService._to_input` uses — with exponent from `read_minor_unit_exponent(
conn)`. Alerts carry a **positive magnitude** in `amount_minor` (the UI owns
sign/format). The category average is an **integer round-half-up** computed with
integer arithmetic only — `(sum(prior) + K // 2) // K` — never a `Decimal`/float
division (D3). (INV-15.)

### D8 — `today` injection

`AlertService.alerts(today: date)` takes `today` as a parameter (no default), the
`RecurringService`/`ForecastService` seam — so alert logic is hermetically testable.
The Home view passes `date.today()` at the call site, exactly as it already does for
`RecurringService.summary(date.today())`. (INV-16.)

### D9 — Surface: a non-intrusive dashboard alerts card

A new `AlertsCard` widget (a plain `QWidget`/`QFrame` matching the existing dashboard
card idiom — no new toast/banner framework) is inserted into
`HomeView._build_dashboard` **above the selectors row** (the most-visible,
least-disruptive slot). **Object names** (for the qtbot tests, matching the existing
`dashboard_net` / `dashboard_trend_chart` convention): the card is
`dashboard_alerts`; each row's dismiss button is `alert_dismiss` (the button carries
its alert `key` — e.g. via a Qt property or closure — so the handler knows what to
dismiss). The card is **hidden entirely when there are no alerts**
(`setVisible(False)`), so a healthy dashboard shows nothing new; when present, each
alert is one row: a translated summary label + a **Dismiss** (`✕`) button.

**Rendering vs the dismiss write-path — the lock distinction (M2).** *Rendering*
the card is a read on an unlocked vault (the dashboard shows only post-unlock, like
the recurring card — no lock handling needed there). But the **Dismiss click is a
*mutating* write** to the vault, and the codebase guards every mutating dashboard
slot against a mid-interaction auto-lock. So the click handler wraps
`AlertService.dismiss(key)` in a `VaultLockedError`-silent guard (mirroring
`RecurringWidget`/`TransfersWidget`), then does a **card-local rebuild** — it
re-reads `alerts(today)` and rebuilds only the `AlertsCard` (hiding it if now empty),
**not** a full `HomeView.refresh()` (which re-runs every reporting/drill/trend query
— unnecessary for a dismissal). The **service returns structured `SpendingAlert`s;
the view builds the translated strings** (the FIBR-0138 pattern — rendering lives in
the QObject view, never hard-coded English in the service). `HomeView.__init__` gains
an `AlertService` constructor arg (wired in `main_window.py`, mirroring how
`RecurringService` was threaded in). (INV-17, INV-18.)

### D10 — Constants (documented defaults, one home)

Module-level in `services/alerts.py`, so v2 can lift them into Settings (§6):
`_NEW_MAX_OCCURRENCES = 4` (a stream with ≤ this many occurrences is "new" — D2),
`_SPIKE_FACTOR = 2`, `_SPIKE_WINDOW = 3` (prior complete months averaged),
`_MIN_BASELINE_MAJOR = 50` (the service passes the detector `min_baseline =
_MIN_BASELINE_MAJOR * 10**exponent`, so the detector stays exponent-free — D3),
`_MISS_GRACE = 3` (days). All are cited in the INV tests so a change is a conscious,
test-visible edit.

## 3. New / changed models

```python
# models.py
class AlertKind(StrEnum):
    NEW_RECURRING = "new_recurring"
    CATEGORY_SPIKE = "category_spike"
    MISSED_DEBIT = "missed_debit"

@dataclass
class SpendingAlert:
    kind: AlertKind
    key: str                 # opaque stable dismissal identity (D5)
    label: str               # merchant (a/c) or category name (b)
    amount_minor: int        # a: charge magnitude; b: this-period spend; c: expected charge
    baseline_minor: int      # b: rolling-average spend; a/c: 0 (unused)
    on: date | None          # c: the due date that was missed; a/b: None
```

Field order pinned (repo convention). All money positive-magnitude integers (the UI
owns sign/format). `baseline_minor`/`on` are the only kind-specific fields; the UI
switches on `kind` to render.

**Prepared detector inputs** (in `services/alerts.py`, next to the detectors —
mirroring `ForecastInput` living beside `project_forecast`). These are the
**integer-minor**, `Decimal`-free shapes the service builds and the pure detectors
consume (D1/D7/H2):

```python
# services/alerts.py
@dataclass
class NewRecurringInput:      # (a) — from a suggested OUT RecurringItem
    merchant: str
    merchant_key: str
    amount_minor: int         # positive magnitude
    occurrences: int          # crossed the ≥3 detection threshold recently?

@dataclass
class CategorySpikeInput:     # (b) — one per spending category
    category_id: int
    category_name: str
    current_minor: int        # last-complete-month spend (transfer-excluded)
    prior_minor: tuple[int, ...]   # the _SPIKE_WINDOW prior months' spend

@dataclass
class MissedDebitInput:       # (c) — from a confirmed OUT RecurringItem
    merchant: str
    merchant_key: str
    amount_minor: int         # positive magnitude
    next_expected: date       # detect_missed_debits compares this + grace vs today
```

The three detectors return `list[SpendingAlert]`; the service concatenates, orders
(D1), and filters dismissed keys.

## 6. Known limitations (documented, honest)

- **New recurring *income* not flagged (v1).** (a) is OUT-only (the layman ask is
  "a new subscription starts"). A new recurring salary/credit is a natural v2 add.
- **Category spike uses the last *complete* month, not real-time.** A mid-month
  overspend surfaces after month close (a whole-month vs whole-months comparison is
  the only apples-to-apples one without proration). A real-time day-of-month-clipped
  variant is a v2 refinement.
- **Thresholds are fixed constants** (`_SPIKE_FACTOR`, `_SPIKE_WINDOW`,
  `_MIN_BASELINE_MAJOR`, `_MISS_GRACE`). A Settings panel to tune them is v2 (the
  constants live in one module for that reason, D10).
- **Missed-debit is bounded by the recurring activeness window.** A debit missed for
  more than ~2 cadence intervals ages the stream out of `confirmed`, so a very stale
  miss stops alerting rather than nagging — acceptable (the alert is most useful when
  fresh) but means re-opening the app months later won't resurface an old miss.
- **`_MIN_BASELINE` is a digit-count floor, not currency-value-normalised** (50 ×
  10^exponent). Fine for the SA/Rand primary use; a currency-aware floor is v2.
