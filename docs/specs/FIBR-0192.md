# FIBR-0192 — Remember the last two surfaces' columns, and make Reset layout reset them

**Status:** draft (2026-07-30).
**Kind:** feature.
**Source:** ROADMAP FIBR-0192 (cold-eyes-2026-07-28, FIBR-0113 loop 2). Split out
of FIBR-0113, which had folded this work in and found it the single largest
source of that spec's own review defects.
**Depends on:** FIBR-0117 (the `ui/_table_state.py` seam this extends), FIBR-0052
(the `Window` menu, the window INI, and `Reset layout` itself).
**Blocker for:** FIBR-0084's ✅ — this is its last open surface. Do **not** flip
FIBR-0084 until this ships.
**Inherits:** FIBR-0113 **INV-13** (the Forecast table joining the shared column
scheme) and **INV-14** (Reset layout clearing saved column state), both withdrawn
there on 2026-07-28 and re-homed here as §5 INV-1 and INV-5/INV-6.

**Layman:** Two places in finbreak still won't let you drag their columns wider or
into a different order and remember it — the Forecast tab's list of upcoming
items, and the three category breakdown lists on the Home dashboard. This adds
that. It also fixes the `Window → Reset layout` menu item, which today puts the
window back to its default size but silently leaves every table's columns exactly
as they were; after this it puts the columns back too, straight away.

## 1. Goal

Two surfaces — four headers in all — gain the FIBR-0117 column behaviour, and one
menu item starts doing what its name says:

1. The Forecast tab's events table remembers its column widths and order.
2. The three Home dashboard breakdown trees do the same, each under its own key.
3. `Window → Reset layout` clears every saved column layout **and** returns every
   **remembered** live header to its build-time default in the same click. A view
   built without `remember_columns` is not touched (§4.3).

With these, every relevant header in the app is covered and FIBR-0084 closes.

## 2. Problem

Three gaps, each resolved against source on 2026-07-30 (not recalled):

**The Forecast table is configured like its siblings and wired like none of
them.** `ui/forecast.py::ForecastWidget._make_table` builds a four-column
`QTableWidget`, already named `forecast_events`, already `NoEditTriggers` /
`SelectRows` / `SingleSelection` — but `forecast.py` imports nothing from
`_table_state`, so its columns are neither drag-reorderable nor remembered. A
fresh `QTableWidget` header is **not** movable by default (measured, §2.1), so
this is a real absence rather than a Qt default filling in.

**The Home breakdown trees have a visible header and no persistence.**
`ui/home.py::HomeView._build_column` builds a `QTreeWidget` with
`setColumnCount(2)`, visible `setHeaderLabels([Name, Amount])` and objectName
`dashboard_breakdown_<key>`, once for each of the three keys `_build_dashboard`
iterates — `expenditure`, `income`, `transfers`. `home.py` also imports nothing
from `_table_state`. FIBR-0084's own text puts this surface in scope
("Make each QTableView/QTreeView header user-resizable AND movable"), confirmed
by the user 2026-07-28.

The obstacle is a signature: `_table_state.remember_columns` is typed
`(table: QTableWidget) -> None` and reaches its header via
`table.horizontalHeader()`. A `QTreeWidget` is neither — it exposes `header()`.

**Reset layout resets everything except columns.**
`ui/main_window.py::MainWindow._reset_layout` removes exactly `_KEY_GEOMETRY`,
`_KEY_STATE` and `_KEY_SIZE`, then resizes and centres. It never touches the
`columns/<objectName>` entries `remember_columns` writes, so a user who has
dragged a table into an unreadable state and reaches for Reset layout gets the
window back and the table unchanged. FIBR-0113 records this as its **INV-14**,
withdrawn there on 2026-07-28 and deferred to this item.

Three of these rows each killed a defect that had already survived a careful

## 3. Scope decisions (agreed with the user)

1. **The Forecast table gets `remember_columns` only — no click-to-sort** (user,
   2026-07-30). Its last column is **Balance after**, a running total that is
   only meaningful in date order; sorting by Merchant would pair each row with
   another row's balance. This also sidesteps the hazard the roadmap bullet
   records: `_fill_events` uses a bare `setRowCount` + `setItem` loop with no
   `fill_guard`, so enabling sorting *without first wrapping the fill* would let
   Qt re-sort mid-fill. The wrap is **not** added here — `fill_guard` only does
   work when sorting is enabled, and adding a no-op guard is scaffolding for a
   future this decision has rejected. What is added instead is a comment at
   `_make_table` naming both reasons, so the next contributor meets them.
2. **Reset layout resets live headers immediately, not just the stored state**
   (user, 2026-07-30). Clearing the INI alone would leave the menu item looking
   broken: the window snaps back, the columns do not, until the next launch.
3. **The Home trees keep `setSortingEnabled(False)`** (mine). The reporting
   service pre-sorts every level biggest-first (**FIBR-0138 INV-7**, cited by
   FIBR-0143 INV-4); a user sort would fight it. Only persistence is added.
4. **Categories stays out of scope.** FIBR-0084's headline sentence *names*
   Categories among the tables to cover, and its later body then excludes it —
   "Categories stays deliberately out of scope (single column under
   `setHeaderHidden(True)` — nothing to resize or reorder)". The body is right and
   this spec follows it: `ui/categories.py` builds a `QTreeWidget` with
   `setHeaderHidden(True)` and one column, so there is no header to resize or
   reorder and the ask is vacuous there. Flagged because §12 flips FIBR-0084 ✅
   and a reader checking that bullet's headline against this spec will find a
   named surface unaddressed.

## 4. Design

### 4.1 Widen `remember_columns` to accept either view

`_table_state.remember_columns` takes `QTableWidget | QTreeWidget`, and a
module-private helper resolves the header:

```python
def _header_of(view: QTableWidget | QTreeWidget) -> QHeaderView:
    """The column header of either view kind — QTableWidget names it
    ``horizontalHeader``, QTreeWidget just ``header``."""
    return view.horizontalHeader() if isinstance(view, QTableWidget) else view.header()
```

Nothing else about the **existing** behaviour changes: the same
`columns/<objectName>` key, the same restore-then-connect order, the same three
signals. §4.2 adds one new step inside this function, between the movable flag
and the restore. The seven existing call sites (counted in §7) are untouched —
the union widens what is accepted and narrows nothing.

`selected_index`, `tag_row`, `select_by_index`, `fill_guard` and `enable_sorting`
keep their `QTableWidget` types. They are about a table's parallel row list and
its sort, and neither new surface has one.

### 4.2 Capture the build-time default

`remember_columns` records the header's state at exactly one point: **after
`setSectionsMovable(True)`, before the `restoreState`.** Both halves of that
sentence are load-bearing, and getting either wrong is silent:

```python
_DEFAULT_STATE_PROP = "finbreak_default_header_state"   # module-level, beside _ROW_INDEX_ROLE

header = _header_of(view)
header.setSectionsMovable(True)
view.setProperty(_DEFAULT_STATE_PROP, header.saveState())   # <- after movable, before restore
state = _settings().value(key)
if state is not None:
    header.restoreState(state)
```

- **After `setSectionsMovable(True)`**, because `saveState()` serialises that
  flag (measured, §2.1 row 3). Captured one line earlier, the stored "default"
  carries `movable = False`, and the first Reset layout would turn drag-reorder
  off on every remembered view then live — and, once a later resize persists the flag-less state, across restarts too.
  That is the exact behaviour FIBR-0084 exists to deliver, disabled by the
  feature meant to restore it. INV-5 carries a clause against it.
- **Before the restore**, because after it the state is the *user's* layout, not
  the default, and a reset would then restore whatever the user last had.

Stored on the **view**, as a dynamic Qt property, not in a module-level registry.
A registry keyed by `objectName` would outlive the widget that owns it: it would
leak across a workspace rebuild, across two windows in one process, and across
tests in one session. The property dies with the widget, which is the lifetime
that is actually correct. `QByteArray` round-trips through `setProperty` /
`property` unchanged (measured, §2.1 row 9).

`saveState()` on an unshown header records Qt's `defaultSectionSize` (100px,
measured) and the identity column order. That is the right target: it is what a
first-run user sees before touching anything. Headers with
`stretchLastSection` — `transactions_table` sets it explicitly, and every
`QTreeWidget` header carries it on by default (§2.1 row 7), so the three new Home
trees have it too — re-stretch on the next layout pass, exactly as on first run.

**The capture is only correct if the view's columns and `objectName` are already
set**, since both the section count and the settings key are read at this moment.
All seven existing call sites were checked and all seven comply — each sets
`QTableWidget(0, N)`, `setObjectName` and `setHorizontalHeaderLabels` before
calling (verified 2026-07-30 across `rules`, `statements`, `recurring`,
`transfers`, `transactions`, `accounts`, `import_wizard`). §4.5 keeps the two new
sites to the same order.

### 4.3 `reset_columns(root)`

A new function beside the others in `_table_state`:

```python
def reset_columns(root: QWidget) -> None:
    """Put every remembered header under ``root`` back to the default captured by
    ``remember_columns``. Views built without it are skipped."""
    views: list[QTableWidget | QTreeWidget] = [
        *root.findChildren(QTableWidget),
        *root.findChildren(QTreeWidget),
    ]
    for view in views:
        state = view.property(_DEFAULT_STATE_PROP)
        if state is not None:
            _header_of(view).restoreState(state)   # NOT under blockSignals — see below
```

`findChildren` is recursive, so it reaches the Home trees through the dashboard's
`QScrollArea` and the tab pages through the workspace's `QTabWidget` (measured
through one nesting level, §7 probe). Two calls rather than one tuple argument:
explicit, and it types cleanly.

**The restore must NOT be wrapped in `blockSignals`, and that is the subtlest
requirement in this document.** It is worth stating as a prohibition because
blocking looks like obvious hygiene here and it silently breaks a shipped
behaviour.

`restoreState` emits no `sectionResized` or `sectionMoved` (§2.1 row 4), so the
width/order save is never re-triggered by it. It *does* emit
`sortIndicatorChanged` — and **`QTableView`'s own re-sort rides on that signal.**
Block it and the header shows the restored default's sort arrow while the rows
stay in the user's old order (measured, §2.1 row 6: an *ascending* indicator over
`['cherry', 'banana', 'apple']`). Four remembered tables are click-sortable, and
this is precisely the split `tests/features/table_state/spec.md` row 4b already
calls a defect: "the restored header re-sorts the rows (**not just the indicator
arrow**)". INV-8 clause 2 is the test.

`remember_columns`' own `_save` also listens to that signal, so the restore may
write the just-restored default back to the INI — harmless, and §4.4's clear
removes it. Whether it writes at all is not even deterministic: PySide6 cannot
always marshal the signal's `Qt::SortOrder` argument, in which case the handler
raises `TypeError` to stderr instead of running (§2.1 row 5). **That stderr line
is accepted noise, deliberately.** It is recorded here because the obvious way
to silence it — blocking the header's signals — is exactly the change that
breaks sort restoration, and a future contributor who meets the `TypeError`
without this paragraph will make it.

### 4.4 `_reset_layout` — resize first, clear last

The order changes, and the order is the design:

```python
def _reset_layout(self) -> None:
    self.resize(_DEFAULT_WINDOW_SIZE)
    self._center_window()          # a no-op on Wayland; the resize above still applies
    reset_columns(self)            # live headers back to their build-time defaults
    settings = self._settings()
    settings.remove(_KEY_GEOMETRY)
    settings.remove(_KEY_STATE)
    settings.remove(_KEY_SIZE)
    settings.remove("columns")     # the whole group written by remember_columns
    settings.sync()
```

Three reasons for this sequence, in the order they bite:

1. **The resize can re-save the user's old column layout.** `transactions_table`
   sets `setStretchLastSection(True)` explicitly
   (`ui/transactions.py::TransactionsWidget._build_table`) and every
   `QTreeWidget` header has it on by default (§2.1 row 7), so resizing the window
   re-lays-out those sections, emits `sectionResized`, and `remember_columns`'
   handler writes the **pre-reset** layout straight back. This is the write that
   must not survive, and the two possible emission timings are neutralised by
   different parts of the sequence — which is why both orderings matter:
   - **Synchronous** (the emission lands inside `self.resize(...)`): the write
     carries the user's *old* layout, because `reset_columns` has not run yet.
     What erases it is `settings.remove("columns")` running afterwards. This is
     the case that makes **clear-last** mandatory.
   - **Deferred** (Qt defers the layout pass past `_reset_layout`, §5 INV-6's
     note): the write lands after `reset_columns` and so carries the **default**
     state. Harmless, and beyond the reach of any ordering.
2. **The restore may re-save as well**, via `sortIndicatorChanged` (§2.1 row 5),
   and that write is the default state — harmless in itself. Clearing last simply
   leaves the group empty rather than holding a default-valued entry. A tidiness
   reason; reason 1 is the correctness one.
3. `settings.remove("columns")` drops the whole group; the four flat keys
   (`geometry`, `window_state`, `window_size`, `last_tab`) are not inside it, so
   nothing else is caught. `last_tab` is deliberately not removed — Reset layout
   has never cleared it and this item does not change that (§9).

`reset_columns(self)` is passed the window, not the workspace: the `Window` menu
holding this action needs no vault and stays enabled while locked
(`_set_vault_chrome_enabled` enables only toolbar / File / View), so
`_reset_layout` is reachable with no workspace built at all. Passing `self` makes
that case a no-op over an empty `findChildren` result rather than an
`AttributeError` on `None` (INV-7).

### 4.5 The two call sites

`ui/forecast.py::ForecastWidget._make_table` adds `remember_columns(table)`
before its `return`, plus the comment §3 decision 1 requires.
`ui/home.py::HomeView._build_column` adds `remember_columns(tree)` after
`setSortingEnabled(False)`. Both after the objectName and the columns are set —
the key and the section count both come from the widget's state at that moment.

## 5. Invariants

- **INV-1** — **The Forecast events table is drag-reorderable and its columns
  persist.** After `ForecastWidget` is constructed,
  `_events_table.horizontalHeader().sectionsMovable()` is `True` (a fresh
  `QTableWidget` header is `False` — §2.1, so this discriminates); and resizing a
  column, then destroying and rebuilding the widget, restores that width.
  *Breaks if:* `forecast.py` drops the `remember_columns` call, or the table's
  objectName changes and silently starts a new key.
  *Test:* `tests/features/table_state/test_table_state.py::test_FIBR0192_INV1_forecast_columns_movable_and_remembered`.
- **INV-2** — **The Forecast table is not click-sortable, and its rows stay in
  date order.** `_events_table.isSortingEnabled()` is `False` after construction
  and after `refresh()`; and a real left-click on the **Merchant** header leaves
  the row order byte-identical to what `_fill_events` wrote.
  *Precondition — without it the clause is vacuous:* the vault must hold at least
  two confirmed recurring items whose **merchant-alphabetical order differs from
  their date order**. `project_forecast` stable-sorts events by
  `(on, merchant, direction)` (`services/forecast.py`), so the table is
  date-ascending by construction; with one event, or with merchant order matching
  date order, a click sorts nothing visible and the leg passes against a build
  that *did* add `enable_sorting`. An empty vault renders no rows at all — the
  "No confirmed recurring items yet" status — which is the same trap.
  *Breaks if:* someone adds `enable_sorting` — the click then reorders, and
  because `_fill_events` has no `fill_guard`, a later refill can also pair a
  running balance with another event's date (§3 decision 1).
  *Test:* `tests/features/table_state/test_table_state.py::test_FIBR0192_INV2_forecast_is_not_click_sortable`.
- **INV-3** — **Each of the three Home breakdown trees remembers its own columns
  under its own key.** Resizing column 0 of `dashboard_breakdown_expenditure`,
  `…_income` and `…_transfers` to three *distinct* widths, then rebuilding
  `HomeView`, restores all three distinctly; and the window INI holds three
  separate `columns/dashboard_breakdown_*` keys.
  *Breaks if:* the trees share or lose their objectName — the FIBR-0012
  cross-corruption class, where two tables share the empty `columns/` key and
  overwrite each other.
  *Note:* this invariant deliberately does **not** assert `sectionsMovable()`.
  A `QTreeWidget` header is movable by default (§2.1), so that clause would pass
  against a build with no `remember_columns` call at all.
  *Test:* `tests/features/table_state/test_table_state.py::test_FIBR0192_INV3_home_breakdown_trees_remember_distinct_columns`.
- **INV-4** — **`remember_columns` accepts both view kinds at type level.** The
  gate's `mypy` stage is clean with `home.py` passing a `QTreeWidget`.
  *Breaks if:* the parameter is left `QTableWidget` — `home.py`'s call is then an
  `arg-type` error, which is how this gap was found.
  *Test:* the `mypy` stage of `./scripts/ci-local.sh` (no separate test — a type
  error is a gate failure, not a test failure).
- **INV-5** — **Reset layout returns live headers to their defaults, in the same
  click — and leaves them still reorderable.** With a workspace live, widening a
  Transactions column and dragging it to a new position, then invoking
  `_reset_layout()`, leaves that column at its build-time width and its
  build-time **visual** position (`header.visualIndex(logical)` back to identity)
  **without** a rebuild or a restart; and `horizontalHeader().sectionsMovable()`
  is **still `True`** afterwards; and a column resized *after* the reset is still
  persisted across a rebuild.
  *Why visual, not logical:* a drag never moves a section's logical index — the
  seam's own docstring says "Reordering is visual-only". A clause asserting the
  *logical* index would pass against a build where `reset_columns` does nothing
  to order at all, which is half of what this invariant exists to prove.
  *Breaks if:* `_reset_layout` only clears settings (the rejected option in §8) —
  the column keeps the widened width until the widget is next constructed. The
  movability clause breaks if §4.2's capture is placed before
  `setSectionsMovable(True)`: the restored "default" then carries `movable=False`
  and every remembered header silently stops being drag-reorderable (§2.1 row 3).
  The third clause breaks if the restore is wrapped in `blockSignals` without a
  `finally`, or in any construct that leaves the header's signals blocked:
  persistence then ends for the session, and every other leg here still passes
  because they all resize *before* the reset. Without these clauses nothing in
  the suite would notice either failure.
  *Test:* `tests/features/table_state/test_table_state.py::test_FIBR0192_INV5_reset_layout_restores_live_headers`.
- **INV-6** — **A reset survives a restart.** After `_reset_layout()`, a freshly
  constructed widget shows default columns — i.e. no *differing* saved state is
  left behind.
  *Breaks if:* the clear never runs, or it runs **before the resize while
  `reset_columns` does not run at all** — the resize's `sectionResized` then
  re-saves the user's pre-reset layout after the group was emptied, and the next
  construction restores it. This is precisely today's ordering plus the missing
  restore.
  *Does **not** break if* the clear merely runs before the restore: `reset_columns`
  has already put the header at its default by then, so any re-save carries the
  default state and a rebuild still shows default columns. That ordering is
  untidy, not incorrect — §4.4 reason 2 says so, and no invariant here
  discriminates it (§11).
  *Note:* stated as "a rebuild shows the default", not "the INI has no `columns`
  group". Qt may defer the layout pass that emits `sectionResized` until after
  `_reset_layout` returns, in which case a key reappears holding the *default*
  state — visually identical, and an emptiness assertion would fail on a correct
  build. This is the caution the roadmap bullet recorded.
  *Test:* `tests/features/table_state/test_table_state.py::test_FIBR0192_INV6_reset_layout_survives_a_rebuild`.
- **INV-7** — **Reset layout is safe with no workspace.** Invoked before unlock,
  when the `Window` menu is enabled but no tables exist, `_reset_layout()` does
  not raise.
  *Breaks if:* `reset_columns` is passed `self._workspace`, which is `None` until
  a vault is open.
  *Test:* `tests/features/table_state/test_table_state.py::test_FIBR0192_INV7_reset_layout_before_unlock_does_not_raise`.
- **INV-8** — **A reset restores the BUILD-TIME default, not the user's saved
  layout — and re-sorts the rows with it.** Seed `columns/transactions_table` in
  the window INI with a non-default layout **before** the widget is constructed,
  so the construction restores it; then `_reset_layout()`. Two clauses:
  (a) the column returns to its build-time width, not the seeded one;
  (b) on a table with an active user sort, the row order after the reset matches
  the restored sort indicator.
  *Breaks if:* §4.2's capture is placed *after* the `restoreState` — the stored
  "default" is then the seeded layout, and the reset restores the very thing the
  user asked to be rid of. Every other leg in this spec passes on a first run
  with an empty INI, so this is the only fixture that discriminates it — and a
  returning user is the *normal* case, which is what makes the gap worth closing
  rather than deferring. Clause (b) breaks if the restore is wrapped in
  `blockSignals` (§4.3): the indicator flips to the default while the rows keep
  the user's old order (§2.1 row 6).
  *Test:* `tests/features/table_state/test_table_state.py::test_FIBR0192_INV8_reset_restores_build_time_default_not_saved_state`.

## 6. Failure modes

- **A deferred layout re-saves after the clear.** Covered above; the consequence
  is a `columns/*` key holding the default state, which restores to the same
  picture. INV-6 is phrased to be true either way.
- **Someone "tidies up" the stderr `TypeError` with `blockSignals`.** The most
  likely future regression in this design, because the fix looks obviously right
  and its damage is invisible: blocking kills the sort re-application that rides
  on `sortIndicatorChanged`, leaving a default sort arrow over the user's old row
  order on four click-sortable tables (§2.1 row 6). INV-8 clause 2 is the test
  that would go red. A blocked header that also escapes its `finally` stops
  persisting column changes for the whole session, with no symptom until the next
  launch — INV-5 clause 3.
- **`QTreeWidget.clear()` on every dashboard refresh.** `_render_column` clears
  each tree's *items* on every `refresh()`, after `remember_columns` has captured
  the default and connected its handlers. Measured (§2.1 row 8): column count,
  section widths, header labels and the dynamic property all survive, so INV-3
  holds across a refresh. Recorded because it is the first question a reader asks
  of this design, and the answer is not obvious from `clear()`'s name.
- **The import wizard open during the reset.** `ImportWizardWidget` is not a
  dialog — `_open_import` hands it to `_set_live`, which **replaces** the
  workspace (destroying it) and adds the wizard to the window's content stack. So
  a reset taken mid-import finds the wizard's preview table and none of the tab
  tables, because the tab tables no longer exist. Resetting the preview table is
  correct, not collateral: it is one of the nine remembered call sites.
- **The dashboard is built lazily.** It is not — `HomeView.__init__` adds both
  stack pages eagerly, so the three trees exist from construction whether or not
  the dashboard page is current. A future change to build the dashboard on demand
  would silently drop them from `reset_columns`' sweep and from INV-3.
- **A tree's column count changes after `remember_columns` runs.** A restored
  state carrying a different section count is ignored by Qt rather than applied.
  Both new surfaces set their columns before the call (§4.5), so this cannot
  arise today; a future column added to either must keep that order.
- **Testing visibility on a non-current page.** The Home trees sit on the
  dashboard page of a `QStackedWidget`. Probe them with `isHidden()`, not
  `isVisible()` — a widget on a non-current page reports `isVisible() == False`
  even after `setVisible(True)`, because the whole ancestor chain must be shown.

## 8. Alternatives considered (and rejected)

- **Rebuild the workspace on reset** instead of restoring headers in place. The
  machinery exists (`_clear_live` / `_set_live` / `_ensure_workspace`) and a
  rebuilt widget would find no saved state and use defaults. Rejected: it throws
  away the current tab, the selection and every tab's scroll position, re-reads
  the vault for a cosmetic action — and it cannot run at all before unlock, where
  the action is enabled (INV-7).
- **A module-level registry of default states keyed by `objectName`.** Rejected
  on lifetime: it outlives the widgets, leaks across a workspace rebuild and
  across tests in one session, and two windows in one process would collide on
  the same key. The dynamic property has exactly the right lifetime.
- **Persist the defaults into the INI** under their own group. Rejected: it
  writes to disk something derivable at build time in one call, and it would need
  a migration story for existing INIs the moment a column is added.
- **Have `remember_columns` take a `QHeaderView`** and sidestep the union.
  Rejected: the settings key is `columns/{view.objectName()}` and headers carry
  no object name — the call sites would each have to pass a key by hand, which is
  the duplication the FIBR-0012 cross-corruption bug came from.
- **Give the Forecast table click-to-sort** (user decision, §3 decision 1). Rejected
  because **Balance after** is a running total, meaningless outside date order.
- **Wrap the restore in `blockSignals`** to make the save handler's behaviour
  deterministic and silence the PySide6 `TypeError` (§2.1 row 5). An earlier
  draft of §4.3 specified exactly this. Rejected on measurement: the view's own
  re-sort rides on `sortIndicatorChanged`, so blocking leaves the restored sort
  arrow over the user's old row order (§2.1 row 6) — the split
  `tests/features/table_state/spec.md` row 4b already calls a defect. The
  `TypeError` is accepted instead.
- **Assert an empty `columns` group after a reset.** Rejected: it can fail
  against a correct build when Qt defers the resize (INV-6's note), and it is the
  "assert the user-visible outcome, not just an empty INI" caution the roadmap
  bullet recorded before drafting began.

## 10. Resource cost

One `QByteArray` per remembered view, held for the widget's lifetime — 127 bytes
measured for a two-column tree (§7 probe), more for a six-column table, so low
single-digit KB across all 11 views. `reset_columns` walks the
widget tree twice per invocation — a menu action a user triggers by hand, on a
tree of a few hundred widgets. Neither is measurable.

No new file, no new dependency, no new settings key beyond the `columns/*`
entries `remember_columns` already writes.
