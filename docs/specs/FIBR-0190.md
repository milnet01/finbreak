# FIBR-0190 — Family E: the Standard Bank "Payments / Deposits" current-account layout

**Status:** DRAFT (2026-08-03) — in the `/cold-eyes` gate, 1 loop run.
**Kind:** fix.
**Covers:** **FIBR-0190** only. One spec per roadmap item (`spec-format.md` §2).
**Extends:** [`FIBR-0050`](FIBR-0050.md) — the Standard Bank reader contract.
This spec adds a fifth layout family to that design and does not restate it.
**Invariant numbering:** this spec's invariants are **`INV-1`..`INV-10`**, bare,
as `spec-format.md` §7 requires for `spec_query` to parse them.
`tests/features/standard_bank_pdf/spec.md` already uses bare `INV-1`..`INV-14`
for **FIBR-0050's** invariants, so the two collide *in that file* — resolved the
way this project already resolves it everywhere else: the test contract
qualifies at the citation site (`FIBR-0190 INV-3`), exactly as
`tests/features/auto_update/spec.md` writes `FIBR-0131 INV-1` and
`tests/features/accounts/spec.md` writes `Source: FIBR-0005 INV-1`. The spec is
not renamed; the citation is qualified.
**Depends on:** FIBR-0050 (the reader), FIBR-0009 (`_normalise_to_plaintext`,
the page/row caps), FIBR-0171 (`closing_minor`, the forecast anchor),
FIBR-0216 (`_draft`'s per-row degradation).
**Source:** ROADMAP FIBR-0190, `user-request-2026-07-28`.

**Layman:** A real Standard Bank current-account statement imports **nothing**
today — not one of its 182 transactions. The reader already handles four page
layouts, and the bank prints this one in a fifth: the money-out column is headed
**Payments** instead of **Debits**, and money-in **Deposits** instead of
**Credits**. Because no reader recognises those words, the app falls back to its
generic table reader, which cannot tell the columns apart on a page with no
ruled lines — so it offers zero rows. This adds the missing reader.

decisions (D1–D11) · Design (**§4.3 the row grammar, §4.5 the completeness gate
and the `closing_minor` wiring**) · Invariants (INV-1..INV-10) · Failure modes ·
Tests · Alternatives rejected · Out of scope · Resource cost · What checks this ·
Cross-doc impact · Cold-eyes loop log.

## 1. Goal

A Standard Bank current-account statement printed in the
`Date Description Payments Deposits Balance` layout imports every one of its
transaction rows, with money-out negative in budget view, under the same
all-or-nothing integrity contract FIBR-0050 gives every other family.

Non-goal: the generic PDF fallback is **not** improved. It cannot split these
columns (§2.1) and this spec does not try to make it — the dedicated reader is
the fix.

---

## 2. Problem

### 2.1 Both import paths fail, so the user sees nothing

`detect_standard_bank` returns `None` for this layout, so the wizard falls
through to the generic FIBR-0009 PDF path, which finds the table but cannot
column-split its rows — the page carries no ruling lines for `pdfplumber` to
split on, so each row lands whole in cell 0. The result the ROADMAP bullet
records is `drafts=0, errors=183`.

The legal marker **is** present, so this is unambiguously a Standard Bank
statement; every family signature simply misses:

| Family | Signature it wants | Why it misses |
|---|---|---|
| A | `debits` + `credits` + `date` + `balance` | the word "credits" appears nowhere in the document |
| B | `posting` + `effective` + `debit` + `credit` + `balance` | none of them print |
| C | `date` + `description` + `amount` (+ card marker) | no "amount" column |
| D | `withdrawals` + `deposits` + `balance` | "deposits" prints, "withdrawals" does not |

So the money-out column is headed **Payments** and money-in **Deposits** — a
fifth transactional layout. "Payments" as a money-**out** heading inverts the
ordinary reading of the word and is the single most confusable thing in this
design; §4.3 and the implementation both carry a comment saying so.

### 2.2 What the reference statement actually contains — measured

Verified 2026-08-03 against the real 12-page, 3-month SBSA current-account
statement named in the ROADMAP bullet
(`/mnt/Emulators/storage_backup_2026-05-08/…`, **local-only — real payees and
balances; never committed, and nothing derived from it enters
`tests/fixtures/` un-anonymised**). Every figure below is an output of a probe
script run against that file, not a reading of it; the scripts print verdicts
and shapes only, never an amount or a payee.

**Document shape**

| Fact | Value |
|---|---|
| Pages | 12 |
| Transaction rows | **182** |
| Money tokens per row | **exactly 2, on every row** (histogram `{2: 182}`) |
| Rows money-out / money-in | 132 / 50 |
| Header, reprinted every page | `Date Description Payments Deposits Balance` |
| Opening anchor | `STATEMENT OPENING BALANCE <amount>`, page 1 only |
| Closing-balance line | **none, anywhere in the document** |
| `Statement from … to …` period line | **absent** — the summary prints `From:` / `To:` instead |
| Last-page column totals | `Payments -R<amount>` / `Deposits R<amount>`, **each alone on its own line** |

**Row token shapes** — the evidence the grammar in §4.3 rests on, and the part
a token count alone cannot establish (`_MONEY` matches the numeric core whether
or not an `R` or a trailing `-` sits beside it):

| Token | Measured form | Count |
|---|---|---|
| Date | `D[D] Mon YY`, **Title-case** (`28 Feb 26`) | 182 / 182 Title-case, **0** upper-case |
| Balance sign | **leading** minus (`-999.99`) | **0** rows carry a trailing-minus balance; **30** carry a leading-minus one |
| Amount / balance prefix | **bare** — no `R` on either money token | the grammar in §4.3, which admits no `R`, matches **182 / 182** |
| `R` elsewhere on a row | inside the **description** only | 3 rows — see D3 |

**Integrity, run against the proposed grammar**

| Check | Result |
|---|---|
| Rows matched by §4.3's grammar | **182 / 182** |
| Per-row \|delta\| == printed amount, sign included | **182 ok, 0 mismatched** |
| `Payments` total == Σ money-out | **True** |
| `Deposits` total == Σ money-in | **True** |
| Totals fall inside a transaction region | **No** — the summary page's `_table_region` is empty (`0:0`) |

Four things this reconciles or corrects:

- **The ROADMAP bullet says 183 rows; the truth is 182.** The generic fallback's
  "183 data rows" counted the `STATEMENT OPENING BALANCE` line as a data row.
  182 + 1 = 183. The bullet is annotated rather than rewritten (§12).
- **The balance's minus is leading, which is the opposite of Family A.**
  FIBR-0050 records Family A printing `730.55-`; E prints `-730.55`. This is the
  single most load-bearing measurement in the document, because a grammar built
  on A's convention would reject every overdrawn row and refuse the statement.
  D3 records what the grammar does about the other convention.
- **Dates are Title-case on every row**, so `_MON_RE` — which is Title-case and
  carries no `re.I` — is correct as-is. Recorded because "the header prints in
  caps" makes the opposite assumption look reasonable.
- **`opening + Σ amounts == final balance` is *not* independent evidence** and is
  therefore not listed above. It is entailed by the per-row check: the deltas
  telescope, so it restates the row above rather than corroborating it.

The probe scripts live in this session's scratchpad, not the repo — they read a
file that must never be committed, so they cannot ship as tests. What ships
instead is the anonymised fixture (§4.6), against which the same assertions run
in CI on committed bytes.

## 3. Scope decisions

- **D1 — A new Family E, not a Family-A variant.** Detection signature, row
  grammar, opening anchor, period handling and completeness gate all differ
  from A. A variant flag would branch at every one of those five points.
- **D2 — E is tried immediately after D and before B**, giving the full order
  **C → D → E → B → A**. Measured: zero collisions today (§4.1), so the slot is
  not load-bearing for the current corpus; it is defence for a future
  Money-Market statement that prints the word "payments" near its header.
  FIBR-0050 INV-2a fixes the old order string and is updated with it (§12).
- **D3 — The row grammar composes `_MONEY` and admits no `R` prefix and no
  trailing minus.** Two decimals are what stop a reference number inside a
  description being read as the amount — which matters here, because 3 of the
  182 rows carry an `R`-prefixed token *inside the description* (§2.2), and a
  money group loosened to accept `R` would become ambiguous against them.
  Trailing-minus is likewise excluded: it does not occur (0 / 182), and were a
  future statement to print one, failing the grammar gives an all-or-nothing
  refusal, which is the safe outcome. Silently accepting it would risk a
  wrong-signed balance.
- **D4 — `_cc_iso` is renamed `_dmy_iso` and shared,** not copied — it already
  converts `DD Mon YY` → ISO. Its signature is unchanged: it takes one
  space-joined `"28 Feb 26"` string and splits it internally, so
  `_parse_family_e` passes `f"{d} {mon} {yy}"` from its three capture groups
  rather than the signature growing three parameters for one caller.
- **D5 — `_looks_like_row`'s widening is opt-in per family,** not global.
  E's rows lead with a date, which no existing family's rows do; widening the
  shared predicate for everyone would let a Family-A continuation line that
  happens to start `12 Jan 25` be promoted to a row and then rejected by A's
  strict grammar — turning a working import into an all-or-nothing refusal.
- **D6 — `_anchor_balance` and `_capture_opening` *are* widened globally**, in
  deliberate contrast to D5, because the risk is not symmetric: they match a
  literal marker string, and adding `statement opening balance` can only change
  behaviour for a statement that prints that phrase. No A/B/C/D fixture does
  (`workspace_search "statement opening balance"` → 0 hits outside this spec).
  D5's hazard is a *shape* predicate that fires on incidental text; this is an
  exact phrase.
- **D7 — E has no printed period, so it must NOT join Family A's
  `period is None` refusal.** `parse` raises `_MISPARSE` when `period is None`
  **for Family A only**, because A needs the period for year inference. E carries
  a 2-digit year on every row and needs no inference, and §2.2 measured that E
  prints no `Statement from … to …` line at all — so an implementer who extends
  A's branch to cover E bricks every E statement. `_span` falls back to min/max
  parsed date, which is correct here.
- **D8 — The completeness gate uses the printed `Payments` / `Deposits`
  totals,** which are exact column sums (§2.2, measured). This is the part of
  the design that is *better* than Family A's: the per-row running-balance chain
  catches an interior dropped row (the next row's delta stops matching) but is
  **blind to a truncated tail** — if the final page's rows were dropped, every
  surviving row still reconciles. The totals catch exactly that.
- **D9 — The totals gate is optional-when-absent, and needs *both* totals.**
  One statement has been observed; a mandatory gate would refuse a valid
  statement whose summary is shaped differently. Requiring both is deliberate
  rather than lazy: a statement with no money-in rows plausibly prints no
  `Deposits` total, and half a gate — checking `Payments` alone — would pass a
  statement whose deposits were dropped wholesale. Absent totals degrade E to
  Family-A behaviour: the per-row gate alone.
- **D10 — `closing_minor` is supplied only when the totals gate actually
  ran.** E prints no closing balance, but its final row's running balance *is*
  the closing figure, and the totals gate is what makes it trustworthy. With
  no totals it is unverified, and FIBR-0171's forecast anchor gets `None`
  rather than a number nothing checked. §4.5 specifies the wiring.
- **D11 — Four fixtures** (§4.6): the happy path, the no-totals degradation, a
  totals-mismatch refusal, and an opening-marker-removed refusal. A gate with no
  red fixture is a gate nobody has seen fail.

No change to the generic PDF fallback (§1).

## 4. Design

All symbols below are in `src/finbreak/importers/standard_bank.py` unless said
otherwise.

### 4.1 Detection

`Family` gains `E = "E"`. `detect_standard_bank` gains, immediately after the
Family-D test and before the Family-B test (D2):

```python
if _signature_present(
    full_text, "date", "description", "payments", "deposits", "balance"
):
    return Family.E
```

The resulting order is **C → D → E → B → A**.

`_signature_present`'s default `window=3` is used because it is the value every
other multi-token signature uses, and consistency is the argument — the header
prints on one line, so a 1-line window would also work and would be marginally
tighter. The 3-line window is retained because a header that wraps under a
different page width is the failure this parameter exists for, and no false
positive is reachable at 3 (measured below).

**Measured — no existing statement is stolen.** Running the current detector
and the proposed E signature over all 13 committed fixtures gives zero rows
where both fire:

```
fixture                      current  E-sig fires?
family_a_current.pdf         A        False
family_b_homeloan.pdf        B        False
family_c_creditcard.pdf      C        False
family_d_moneymarket.pdf     D        False
non_sb.pdf                   None     False
   … 13 fixtures, 0 collisions
```

### 4.2 Region and fold

`_table_region` needs **no change**. Its non-C branch already accepts E's
header: the window carries "balance" and "date", and the guard that the header
line itself carry no money token is what rejects the
`Transaction details Available Balance:R…` summary line printed immediately
above it. Verified against the reference statement — the region starts at the
`STATEMENT OPENING BALANCE` line, which is what §4.4 needs.

**The last page's totals are outside every region** (§2.2: its `_table_region`
is empty, `0:0`, because that page reprints no column header). So they cannot be
folded into the final transaction's description, and no new `_TERMINATORS` entry
is needed.

`_fold` gains a **pass-through keyword only** — it forwards `dmy_lead` to the
predicate and its own logic is unchanged. `_looks_like_row` is where the
behaviour changes:

```python
def _looks_like_row(line: str, *, dmy_lead: bool = False) -> bool:
```

`dmy_lead=True` additionally accepts a line leading with a validated
`D[D] Mon YY` date, or carrying the E opening marker. Every existing call site
keeps today's behaviour by omitting the keyword (D5).

### 4.3 The row grammar

```
DD Mon YY  <description>  <signed amount>  <balance>
```

Money-out prints a **leading** `-`; money-in prints none. The balance may also
be negative and likewise carries a **leading** minus — the opposite of Family A's
trailing convention, measured in §2.2 and the reason D3 excludes the trailing
form rather than accepting both.

```python
_E_ROW = re.compile(
    rf"^\s*(\d{{1,2}}) ({_MON_RE}) (\d{{2}})\s+(.*?)\s+"
    rf"(-?{_MONEY.pattern})\s+(-?{_MONEY.pattern})\s*$"
)
```

No `re.I`: `_MON_RE` is Title-case and §2.2 measured every one of the 182 rows
as Title-case. Composing `_MONEY` (D3) requires two decimals, so a reference
number or a masked card number inside a description cannot be mistaken for the
amount.

`_parse_family_e` mirrors `_parse_family_d`'s shape: fold (with `dmy_lead=True`),
seed `prev_balance` from the opening anchor, then per row compute
`delta = balance - prev_balance` and call
`_verify_row(delta, amt_tok, fmt, check_sign=True)`. The draft's signed amount is
`delta`, exactly as A/B/D do it — the printed sign is the cross-check, never the
source (FIBR-0050 INV-7).

The implementation carries a comment on the one genuinely confusable point:
**"Payments" here is the money-OUT column**, despite the word ordinarily
suggesting money in.

### 4.4 The opening anchor

E prints `STATEMENT OPENING BALANCE <amount>` instead of Family A's
`Balance Brought Forward`. A module constant

```python
_E_OPENING = "statement opening balance"
```

is recognised by `_anchor_balance` and by `_capture_opening`, both of which
already scan for `_BROUGHT_FORWARD` and gain the E marker alongside it rather
than a second function (D6 explains why global widening is safe here where D5
forbids it for `_looks_like_row`).

`_capture_opening` must learn the marker because it otherwise **raises** on
every E statement — not because a checksum consumes its value. For E,
`_verify_checksum` returns early (§4.5), so the opening's real consumers are
`_parse_family_e`'s running-balance seed and the totals gate's final-balance
derivation.

**Which error a statement with no opening marker actually raises.** `parse`
runs the family parser *before* `_capture_opening`, so the message the user sees
is `_parse_family_e`'s, not `_capture_opening`'s. The two differ:

| Raiser | Message |
|---|---|
| `_parse_family_e` (`prev_balance is None`) — **the one that fires** | `couldn't find the opening balance on this statement — try your bank's CSV or OFX export` |
| `_capture_opening` (unreachable for this case) | `couldn't find the opening balance on this statement` |

`_parse_family_e` reuses the existing suffixed wording verbatim; §7.5 asserts
that string.

### 4.5 The completeness gate and the `closing_minor` wiring

`_CLOSING_MARKERS` gains `Family.E: ()` — an explicit empty tuple, so
`_capture_closing` returns `None` for E rather than raising `KeyError`, and the
"E prints no closing figure" fact is stated in the table where a reader looks
for it. `_verify_checksum`'s `closing is None` arm returns early for E as it
does for A.

E's real gate is a new module function with **one** call site:

```python
_E_TOTAL = re.compile(
    rf"^\s*(Payments|Deposits)\s+-?R({_MONEY.pattern})\s*$", re.I
)


def _verify_e_totals(
    full_text: str, drafts: list[TransactionDraft], opening: Decimal, exponent: int
) -> int | None:
    ...
```

- It iterates `full_text.splitlines()` and matches each line, exactly as
  `_capture_closing` does. It does **not** `search` the whole blob: the pattern
  is line-anchored and `re` does not treat `^`/`$` as line boundaries without
  `re.MULTILINE`, so a whole-blob scan would match nothing.
- The sign is **not** captured. Comparison is on **magnitudes**, in minor units:
  `abs(Σ negative draft amounts) == abs(payments_total)` and
  `abs(Σ positive draft amounts) == abs(deposits_total)`. Sign is already owned
  by INV-10 and the per-row gate; a signed comparison would raise on a valid
  statement that printed `Payments R<amount>` without the minus, and D9 already
  requires both totals to be present, which is what a magnitude comparison would
  otherwise be weaker about.
- **Both totals found** → verify as above, raising the existing all-or-nothing
  message on mismatch, and return
  `to_minor(opening, exponent) + Σ d.amount_minor` — the final running balance,
  in minor units.
- **Either total missing** → return `None`, no verification (D9).

**Wiring.** `parse` currently derives `closing_minor` solely from
`_capture_closing`, and rebuilds the returned `ParseResult` from scratch, so a
value returned by `_parse_family_e` would be discarded. `parse` therefore gains
one branch after the family dispatch and the existing `_verify_checksum` call:

```python
if family is Family.E:
    closing_minor = _verify_e_totals(full_text, result.drafts, opening, exponent)
```

placed after `opening` is computed, so it reuses that value rather than
re-scanning. For every other family `closing_minor` keeps today's derivation.

An E statement with **zero** transactions (a quiet month — FIBR-0050 INV-11
carries the same case for A and D) returns an empty-draft `ParseResult`;
`_verify_e_totals` compares Σ = 0 against the printed totals, which for a genuine
quiet month are absent or zero, and `closing_minor` is the opening balance
unchanged.

### 4.6 The fixtures

Four synthetic `reportlab` fixtures in
`tests/features/standard_bank_pdf/fixtures/`, authored the way every existing
one was (invented merchants, invented amounts, the fake account number
`00 000 000 0`, the SB legal marker). `reportlab` stays a probe/authoring tool
and does **not** become a project or test dependency — FIBR-0050 and
`tests/features/pdf_import/spec.md` already fix that rule.

- `family_e_current.pdf` — 2 pages, header reprinted on both, the opening
  line, the `Please verify` terminator, and a summary page carrying both
  totals each on its own line. Its rows deliberately include the shapes §2.2
  measured: a wrapped description, a description containing digits and a masked
  card number, a description containing an `R`-prefixed token, a money-in row,
  and a row that takes the running balance **negative with a leading minus**.
- `family_e_no_totals.pdf` — the same statement with the totals removed (D9).
- `family_e_totals_fail.pdf` — **rows untouched and internally consistent**;
  only the *printed totals* are altered, as a dropped tail would leave them.
  Editing rows instead would trip the per-row chain first and the leg would pass
  against an implementation with no totals gate at all (§7).
- `family_e_no_opening.pdf` — the opening-marker line removed (D11, §7.5).

The running balance in each is recomputed so the per-row gate passes, exactly
as the existing standard_bank fixtures were produced.

## 5. Invariants

Every `*Test:*` clause names a leg in §7. Only INV-2's and INV-9's can be
run today — they share §7.2, which needs no new code. The rest describe code
this spec is the contract for, so per `/write-spec`'s drafting rules they carry
no pasted output rather than a manufactured one; each was instead checked by the
mutation-on-paper question, and §7 records the one leg that changed as a result.

- **INV-1** — A document carrying the SB legal marker and a header block with
  `date`+`description`+`payments`+`deposits`+`balance` detects as `Family.E`.
  *Breaks it:* dropping any one of the five tokens from the signature.
  *Test:* §7.1 — `detect_standard_bank` on the **text extracted from**
  `family_e_current.pdf` returns `Family.E`.
- **INV-2** — Adding Family E changes no existing family's detection.
  *Breaks it:* loosening the signature to a subset of the five tokens — e.g.
  dropping `payments`, after which the Family-D fixture's
  `withdrawals`/`deposits`/`balance` header also satisfies E. (Re-ordering E
  against C/D/B/A is *not* a breaker this test can catch, since §4.1 measured
  that E fires on none of the 13 fixtures; D2 is defence, not a tested
  property.) *Test:* the 13 committed fixtures each still detect as the family
  they detect as today (§7.2) → run today against the *proposed* signature,
  13 fixtures, 0 collisions (§4.1).
- **INV-3** — Every line the fold classifies as an E **transaction** row —
  that is, every folded line other than the opening anchor, which
  `_anchor_balance` consumes first — parses under `_E_ROW`; one that does not
  raises the all-or-nothing `_MISPARSE` ValueError rather than being skipped.
  *Breaks it:* a `continue` in place of the raise — which is what turns a
  mis-parse into a silent under-import.
  *Test:* §7.9 — a region line the fold accepts but `_E_ROW` rejects, asserting
  the raise.
- **INV-4** — An E row's stored amount is the running-balance **delta**, and
  the printed amount must agree with it in magnitude *and* sign.
  *Breaks it:* taking the printed amount as the stored value; the row would
  then survive a balance column the parse had mis-read.
  *Test:* §7.3 — assert each draft's `amount_minor` equals the difference of
  the two balances that bracket it.
- **INV-5** — The opening balance comes from `STATEMENT OPENING BALANCE`;
  a statement carrying neither that marker nor `brought forward` raises
  `_parse_family_e`'s suffixed opening-balance error (§4.4). *Breaks it:*
  seeding `prev_balance` from the first row's balance, which would silently
  swallow the first transaction. *Test:* §7.5 — `family_e_no_opening.pdf`
  raises, with the suffixed message asserted verbatim.
- **INV-6** — When both column totals print, |Σ money-out| equals the
  `Payments` total and |Σ money-in| equals the `Deposits` total, in minor units,
  or the import raises. *Breaks it:* dropping the final page's rows — the case
  the per-row chain cannot see (D8). *Test:* §7.6 —
  `family_e_totals_fail.pdf` raises.
- **INV-7** — When either total is absent, the import still succeeds on the
  per-row gate alone. *Breaks it:* making the totals mandatory, which refuses a
  valid statement. *Test:* §7.7 — `family_e_no_totals.pdf` imports, drafts
  non-empty.
- **INV-8** — `closing_minor` is `opening + Σ amount_minor` when INV-6's
  gate ran, and `None` otherwise. *Breaks it:* supplying it unconditionally,
  which hands FIBR-0171's forecast an anchor nothing verified; or leaving
  `parse`'s existing `_capture_closing`-only derivation in place, which yields
  `None` even when the gate did run. *Test:* §7.7 (the `None` arm) and §7.8
  (the present arm).
- **INV-9** — Families A, B and D fold identically before and after this
  change. *Breaks it:* widening `_looks_like_row` globally instead of behind
  the `dmy_lead` keyword (D5). *Test:* §7.2 for detection, plus the existing
  A/B/D end-to-end legs run unchanged — see §11 for what this does *not* cover.
- **INV-10** — A row in the `Payments` column stores a **negative**
  `amount_minor`. *Breaks it:* reading "Payments" as money-in — the single most
  likely misreading in this layout (§2.1).
  *Test:* §7.3 — assert a known money-out row's `amount_minor < 0`.

## 6. Failure modes

| Case | Behaviour |
|---|---|
| Header present, no opening marker | `_parse_family_e`'s suffixed opening-balance ValueError (INV-5, §4.4) |
| A folded line that is not a valid E row | `_MISPARSE` ValueError, whole statement refused (INV-3) |
| Row amount disagrees with its balance delta | existing "didn't add up" ValueError (INV-4) |
| Both totals present and inconsistent | all-or-nothing ValueError (INV-6) |
| Either total absent | import succeeds, `closing_minor` is `None` (INV-7, INV-8) |
| Zero transactions (quiet month) | empty-draft `ParseResult`; totals compare against Σ = 0; `closing_minor` is the opening balance when the gate ran (§4.5) |
| Balance printed with a **trailing** minus | `_MISPARSE` — deliberate, D3; does not occur in the reference statement (0 / 182) |
| A printed `0.00` row | degrades to a `RowError` for that row only, statement still imports — existing `_draft` behaviour (FIBR-0216), unchanged by this spec |
| Statement exceeds the page / row caps | existing FIBR-0009 caps, unchanged |

## 7. Tests

New legs in `tests/features/standard_bank_pdf/test_standard_bank.py`, with the
contract rows added to that directory's `spec.md` under the `INV-*` names.

1. **Detection** — text extracted from `family_e_current.pdf` →
   `Family.E` (INV-1).
2. **No regression** — a parametrised leg over the 13 existing fixtures
   asserting each still detects as today's family (INV-2, INV-9).
3. **End-to-end** — parse `family_e_current.pdf`; assert the row count, that
   each draft's `amount_minor` equals its bracketing balance difference
   (INV-4), that money-out rows are negative (INV-10), that the wrapped
   description is folded whole, and that the leading-minus negative-balance row
   parses.
4. **Grammar unit legs** — `_E_ROW` against synthetic strings: a description
   containing a 2-decimal-looking reference, a masked card number, an
   `R`-prefixed description token, a leading-minus balance, a money-in row, and
   a **rejection** leg for a trailing-minus balance (D3).
5. **Opening** — `family_e_no_opening.pdf` raises, message asserted verbatim
   (INV-5).
6. **Totals gate red** — `family_e_totals_fail.pdf` raises (INV-6).
7. **Totals absent** — `family_e_no_totals.pdf` imports, `closing_minor is
   None` (INV-7, INV-8).
8. **`closing_minor` present** — `family_e_current.pdf` yields
   `opening + Σ amount_minor` in minor units (INV-8).
9. **Mis-parse raises, never skips** — a synthetic region line the fold accepts
   under `dmy_lead=True` but `_E_ROW` rejects (a date-led line with one money
   token), asserting `_MISPARSE` (INV-3).

Legs 1–9 cannot be run until the code exists. Each was checked by the
mutation-on-paper question — *which rule makes this fixture fail, and is it the
rule under test?* Two needed the check and changed as a result:

- **Leg 6** — a totals-mismatch fixture built by editing *rows* would fail the
  per-row chain first, so the leg would pass against an implementation with no
  totals gate at all. The fixture therefore alters **only the printed totals**
  (§4.6).
- **Leg 9** — was originally folded into leg 3, which asserts only on a
  well-formed statement and so could never exercise the raise-vs-skip branch
  INV-3 names. It is now its own leg with its own fixture text.

## 8. Alternatives considered (and rejected)

- **Fix the generic PDF fallback to split columns without ruling lines.**
  Rejected: it would need x-coordinate clustering across the whole page, a far
  larger and riskier change than a 5-column grammar, and it would still be
  guessing where a dedicated reader knows.
- **Family-A variant flag instead of a new family.** Rejected under D1.
- **Global widening of `_looks_like_row`.** Rejected under D5 — it can convert
  a working Family-A import into a refusal. (`_anchor_balance` and
  `_capture_opening` *are* widened globally; D6 says why the two cases differ.)
- **Accepting a trailing-minus balance as well as a leading one.** Rejected
  under D3 — it does not occur, and refusing is safer than guessing a sign.
- **Skip the completeness gate, matching Family A.** Rejected under D8: the
  totals are printed, they are exact, and without them a truncated tail imports
  silently and wrongly. This is a money-critical project (`CLAUDE.md`).
- **Make the totals gate mandatory.** Rejected under D9 — one observed
  statement is not enough evidence to refuse every statement without them.
- **Verify only whichever total is present.** Rejected under D9 — half a gate
  passes a statement whose deposits were dropped wholesale.
- **A signed comparison in the totals gate.** Rejected under §4.5 — it raises on
  a valid statement printing `Payments R<amount>` with no minus.
- **Adding `payments` to `_HEADER_TOKENS`.** Rejected as speculative: the
  header is excluded from the region by `_table_region` before `_is_boilerplate`
  is ever consulted (§4.2), and `_HEADER_TOKENS` deliberately excludes
  `description`, so an E header could never match it anyway.

## 10. Resource cost

Two passes per E statement, with **different bounds**: one regex pass over the
transaction region, linear in `len(region_lines)` and bounded by `_MAX_PDF_ROWS`;
and one scan of `full_text.splitlines()` for the two totals, linear in the whole
document and bounded by `_MAX_PDF_PAGES` (both FIBR-0009). Neither runs for any
other family. No new dependency, no schema change, no migration.
