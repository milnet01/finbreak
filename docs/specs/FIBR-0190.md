# FIBR-0190 — Family E: the Standard Bank "Payments / Deposits" current-account layout

**Status:** DRAFT (2026-08-03) — not yet through the `/cold-eyes` gate.
**Kind:** fix.
**Covers:** **FIBR-0190** only. One spec per roadmap item (`spec-format.md` §2).
**Extends:** [`FIBR-0050`](FIBR-0050.md) — the Standard Bank reader contract.
This spec adds a fifth layout family to that design and does not restate it;
FIBR-0050's INV-numbers are untouched and this document numbers its own from
INV-1 within the Family-E scope.
**Depends on:** FIBR-0050 (the reader), FIBR-0009 (`_normalise_to_plaintext`,
the page/row caps), FIBR-0171 (`closing_minor`, the forecast anchor),
FIBR-0216 (`_draft`'s per-row degradation).
**Source:** ROADMAP FIBR-0190, `user-request-2026-07-28`.

**Layman:** A real Standard Bank current-account statement imports **nothing**
today — not one of its 182 transactions. The app has readers for six Standard
Bank statement shapes, and this is a seventh the bank has started printing: the
money-out column is headed **Payments** instead of **Debits**, and money-in
**Deposits** instead of **Credits**. Because no reader recognises those words,
the app falls back to its generic table reader, which cannot tell the columns
apart on a page with no ruled lines — so it offers zero rows. This adds the
missing reader.

**Contents:** Goal · Problem (**§2.2 is the measured evidence**) · Scope
decisions (D1–D10) · Design (**§4.3 the row grammar, §4.5 the completeness
gate**) · Invariants (INV-1..INV-10) · Failure modes · Tests · Alternatives
rejected · Out of scope · Resource cost · What checks this · Cross-doc impact ·
Cold-eyes loop log.

## 1. Goal

A Standard Bank current-account statement printed in the
`Date Description Payments Deposits Balance` layout imports every one of its
transaction rows, with money-out negative in budget view, under the same
all-or-nothing integrity contract FIBR-0050 gives every other family.

Non-goal: the generic PDF fallback is **not** improved. It cannot split these
columns (§2.2) and this spec does not try to make it — the dedicated reader is
the fix.

---

## 2. Problem

### 2.1 Both import paths fail, so the user sees nothing

`detect_standard_bank` (`standard_bank.py`) returns `None` for this layout, so
the wizard falls through to the generic FIBR-0009 PDF path, which finds the
table but cannot column-split its rows — the page carries no ruling lines for
`pdfplumber` to split on, so each row lands whole in cell 0. The result the
ROADMAP bullet records is `drafts=0, errors=183` under every date format tried.

The legal marker **is** present, so this is unambiguously a Standard Bank
statement; every family signature simply misses:

| Family | Signature it wants | Why it misses |
|---|---|---|
| A | `debits` + `credits` + `date` + `balance` | the word "credits" appears nowhere in the document |
| B | `posting` + `effective` + `debit` + `credit` + `balance` | none of them print |
| C | `date` + `description` + `amount` (+ card marker) | no "amount" column |
| D | `withdrawals` + `deposits` + `balance` | "deposits" prints, "withdrawals" does not |

So the money-out column is headed **Payments** and money-in **Deposits** — a
fifth transactional layout. "Payments" as a money-**out** heading inverts the
ordinary reading of the word and is the single most confusable thing in this
design; §4.3 and the implementation both carry a comment saying so.

### 2.2 What the reference statement actually contains — measured

Verified 2026-08-03 against the real 12-page, 3-month SBSA current-account
statement named in the ROADMAP bullet
(`/mnt/Emulators/storage_backup_2026-05-08/…`, **local-only — real payees and
balances; never committed, and nothing derived from it enters
`tests/fixtures/` un-anonymised**). Every figure below is an output of a probe
script run against that file, not a reading of it; the scripts print verdicts
and shapes only, never an amount or a payee.

| Fact | Value | How measured |
|---|---|---|
| Pages | 12 | `probe_shape.py` |
| Transaction rows | **182** | `probe_shape.py` — date-leading lines |
| Money tokens per row | **exactly 2, on every row** | `probe_shape.py` histogram `{2: 182}` |
| Rows with money-out / money-in | 132 / 50 | `probe_totals.py` |
| Header, reprinted every page | `Date Description Payments Deposits Balance` | `probe_closing.py` |
| Opening anchor | `STATEMENT OPENING BALANCE <amount>`, page 1 only | `probe_closing.py` |
| Closing-balance line | **none, anywhere in the document** | `probe_closing.py` — the only closing-ish markers across 12 pages are the opening line and the `Please verify` terminator |
| Last-page column totals | `Payments -R<amount>` / `Deposits R<amount>` | `probe_closing.py` |
| `Payments` total == Σ money-out | **True** | `probe_totals.py` |
| `Deposits` total == Σ money-in | **True** | `probe_totals.py` |
| Per-row \|delta\| == printed amount, sign included | **182 ok, 0 mismatched** | `probe_totals.py` |
| opening + Σ amounts == final printed balance | **True** | `probe_totals.py` |

Two things this reconciles:

- **The ROADMAP bullet says 183 rows; the truth is 182.** The generic
  fallback's "183 data rows" counted the `STATEMENT OPENING BALANCE` line as a
  data row. 182 transactions + 1 opening line = 183. The bullet is annotated
  rather than rewritten (§12).
- **The bullet describes the row as "date-first with an already-SIGNED single
  amount plus a balance tail", which the measurement confirms**, and adds the
  part the bullet could not see: the shape is *uniform*. There is no row with a
  missing amount, no row with three money tokens, and no date-leading
  continuation line. That uniformity is what makes a strict grammar safe here.

The probe scripts live in this session's scratchpad, not the repo — they read a
file that must never be committed, so they cannot be shipped as tests. What
ships instead is the anonymised fixture (§4.6), against which the same
assertions run in CI on committed bytes.

## 3. Scope decisions

- **D1 — A new Family E, not a Family-A variant.** Detection signature, row
  grammar, opening anchor and completeness gate all differ from A. A variant
  flag would branch at every one of those four points, which is a family
  wearing a flag's clothes.
- **D2 — E is tried after D and before A** in `detect_standard_bank`.
  Measured: zero collisions today (§4.1), so the order is not load-bearing for
  the current corpus; it is defence for a future Money-Market statement that
  happens to print the word "payments" near its header.
- **D3 — The row grammar composes `_MONEY`,** rather than the looser
  `[\d.,]+` Families A and D use. A two-decimal requirement is what stops a
  reference number inside a description being read as the amount.
- **D4 — `_cc_iso` is renamed `_dmy_iso` and shared,** not copied. It already
  converts `DD Mon YY` → ISO, which is exactly E's date form.
- **D5 — `_looks_like_row`'s widening is opt-in per family,** not global.
  E's rows lead with a date, which no existing family's rows do; widening the
  shared predicate for everyone would let a Family-A continuation line that
  happens to start `12 Jan 25` be promoted to a row and then rejected by A's
  strict grammar — turning a working import into an all-or-nothing refusal.
- **D6 — The completeness gate uses the printed `Payments` / `Deposits`
  totals,** which are exact column sums (§2.2, measured). This is the part of
  the design that is *better* than Family A's, and the reason to do it rather
  than take the "no closing figure → per-row gate only" shortcut: the per-row
  running-balance chain catches an interior dropped row (the next row's delta
  stops matching) but is **blind to a truncated tail** — if the final page's
  rows were dropped, every surviving row still reconciles. The totals catch
  exactly that.
- **D7 — The totals gate is optional-when-absent.** One statement has been
  observed. A mandatory gate would refuse a valid statement whose summary page
  is shaped differently (a 1-month statement, say). Absent totals degrade E to
  Family-A behaviour: the per-row gate alone.
- **D8 — `closing_minor` is supplied only when the totals gate actually
  ran.** E prints no closing balance, but its final row's running balance *is*
  the closing figure, and the totals gate is what makes it trustworthy. With
  no totals it is unverified, and FIBR-0171's forecast anchor gets `None`
  rather than a number nothing checked.
- **D9 — No change to the generic PDF fallback** (§1).
- **D10 — Three fixtures, not one** (§4.6): the happy path, the no-totals
  degradation, and a totals-mismatch refusal. A gate with no red fixture is a
  gate nobody has seen fail.

## 4. Design

All symbols below are in `src/finbreak/importers/standard_bank.py` unless said
otherwise.

### 4.1 Detection

`Family` gains `E = "E"`. `detect_standard_bank` gains, between the D and A
tests:

```python
if _signature_present(
    full_text, "date", "description", "payments", "deposits", "balance"
):
    return Family.E
```

`_signature_present`'s default `window=3` is right: the header prints on one
line, and the 3-line window is what finds it on continuation pages.

**Measured — no existing statement is stolen.** Running the current detector
and the proposed E signature over all 13 committed fixtures gives zero rows
where both fire:

```
fixture                      current  E-sig fires?
family_a_current.pdf         A        False
family_b_homeloan.pdf        B        False
family_c_creditcard.pdf      C        False
family_d_moneymarket.pdf     D        False
non_sb.pdf                   None     False
   … 13 fixtures, 0 collisions
```

### 4.2 Region and fold

`_table_region` needs **no change**. Its non-C branch already accepts E's
header: the window carries "balance" and "date", and the guard that the header
line itself carry no money token is what rejects the
`Transaction details Available Balance:R…` summary line printed immediately
above it. Verified against the reference statement — the region starts at the
`STATEMENT OPENING BALANCE` line, which is what §4.4 needs.

`_fold` needs no change either, but the predicate it calls does. `_looks_like_row`
gains an opt-in second parameter:

```python
def _looks_like_row(line: str, *, dmy_lead: bool = False) -> bool:
```

`dmy_lead=True` additionally accepts a line leading with a validated
`D[D] Mon YY` date, or carrying the E opening marker. `_fold` takes and
forwards the same keyword. Every existing call site keeps today's behaviour by
omitting it (D5).

### 4.3 The row grammar

```
DD Mon YY  <description>  <signed amount>  <balance>
```

Money-out prints a leading `-`; money-in prints none. The **balance** may also
be negative (the reference account goes overdrawn mid-statement), and
`_is_negative` already accepts a minus "leading or trailing", so
`_signed_balance` handles both ends unchanged.

```python
_E_ROW = re.compile(
    rf"^\s*(\d{{1,2}}) ({_MON_RE}) (\d{{2}})\s+(.*?)\s+"
    rf"(-?{_MONEY.pattern})\s+(-?{_MONEY.pattern})\s*$"
)
```

Composing `_MONEY` (D3) requires two decimals, so a reference number or a
masked card number inside a description — both present in the reference
statement — cannot be mistaken for the amount. `_MON_RE` is the existing
validated month alternation, so a three-letter word in a description is not a
date.

`_parse_family_e` mirrors `_parse_family_d`'s shape: fold, seed `prev_balance`
from the opening anchor, then per row compute `delta = balance - prev_balance`
and call `_verify_row(delta, amt_tok, fmt, check_sign=True)`. The draft's
signed amount is `delta`, exactly as A/B/D do it — the printed sign is the
cross-check, never the source (FIBR-0050 INV-7).

The implementation carries a comment on the one genuinely confusable point:
**"Payments" here is the money-OUT column**, despite the word ordinarily
suggesting money in.

### 4.4 The opening anchor

E prints `STATEMENT OPENING BALANCE <amount>` instead of Family A's
`Balance Brought Forward`. A module constant

```python
_E_OPENING = "statement opening balance"
```

is recognised by `_anchor_balance` (so the parse loop seeds `prev_balance` from
it) and by `_capture_opening` (so the checksum's opening is found). Both
already scan for `_BROUGHT_FORWARD`; both gain the E marker alongside it rather
than a second function.

A statement with neither marker raises the existing friendly
"couldn't find the opening balance on this statement" — unchanged wording.

### 4.5 The completeness gate

`_CLOSING_MARKERS` gains `Family.E: ()` — an explicit empty tuple, so
`_capture_closing` returns `None` for E rather than raising `KeyError`, and the
"E prints no closing figure" fact is stated in the table where a reader looks
for it. `_verify_checksum`'s `closing is None` arm returns early for E as it
does for A.

E's real gate is separate and new:

```python
_E_TOTAL = re.compile(
    rf"^\s*(Payments|Deposits)\s+(-?)R({_MONEY.pattern})\s*$", re.I
)
```

scanned over the full document text. When **both** totals are found:

- Σ of the negative draft amounts must equal the `Payments` total, and
- Σ of the positive draft amounts must equal the `Deposits` total,

or the import raises the existing all-or-nothing message. When either is
absent, the gate is skipped (D7) and `closing_minor` is `None` (D8).

Comparison is in **minor units**, via `to_minor`, matching `_verify_checksum` —
never `Decimal` equality on the parsed figures, which would make the gate
sensitive to a trailing-zero difference the minor-unit conversion removes.

### 4.6 The fixture

Three synthetic `reportlab` fixtures in
`tests/features/standard_bank_pdf/fixtures/`, authored the way every existing
one was (invented merchants, invented amounts, the fake account number
`00 000 000 0`, the SB legal marker). `reportlab` stays a probe/authoring tool
and does **not** become a project or test dependency — FIBR-0050 §D and
`tests/features/pdf_import/spec.md` already fix that rule.

- `family_e_current.pdf` — 2 pages, header reprinted on both, the opening
  line, the `Please verify` terminator, and a summary page carrying both
  totals. Its rows deliberately include the four shapes the reference
  statement contains: a wrapped description, a description containing digits
  and a masked card number, a money-in row, and a row that takes the running
  balance **negative**.
- `family_e_no_totals.pdf` — the same statement with the totals removed
  (D7's degradation path).
- `family_e_totals_fail.pdf` — totals present but inconsistent with the rows,
  as a dropped tail would leave them (D10).

The running balance in each is recomputed so the per-row gate passes, exactly
as the existing standard_bank fixtures were produced.

## 5. Invariants

Every `*Test:*` clause below names a leg in §7. Only INV-2's can be run today —
the others describe code this spec is the contract for, so per
`/write-spec`'s drafting rules they carry no pasted output rather than a
manufactured one; each was instead checked by the mutation-on-paper question
recorded in §7.

- **INV-1** — A document carrying the SB legal marker and a header block with
  `date`+`description`+`payments`+`deposits`+`balance` detects as `Family.E`.
  *Breaks it:* dropping any one of the five tokens from the signature.
  *Test:* §7.1 — `detect_standard_bank` on `family_e_current.pdf` returns
  `Family.E`.
- **INV-2** — Adding Family E changes no existing family's detection.
  *Breaks it:* placing E's test before C's, or loosening it to a subset of the
  five tokens. *Test:* the 13 committed fixtures each still detect as the
  family they detect as today (§7.2) → run today against the *proposed*
  signature, 13 fixtures, 0 collisions (§4.1).
- **INV-3** — Every line the fold classifies as an E row parses under `_E_ROW`;
  one that does not raises the all-or-nothing `_MISPARSE` ValueError rather
  than being skipped. *Breaks it:* a `continue` in place of the raise — which
  is what turns a mis-parse into a silent under-import.
  *Test:* §7.4's unit legs, plus a §7.3 region line mutated to an invalid
  shape, asserting `ValueError`.
- **INV-4** — An E row's stored amount is the running-balance **delta**, and
  the printed amount must agree with it in magnitude *and* sign.
  *Breaks it:* taking the printed amount as the stored value; the row would
  then survive a balance column the parse had mis-read.
  *Test:* §7.3 — assert each draft's `amount_minor` equals the difference of
  the two balances that bracket it.
- **INV-5** — The opening balance comes from `STATEMENT OPENING BALANCE`;
  a statement carrying neither that marker nor `brought forward` raises the
  friendly opening-balance error. *Breaks it:* seeding `prev_balance` from the
  first row's balance, which would silently swallow the first transaction.
  *Test:* §7.5 — the marker-removed fixture raises, message asserted.
- **INV-6** — When both column totals print, Σ money-out equals the `Payments`
  total and Σ money-in equals the `Deposits` total, in minor units, or the
  import raises. *Breaks it:* dropping the final page's rows — the case the
  per-row chain cannot see (D6).
  *Test:* §7.6 — `family_e_totals_fail.pdf` raises.
- **INV-7** — When the totals do not print, the import still succeeds on the
  per-row gate alone. *Breaks it:* making the totals mandatory, which refuses a
  valid statement. *Test:* §7.7 — `family_e_no_totals.pdf` imports, drafts
  non-empty.
- **INV-8** — `closing_minor` is the final row's balance when INV-6's gate ran,
  and `None` otherwise. *Breaks it:* supplying it unconditionally, which hands
  FIBR-0171's forecast an anchor nothing verified.
  *Test:* §7.7 (the `None` arm) and §7.8 (the present arm).
- **INV-9** — Families A, B and D fold identically before and after this
  change. *Breaks it:* widening `_looks_like_row` globally instead of behind
  the `dmy_lead` keyword (D5). *Test:* §7.2 for detection, plus the existing
  A/B/D end-to-end legs run unchanged — see §11 for what this does *not* cover.
- **INV-10** — A row in the `Payments` column stores a **negative**
  `amount_minor`. *Breaks it:* reading "Payments" as money-in — the single most
  likely misreading in this layout (§2.1).
  *Test:* §7.3 — assert a known money-out row's `amount_minor < 0`.

## 6. Failure modes

| Case | Behaviour |
|---|---|
| Header present, no opening marker | friendly opening-balance ValueError (INV-5) |
| A region line that is not a valid E row | `_MISPARSE` ValueError, whole statement refused (INV-3) |
| Row amount disagrees with its balance delta | existing "didn't add up" ValueError (INV-4) |
| Totals present and inconsistent | all-or-nothing ValueError (INV-6) |
| Totals absent | import succeeds, `closing_minor` is `None` (INV-7, INV-8) |
| A printed `0.00` row | degrades to a `RowError` for that row only, statement still imports — existing `_draft` behaviour (FIBR-0216), unchanged by this spec |
| Statement exceeds the page / row caps | existing FIBR-0009 caps, unchanged |

## 7. Tests

New legs in `tests/features/standard_bank_pdf/test_standard_bank.py`, with the
contract rows added to that directory's `spec.md`.

1. **Detection** — `family_e_current.pdf` → `Family.E` (INV-1).
2. **No regression** — a parametrised leg over the 13 existing fixtures
   asserting each still detects as today's family (INV-2, INV-9).
3. **End-to-end** — parse `family_e_current.pdf`; assert the row count, that
   the money-out rows are negative (INV-10), that the wrapped description is
   folded whole, and that the row taking the balance negative parses.
4. **Grammar unit legs** — `_E_ROW` against synthetic strings: a description
   containing a 2-decimal-looking reference, a masked card number, a negative
   balance, a money-in row (INV-3, D3).
5. **Opening** — a fixture text with the marker removed raises the friendly
   error (INV-5).
6. **Totals gate red** — `family_e_totals_fail.pdf` raises (INV-6).
7. **Totals absent** — `family_e_no_totals.pdf` imports, `closing_minor is
   None` (INV-7, INV-8).
8. **`closing_minor` present** — `family_e_current.pdf` yields the final row's
   balance in minor units (INV-8).

Legs 1–8 cannot be run until the code exists. Each was checked by the
mutation-on-paper question — *which rule makes this fixture fail, and is it the
rule under test?* Leg 6 is the one that needed the check: a totals-mismatch
fixture would also fail the per-row chain if its rows were edited to create the
mismatch, so the fixture must instead alter **only the printed totals**,
leaving every row internally consistent. Otherwise the leg would pass against
an implementation with no totals gate at all.

## 8. Alternatives considered (and rejected)

- **Fix the generic PDF fallback to split columns without ruling lines.**
  Rejected: it would need x-coordinate clustering across the whole page, a far
  larger and riskier change than a 5-column grammar, and it would still be
  guessing where a dedicated reader knows.
- **Family-A variant flag instead of a new family.** Rejected under D1.
- **Global widening of `_looks_like_row`.** Rejected under D5 — it can convert
  a working Family-A import into a refusal.
- **Skip the completeness gate, matching Family A.** Rejected under D6: the
  totals are printed, they are exact, and without them a truncated tail imports
  silently and wrongly. This is a money-critical project (`CLAUDE.md`).
- **Make the totals gate mandatory.** Rejected under D7 — one observed
  statement is not enough evidence to refuse every statement without them.
- **Adding `payments` to `_HEADER_TOKENS`.** Rejected as speculative: the
  header is excluded from the region by `_table_region` before `_is_boilerplate`
  is ever consulted (§4.2), and `_HEADER_TOKENS` deliberately excludes
  `description`, so an E header could never match it anyway.

## 9. Out of scope

- The generic PDF fallback (§1, D9).
- The other banks blocked on sample statements (FIBR-0074).
- Re-verifying against the real statement in CI — impossible by construction;
  the verification is local and one-time, and the fixture carries it forward.

## 10. Resource cost

One additional regex pass over the transaction region per E statement, plus one
full-text scan for the two totals. Both are linear in the already-bounded
region (`_MAX_PDF_ROWS`, FIBR-0009), and neither runs for any other family. No
new dependency, no schema change, no migration.
