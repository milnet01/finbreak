# FIBR-0086 — Account numbers + import auto-detect

Closed 2026-08-06. Spec: [`docs/specs/FIBR-0086-account-number-auto-detect.md`](../specs/FIBR-0086-account-number-auto-detect.md).

## What changed

- **`services/account_match.py`** (new) — `normalise_account_number` (digits
  only, leading zeros stripped) and the `match_account` ladder. Only an
  unambiguous single match ever changes what the user sees selected.
- **`importers/base.py`** — `SourceAccountHint` (number as printed, plus an
  optional name and family), carried on `ParseResult` as one new field appended
  last with a default.
- **`importers/standard_bank.py`** — `extract_account_number`, confined to the
  header block above `_table_region(...).start`, dispatched on families A, B
  and D only.
- **`importers/ofx_importer.py`** — threads the OFX account id into the hint.
- **`ui/import_wizard.py`** — matches before building the preview, seeds the
  destination combo, and explains the outcome on screen.
- **`ui/account_create.py`** (new) — create-an-account-from-this-statement
  dialog, pre-filled and fully editable.
- **`tests/features/account_detect/`** — 49 tests across four files.

Gate green: 1840 passed / 3 skipped, against a 1791 pre-change baseline.

## What was learned

- **The corpus overturned the obvious design.** Reading the number after the
  words "account number" is the natural implementation and it is wrong: on a
  credit-card statement that label belongs to the debit-order account, and it
  normalises to exactly the current account's number. Eleven of thirteen card
  statements would have filed under the current account. No amount of careful
  reading would have caught it — only measuring the real statements did.

- **Ordering was the whole feature.** Seeding the destination combo *after*
  building the preview, under a `QSignalBlocker`, suppresses the one signal that
  re-points the preview — so the screen would name the matched account while the
  transactions landed elsewhere. Reversing the order reddens INV-7a and leaves
  INV-7 green, which is the proof that INV-7a alone carries it.

- **A test that cannot fail is worse than a missing one.** Review found INV-2's
  named test unfalsifiable: its "foreign" account number sat in a row with no
  label, and the extractor is label-anchored, so no scan width could ever have
  captured it. It had been green from the first run and locked nothing. Three
  further paths were the same shape — the PDF ordering, the on-screen
  explanation, and family D. Each fix here was mutation-tested: revert it, watch
  exactly one test redden.

- **`show_modal` is non-blocking, and stubbing it hid that.** The first draft
  called it as though it returned a dialog code. The tests passed because they
  monkeypatched the helper, so the stub concealed a call that could not work;
  mypy caught it. The tests now drive the real dialog.

- **A redaction is not a fix, and the guard said otherwise.** The new INV-8
  scanner walks `git ls-files`, so the four real numbers redacted from HEAD
  earlier the same day remain in this public repo's history while the test
  reports clean. Filed as FIBR-0247 — the hazard is the false assurance.

## What was deferred

Filed rather than fixed, each with its evidence:

- **FIBR-0247** — the INV-8 scanner cannot see git history.
- **FIBR-0248** — `FINBREAK_CORPUS_NUMBERS` is wired nowhere, so that guard
  skips on every run.
- **FIBR-0249** — a remembered PDF password is stored against the pick-step
  account, which auto-detect now routinely changes.
- **FIBR-0250** — `normalise_account_number`'s zero-strip is ASCII-only while
  its digit filter is not. Can only fail to match, never mis-match.

Already deferred by the spec: FIBR-0240 (family C), FIBR-0241 (masked
matching), FIBR-0242 (family E), FIBR-0243 (OFX account type).
